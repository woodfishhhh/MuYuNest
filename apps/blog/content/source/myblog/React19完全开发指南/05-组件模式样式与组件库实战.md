# 组件模式、样式与组件库实战

组件化不是把每个 `div` 都拆成一个文件，而是给一块职责独立、结构能复用或接口稳定的 UI 划出边界。边界定好以后，再用 Props、组合、状态提升和样式隔离把组件连起来。

```text
业务需求
    ↓
划分组件职责
    ↓
设计 Props 与状态所有权
    ↓
选择组合、受控或封装模式
    ↓
隔离样式并验证复用性
    ↓
沉淀为可发布的组件库
```

## 组件边界

适合单独做成组件的内容，一般至少符合一条：

- 在界面上是职责明确的一块，比如卡片、菜单、对话框。
- 在好几个地方重复出现，结构和行为都差不多。
- 自己有一组状态、事件或生命周期逻辑。
- 需要用稳定的接口把内部实现藏起来。

函数组件的输入是 Props，输出是 React 节点。Props 描述的是调用方能控制什么，别把组件内部的每个实现细节都暴露出来：

```tsx
import type { ReactNode } from 'react';

interface CardProps {
  title: string;
  subtitle?: string;
  children: ReactNode;
  footer?: ReactNode;
}

export function Card({
  title,
  subtitle = '暂无补充信息',
  children,
  footer,
}: CardProps) {
  return (
    <article className="card">
      <header>
        <h2>{title}</h2>
        <p>{subtitle}</p>
      </header>
      <div>{children}</div>
      {footer != null && typeof footer !== 'boolean' ? (
        <footer>{footer}</footer>
      ) : null}
    </article>
  );
}
```

`ReactNode` 里的 `0` 是合法内容，所以不能用普通的 truthy 判断来决定渲不渲染容器，不然 `0` 会变成一段裸文本，而不是 `<footer>` 里的内容。

```tsx
<Card
  title="订单状态"
  footer={<button type="button">查看详情</button>}
>
  <p>订单已发货</p>
</Card>
```

`children` 是一个普通的 Prop，只是名字特殊，用来表达"把内容放进这个结构里"。比起给每种内容加一个专门的字符串属性，组合能更多地保留调用方的表达能力。

React 没有那种要注册到框架实例上的"全局组件"。组件在哪用，就在哪导入。全局消息、通知这类命令式能力，一般是一个服务 API 加一处统一的渲染宿主，组件本身并没有跳出 React 的组件树。

## 组件通信

### 父组件向下传值

父组件通过 Props 把数据和行为传给子组件。子组件别改收到的对象，把 Props 当成只读的快照：

```tsx
interface CounterViewProps {
  value: number;
  onIncrement: () => void;
}

function CounterView({ value, onIncrement }: CounterViewProps) {
  return (
    <div>
      <output>{value}</output>
      <button type="button" onClick={onIncrement}>增加</button>
    </div>
  );
}
```

### 子组件通过回调上报事件

"子传父"其实不是反过来写父组件，而是父组件把回调传下去，子组件在合适的时候调用：

```tsx
import { useState } from 'react';

export function CounterPanel() {
  const [count, setCount] = useState(0);

  return (
    <CounterView
      value={count}
      onIncrement={() => setCount((current) => current + 1)}
    />
  );
}
```

回调名优先描述发生的业务事件，比如 `onSave`、`onSelect`，别写成意思模糊的 `callback`。

### 兄弟组件先考虑状态提升

两个兄弟组件要共享数据时，最直接的做法是把状态提到它们最近的共同父组件：

```tsx
function TemperatureDashboard() {
  const [celsius, setCelsius] = useState(20);

  return (
    <>
      <TemperatureInput value={celsius} onChange={setCelsius} />
      <TemperaturePreview value={celsius} />
    </>
  );
}
```

发布订阅能连接完全独立的模块，但会藏起数据的来源，还多了清理订阅的负担。普通的 React 组件之间，优先用状态提升、Context 或明确的外部 Store，别为了简单的兄弟通信引入事件总线。

## 受控与非受控

"受控"说的是当前的值由谁持有，不只是一种表单写法。

| 模式 | 当前值的来源 | 读取方式 | 适合场景 |
|---|---|---|---|
| 受控 | React State / 父组件 Props | 直接读取状态 | 即时校验、联动、格式化、外部重置 |
| 非受控 | DOM 自己维护 | `ref` 或提交时 `FormData` | 简单表单、低频读取、接入命令式库 |

### 受控输入

文本输入用 `value` 受控，复选框和单选框用 `checked` 受控。对应的 `onChange` 必须同步更新背后的状态：

```tsx
import { useState } from 'react';

export function ProfileForm() {
  const [name, setName] = useState('');
  const [subscribed, setSubscribed] = useState(false);

  return (
    <form>
      <label>
        昵称
        <input
          name="name"
          value={name}
          onChange={(event) => setName(event.target.value)}
        />
      </label>

      <label>
        <input
          name="subscribed"
          type="checkbox"
          checked={subscribed}
          onChange={(event) => setSubscribed(event.target.checked)}
        />
        接收通知
      </label>
    </form>
  );
}
```

一个输入在整个生命周期里不能从受控切成非受控，也不能反过来切。最常见的错误是先传 `undefined`，请求完成后再传字符串：

```tsx
// 错误风险：profile.name 初次渲染时可能是 undefined。
<input value={profile?.name} onChange={handleChange} />

// 保持整个生命周期都是字符串。
<input value={profile?.name ?? ''} onChange={handleChange} />
```

值本来就是只读的话，可以显式加 `readOnly`。别用一个没有 `onChange` 的 `value` 假装默认值。

### 非受控输入

`defaultValue` 和 `defaultChecked` 只提供初始值，之后的输入由 DOM 保存：

```tsx
import { type FormEvent, useRef } from 'react';

export function QuickSearch() {
  const inputRef = useRef<HTMLInputElement>(null);

  function handleSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const keyword = inputRef.current?.value.trim() ?? '';
    console.log(keyword);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input ref={inputRef} name="keyword" defaultValue="React 19" />
      <button type="submit">搜索</button>
    </form>
  );
}
```

文件输入的值由用户和浏览器决定，不能用字符串 `value` 写入文件路径，所以 `<input type="file">` 一直按非受控的方式读：

```tsx
import { useRef } from 'react';

function UploadForm() {
  const fileRef = useRef<HTMLInputElement>(null);

  function upload() {
    const file = fileRef.current?.files?.[0];
    if (file) console.log(file.name, file.size);
  }

  return (
    <>
      <input ref={fileRef} type="file" accept="image/*" />
      <button type="button" onClick={upload}>上传</button>
    </>
  );
}
```

## `lazy` 与 `Suspense`

`lazy` 把动态导入包装成组件，构建工具据此拆分代码；`Suspense` 在代码还没就绪时展示 `fallback`：

```tsx
import { lazy, Suspense, useState } from 'react';

// 必须在模块顶层声明，不能放进组件函数或事件回调。
const SettingsPage = lazy(() => import('./SettingsPage'));

export function Workspace() {
  const [showSettings, setShowSettings] = useState(false);

  return (
    <>
      <button type="button" onClick={() => setShowSettings(true)}>
        打开设置
      </button>

      {showSettings && (
        <Suspense fallback={<p>设置加载中...</p>}>
          <SettingsPage />
        </Suspense>
      )}
    </>
  );
}
```

`lazy` 默认读模块的 `default` 导出。模块只有命名导出的话，可以显式转一下：

```tsx
const Chart = lazy(() =>
  import('./Chart').then((module) => ({ default: module.Chart })),
);
```

别在组件内部调 `lazy` 创建新的组件类型。每次渲染都产生一个新类型，子树会被重新挂载，局部状态也会被重置。

Suspense 边界要放在用户体验上合理的位置：整页路由可以用页面骨架，局部的图表可以只替换图表区域。边界放得太高，整页会闪回加载态；切得太碎，又会到处跳动。

React 19 的 `use` 能读 Promise 或 Context。读 Promise 时，Promise 必须来自稳定的缓存、路由数据层或服务端传入；别在客户端组件每次渲染时临时创建一个新的请求 Promise：

```tsx
import { Suspense, use } from 'react';

interface Product {
  id: number;
  name: string;
}

function ProductList({ data }: { data: Promise<Product[]> }) {
  const products = use(data);
  return <ul>{products.map((item) => <li key={item.id}>{item.name}</li>)}</ul>;
}

export function ProductSection({ data }: { data: Promise<Product[]> }) {
  return (
    <Suspense fallback={<p>商品加载中...</p>}>
      <ProductList data={data} />
    </Suspense>
  );
}
```

`Suspense` 不是任意 `useEffect + fetch` 的通用加载指示器。普通的请求要么自己维护状态，要么交给支持 Suspense 的框架、路由数据层或缓存库。

## HOC 高阶组件

高阶组件是"接收一个组件、返回增强组件"的函数。常见于旧代码、类组件生态，以及需要批量包装第三方组件的场景：

```text
原组件 + 横切能力
        ↓
      HOC
        ↓
保留原 Props 的增强组件
```

一个类型安全的权限 HOC：

```tsx
import type { ComponentType } from 'react';

type Role = 'admin' | 'member';

function useCurrentRole(): Role {
  return 'member';
}

export function withPermission<P extends object>(
  Wrapped: ComponentType<P>,
  requiredRole: Role,
) {
  function WithPermission(props: P) {
    const role = useCurrentRole();

    if (role !== requiredRole) {
      return <p>没有访问权限</p>;
    }

    return <Wrapped {...props} />;
  }

  WithPermission.displayName =
    `withPermission(${Wrapped.displayName ?? Wrapped.name ?? 'Component'})`;

  return WithPermission;
}
```

用 HOC 时要守住几条边界：

- 不改原组件，用容器包装并透传 Props。
- HOC 在模块顶层应用，别在渲染过程中反复创建增强组件。
- 设置 `displayName`，不然调试树里很难认出包装层。
- 静态属性、Ref 和泛型信息不会因为包了一层就自动完整继承，要按约定显式处理。
- 包装层太多会变成"包装地狱"；新代码一般优先用自定义 Hook、普通组合或 Render Props。

HOC 适合复用"怎么连接组件"的逻辑，自定义 Hook 更适合复用"怎么计算或订阅状态"的逻辑，两者解决的问题不完全一样。

## Portal

`createPortal(children, domNode)` 把一段 JSX 放到指定的 DOM 节点，常用在模态框、通知、浮层和 Tooltip 上，避免被祖先的 `overflow`、层叠上下文或定位规则干扰：

```tsx
import type { ReactNode } from 'react';
import { createPortal } from 'react-dom';

interface ModalProps {
  title: string;
  onClose: () => void;
  children: ReactNode;
}

export function Modal({ title, onClose, children }: ModalProps) {
  return createPortal(
    <div className="modal-backdrop" onClick={onClose}>
      <section
        role="dialog"
        aria-modal="true"
        aria-label={title}
        className="modal"
        onClick={(event) => event.stopPropagation()}
      >
        <h2>{title}</h2>
        {children}
        <button type="button" onClick={onClose}>关闭</button>
      </section>
    </div>,
    document.body,
  );
}
```

Portal 只改变物理 DOM 的挂载位置，它在 React 树里还是原来那个子节点，所以：

- Portal 里面照样能读到原树上方提供的 Context。
- 事件按 React 树传播，不按最终的 DOM 树传播。
- 点 Portal 里的内容，可能触发原来 React 父节点的事件，需要的话在正确的位置停止传播。

生产级的对话框还需要焦点圈定、打开后聚焦、关闭后归还焦点、Escape 关闭和背景滚动锁定。Portal 只解决挂载位置，可访问性不会自动做好。

## 样式方案

CSS Modules、CSS-in-JS 和 Tailwind 都不是 React 内置的样式系统。它们由构建工具或第三方库提供，React 只负责输出 `className`、`style` 这些 DOM 属性。

### CSS Modules：构建期局部类名

在 Vite 等工具里，把文件命名成 `*.module.css` 就能导入类名映射：

```css
/* Button.module.css */
.button {
  border: 0;
  padding: 8px 14px;
  background: #1677ff;
  color: white;
}

.danger {
  background: #d4380d;
}

:global(.legacy-focus-ring) {
  outline: 2px solid currentColor;
}
```

```tsx
import styles from './Button.module.css';

export function DeleteButton() {
  return (
    <button className={`${styles.button} ${styles.danger}`} type="button">
      删除
    </button>
  );
}
```

构建工具会把局部类名转成带哈希或作用域信息的名字，降低冲突的概率。`:global(...)` 是显式的逃生口，只该用在全局约定或第三方类名上，别把整个模块又变回全局 CSS。

### CSS-in-JS：样式与组件逻辑共置

以 `styled-components` 为例，库会创建带样式的 React 组件，还能根据 Props 算动态样式：

```tsx
import styled from 'styled-components';

const ActionButton = styled.button<{ $tone: 'primary' | 'danger' }>`
  border: 0;
  padding: 8px 14px;
  color: white;
  background: ${({ $tone }) => ($tone === 'danger' ? '#d4380d' : '#1677ff')};
`;

export function Toolbar() {
  return <ActionButton $tone="primary">保存</ActionButton>;
}
```

这类方案适合强动态的主题和组件级的样式 API，但要考虑依赖体积、运行时插入样式、SSR 配置和调试体验。不同的 CSS-in-JS 库实现差别很大，有的依赖运行时，有的在构建期就提取出来了，不能一概而论。

### Tailwind CSS：原子类组合

Tailwind 把常用的声明映射成小粒度的工具类。以 Tailwind CSS 4 和 Vite 为例：

```bash
npm install tailwindcss @tailwindcss/vite
```

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import tailwindcss from '@tailwindcss/vite';

export default defineConfig({
  plugins: [react(), tailwindcss()],
});
```

```css
/* src/index.css */
@import "tailwindcss";
```

```tsx
export function HeroAction() {
  return (
    <button
      type="button"
      className="rounded bg-blue-600 px-4 py-2 font-semibold text-white hover:bg-blue-700"
    >
      开始使用
    </button>
  );
}
```

工具类能省掉起名的成本，还让响应式和状态变体就近写在组件旁边；代价是 JSX 的类名很长，设计约束需要团队来管。重复的组合要提成组件，别用字符串常量再发明一层难追踪的样式系统。

### 如何选择

| 方案 | 隔离方式 | 动态能力 | 主要代价 |
|---|---|---|---|
| CSS Modules | 构建期类名映射 | 通过条件类名 | 样式与组件分文件 |
| CSS-in-JS | 库生成类名与样式 | Props、主题能力强 | 依赖与潜在运行时成本 |
| Tailwind CSS | 原子工具类约定 | 条件拼接与变体 | JSX 类名密集 |

选择标准是项目现状、设计系统和运行环境，不是"哪一种最像 React"。React 本身不替项目做这个决定。

## 组件库构建

Tree 组件同时涉及类型设计、递归渲染、入口导出、库模式构建、声明文件和 npm 包验证。真正的组件库不只是"能显示"，还要给使用方提供稳定的运行时代码、类型和样式入口。

### 目录与公共入口

```text
packages/
  components/
    tree/
      Tree.tsx
      Tree.css
      types.ts
      index.ts
    index.ts
  index.ts
example/
  App.tsx
vite.config.ts
package.json
```

组件自己的 `index.ts` 管局部出口，总入口汇总公共 API：

```ts
// packages/components/tree/index.ts
export { Tree } from './Tree';
export type { TreeNode, TreeProps } from './types';

// packages/index.ts
export * from './components/tree';
```

公共类型也要导出。不然使用方虽然能渲染组件，却复用不了组件要求的数据结构。

### 一个受控的递归 Tree

```ts
// packages/components/tree/types.ts
export interface TreeNode {
  id: string;
  label: string;
  children?: readonly TreeNode[];
}

export interface TreeProps {
  data: readonly TreeNode[];
  checkedKeys: readonly string[];
  onCheckedChange: (id: string, checked: boolean) => void;
}
```

```tsx
// packages/components/tree/Tree.tsx
import { useMemo } from 'react';
import type { TreeNode, TreeProps } from './types';
import './Tree.css';

interface BranchProps {
  nodes: readonly TreeNode[];
  checked: ReadonlySet<string>;
  onCheckedChange: TreeProps['onCheckedChange'];
}

function Branch({ nodes, checked, onCheckedChange }: BranchProps) {
  return (
    <ul className="ui-tree__list">
      {nodes.map((node) => (
        <li key={node.id} className="ui-tree__node">
          <label>
            <input
              type="checkbox"
              checked={checked.has(node.id)}
              onChange={(event) => onCheckedChange(node.id, event.target.checked)}
            />
            {node.label}
          </label>

          {node.children?.length ? (
            <Branch
              nodes={node.children}
              checked={checked}
              onCheckedChange={onCheckedChange}
            />
          ) : null}
        </li>
      ))}
    </ul>
  );
}

export function Tree({ data, checkedKeys, onCheckedChange }: TreeProps) {
  const checked = useMemo(() => new Set(checkedKeys), [checkedKeys]);
  return <Branch nodes={data} checked={checked} onCheckedChange={onCheckedChange} />;
}
```

递归成立要两个条件：有子节点时调用自己，没有子节点时停下。组件的选择状态由调用方持有，所以它遵守受控组件的约定，不会在内部再复制一份容易不同步的数据。

父子级联勾选属于业务策略：有的树要求选了父节点就全选子节点，有的允许半选，有的只允许选叶子节点。组件库要把策略写进约定，或者作为可选能力提供，别偷偷改传进来的 `data`。

### Vite 库模式与类型声明

```ts
// vite.config.ts
import { resolve } from 'node:path';
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import dts from 'vite-plugin-dts';

export default defineConfig({
  plugins: [
    react(),
    dts({
      include: ['packages'],
      insertTypesEntry: true,
    }),
  ],
  build: {
    lib: {
      entry: resolve(import.meta.dirname, 'packages/index.ts'),
      formats: ['es', 'cjs'],
      fileName: (format) => format === 'es' ? 'index.js' : 'index.cjs',
      cssFileName: 'style',
    },
    rolldownOptions: {
      external: ['react', 'react-dom', 'react/jsx-runtime'],
    },
  },
});
```

`react` 和 `react-dom` 应该由使用方的项目提供。把它们外置并声明成 `peerDependencies`，能避免包体重复，也避免页面里出现两份 React。要输出 UMD 的话，还要配全局变量名；现代包管理器的场景一般优先提供 ESM，再按兼容目标决定要不要保留 CJS 或 UMD。

```json
}
```

`exports` 才是使用方真正看到的公共边界。没列出来的内部文件，业务代码不该深层导入。样式要是由构建产物单独输出，也要给一个稳定的入口，并且别被错误的 Tree Shaking 当成没有副作用的代码删掉。

### 发布前先验证包，而不是只验证源码

```bash
npm run build
npm pack --dry-run
npm pack
```

把生成的 `.tgz` 装进一个干净的示例项目，验证这些：

- ESM 或 CJS 入口能被解析。
- TypeScript 能找到声明文件和导出的公共类型。
- CSS 入口存在，样式生效。
- `react` 没被重复打进组件库。
- 递归渲染、事件回调和受控更新都符合约定。

tarball 的内容和使用方测试都确认通过了，再执行 `npm publish`。包名冲突只是发布失败的原因之一；权限、二次验证、Registry 和版本号也都可能让发布失败。

## 常见问题

### Props 层层透传越来越深

先看组件边界合不合理。真正跨很多层、又有好几处要用的数据，再考虑 Context 或外部 Store，别因为传了两层就马上全局化。

### 输入框偶尔出现受控切换警告

保证文本值一直是字符串、勾选值一直是布尔值。接口数据还没到时用 `value={name ?? ''}`，别先传 `undefined`。

### 懒加载组件每次交互都丢失状态

看是不是在组件函数里面声明了 `lazy`。把它挪到模块顶层，让 React 在多次渲染之间把它认成同一个组件类型。

### Portal 内点击触发了外层页面事件

Portal 的事件按 React 树冒泡。根据交互设计在 Portal 里停止传播，或者调整 Portal 在 React 树里的位置。

### 换了样式工具后仍然冲突

React 不会自动提供 CSS 隔离。查构建配置、全局选择器、第三方类名和 CSS 的引入顺序，别只看文件后缀。

### 源码项目正常，发布后类型或样式丢失

使用方读的是构建产物和 `package.json` 的出口，不是源码目录。用 `npm pack` 生成的真实 tarball 做安装测试，逐项核对 JS、声明文件和 CSS。
