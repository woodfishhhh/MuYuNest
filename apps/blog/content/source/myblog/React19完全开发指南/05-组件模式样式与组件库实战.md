# 组件模式、样式与组件库实战

组件化不是把每个 `div` 都拆成文件，而是为一块具有独立职责、可复用结构或稳定接口的 UI 建立边界。边界确定后，再通过 Props、组合、状态提升和样式隔离把组件连接起来。

```text
业务需求
    ↓
划分组件职责
    ↓
设计 Props 与状态所有权
    ↓
选择组合、受控或封装模式
    ↓
隔离样式并验证复用性
    ↓
沉淀为可发布的组件库
```

## 组件边界

适合独立成组件的内容通常至少符合一项：

- 在界面上是职责明确的一块，例如卡片、菜单、对话框。
- 在多个位置重复出现，并且结构与行为相似。
- 自己拥有一组状态、事件或生命周期逻辑。
- 需要通过稳定接口隐藏内部实现。

函数组件的输入是 Props，输出是 React 节点。Props 应描述调用方能控制什么，而不是暴露组件内部的每个实现细节：

```tsx
import type { ReactNode } from 'react';

interface CardProps {
  title: string;
  subtitle?: string;
  children: ReactNode;
  footer?: ReactNode;
}

export function Card({
  title,
  subtitle = '暂无补充信息',
  children,
  footer,
}: CardProps) {
  return (
    <article className="card">
      <header>
        <h2>{title}</h2>
        <p>{subtitle}</p>
      </header>
      <div>{children}</div>
      {footer != null && typeof footer !== 'boolean' ? (
        <footer>{footer}</footer>
      ) : null}
    </article>
  );
}
```

`ReactNode` 中的 `0` 是合法内容，因此不能用普通 truthy 判断决定是否渲染容器，否则 `0` 会落成裸文本，而不是 `<footer>` 的内容。

```tsx
<Card
  title="订单状态"
  footer={<button type="button">查看详情</button>}
>
  <p>订单已发货</p>
</Card>
```

`children` 是一个普通但特殊命名的 Prop，用于表达“把内容放进这个结构中”。相比为每种内容增加一个专用字符串属性，组合更能保留调用方的表达能力。

React 没有需要注册到框架实例上的“全局组件”。组件在哪里使用，就在哪里导入。全局消息、通知等命令式能力通常是一个服务 API 加一处统一渲染宿主，并不意味着组件本身跳出了 React 的组件树。

## 组件通信

### 父组件向下传值

父组件通过 Props 把数据与行为传给子组件。子组件不应修改收到的对象，而应把 Props 当作只读快照：

```tsx
interface CounterViewProps {
  value: number;
  onIncrement: () => void;
}

function CounterView({ value, onIncrement }: CounterViewProps) {
  return (
    <div>
      <output>{value}</output>
      <button type="button" onClick={onIncrement}>增加</button>
    </div>
  );
}
```

### 子组件通过回调上报事件

“子传父”的本质不是反向写入父组件，而是父组件把回调传下去，子组件在适当时机调用：

```tsx
import { useState } from 'react';

export function CounterPanel() {
  const [count, setCount] = useState(0);

  return (
    <CounterView
      value={count}
      onIncrement={() => setCount((current) => current + 1)}
    />
  );
}
```

回调名优先描述发生的业务事件，例如 `onSave`、`onSelect`，而不是写成含义模糊的 `callback`。

### 兄弟组件先考虑状态提升

两个兄弟组件需要共享数据时，最直接的做法是把状态提升到它们最近的共同父组件：

```tsx
function TemperatureDashboard() {
  const [celsius, setCelsius] = useState(20);

  return (
    <>
      <TemperatureInput value={celsius} onChange={setCelsius} />
      <TemperaturePreview value={celsius} />
    </>
  );
}
```

发布订阅可以连接完全独立的模块，但会隐藏数据来源、增加清理订阅的负担。普通 React 组件之间应优先使用状态提升、Context 或明确的外部 Store，而不是为简单的兄弟通信引入事件总线。

## 受控与非受控

“受控”描述的是当前值由谁持有，不只是一种表单写法。

| 模式 | 当前值的来源 | 读取方式 | 适合场景 |
|---|---|---|---|
| 受控 | React State / 父组件 Props | 直接读取状态 | 即时校验、联动、格式化、外部重置 |
| 非受控 | DOM 自己维护 | `ref` 或提交时 `FormData` | 简单表单、低频读取、接入命令式库 |

### 受控输入

文本输入通过 `value` 受控，复选框和单选框通过 `checked` 受控。对应的 `onChange` 必须同步更新后备状态：

```tsx
import { useState } from 'react';

export function ProfileForm() {
  const [name, setName] = useState('');
  const [subscribed, setSubscribed] = useState(false);

  return (
    <form>
      <label>
        昵称
        <input
          name="name"
          value={name}
          onChange={(event) => setName(event.target.value)}
        />
      </label>

      <label>
        <input
          name="subscribed"
          type="checkbox"
          checked={subscribed}
          onChange={(event) => setSubscribed(event.target.checked)}
        />
        接收通知
      </label>
    </form>
  );
}
```

一个输入在整个生命周期内不能从受控切换成非受控，也不能反向切换。最常见的错误是先传 `undefined`，请求完成后再传字符串：

```tsx
// 错误风险：profile.name 初次渲染时可能是 undefined。
<input value={profile?.name} onChange={handleChange} />

// 保持整个生命周期都是字符串。
<input value={profile?.name ?? ''} onChange={handleChange} />
```

如果值本来就是只读的，可以显式添加 `readOnly`。不要用缺少 `onChange` 的 `value` 假装默认值。

### 非受控输入

`defaultValue` 和 `defaultChecked` 只提供初始值，后续输入由 DOM 保存：

```tsx
import { type FormEvent, useRef } from 'react';

export function QuickSearch() {
  const inputRef = useRef<HTMLInputElement>(null);

  function handleSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const keyword = inputRef.current?.value.trim() ?? '';
    console.log(keyword);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input ref={inputRef} name="keyword" defaultValue="React 19" />
      <button type="submit">搜索</button>
    </form>
  );
}
```

文件输入的值由用户与浏览器决定，不能通过字符串 `value` 写入文件路径，因此 `<input type="file">` 始终按非受控方式读取：

```tsx
import { useRef } from 'react';

function UploadForm() {
  const fileRef = useRef<HTMLInputElement>(null);

  function upload() {
    const file = fileRef.current?.files?.[0];
    if (file) console.log(file.name, file.size);
  }

  return (
    <>
      <input ref={fileRef} type="file" accept="image/*" />
      <button type="button" onClick={upload}>上传</button>
    </>
  );
}
```

## `lazy` 与 `Suspense`

`lazy` 把动态导入包装成组件，构建工具据此拆分代码；`Suspense` 在代码尚未就绪时展示 `fallback`：

```tsx
import { lazy, Suspense, useState } from 'react';

// 必须在模块顶层声明，不能放进组件函数或事件回调。
const SettingsPage = lazy(() => import('./SettingsPage'));

export function Workspace() {
  const [showSettings, setShowSettings] = useState(false);

  return (
    <>
      <button type="button" onClick={() => setShowSettings(true)}>
        打开设置
      </button>

      {showSettings && (
        <Suspense fallback={<p>设置加载中...</p>}>
          <SettingsPage />
        </Suspense>
      )}
    </>
  );
}
```

`lazy` 默认读取模块的 `default` 导出。如果模块只有命名导出，可以显式转换：

```tsx
const Chart = lazy(() =>
  import('./Chart').then((module) => ({ default: module.Chart })),
);
```

不要在组件内部调用 `lazy` 创建新组件类型。每次渲染产生的新类型会让子树被重新挂载，局部状态也会重置。

Suspense 边界应放在用户体验上合理的位置：整页路由可以用页面骨架，局部图表可以只替换图表区域。边界过高会让整页闪回加载态，边界过碎则会出现大量跳动。

React 19 的 `use` 可以读取 Promise 或 Context。读取 Promise 时，Promise 必须来自稳定的缓存、路由数据层或服务端传入；不要在客户端组件每次渲染时临时创建一个新的请求 Promise：

```tsx
import { Suspense, use } from 'react';

interface Product {
  id: number;
  name: string;
}

function ProductList({ data }: { data: Promise<Product[]> }) {
  const products = use(data);
  return <ul>{products.map((item) => <li key={item.id}>{item.name}</li>)}</ul>;
}

export function ProductSection({ data }: { data: Promise<Product[]> }) {
  return (
    <Suspense fallback={<p>商品加载中...</p>}>
      <ProductList data={data} />
    </Suspense>
  );
}
```

`Suspense` 不是任意 `useEffect + fetch` 的通用加载指示器。普通请求要么自己维护状态，要么交给支持 Suspense 的框架、路由数据层或缓存库。

## HOC 高阶组件

高阶组件是“接收组件并返回增强组件”的函数。它常见于旧代码、类组件生态和需要批量包装第三方组件的场景：

```text
原组件 + 横切能力
        ↓
      HOC
        ↓
保留原 Props 的增强组件
```

一个类型安全的权限 HOC：

```tsx
import type { ComponentType } from 'react';

type Role = 'admin' | 'member';

function useCurrentRole(): Role {
  return 'member';
}

export function withPermission<P extends object>(
  Wrapped: ComponentType<P>,
  requiredRole: Role,
) {
  function WithPermission(props: P) {
    const role = useCurrentRole();

    if (role !== requiredRole) {
      return <p>没有访问权限</p>;
    }

    return <Wrapped {...props} />;
  }

  WithPermission.displayName =
    `withPermission(${Wrapped.displayName ?? Wrapped.name ?? 'Component'})`;

  return WithPermission;
}
```

使用 HOC 时要守住几条边界：

- 不修改原组件，使用容器包装并透传 Props。
- HOC 在模块顶层应用，不要在渲染过程中反复创建增强组件。
- 设置 `displayName`，否则调试树中很难识别包装层。
- 静态属性、Ref 和泛型信息不会因为包装自动完整继承，需要按契约显式处理。
- 包装层过多会产生“包装地狱”；新代码通常优先选择自定义 Hook、普通组合或 Render Props。

HOC 适合复用“如何连接组件”的逻辑，自定义 Hook 更适合复用“如何计算或订阅状态”的逻辑，两者解决的问题并不完全相同。

## Portal

`createPortal(children, domNode)` 把一段 JSX 放到指定 DOM 节点，常用于模态框、通知、浮层和 Tooltip，避免受到祖先的 `overflow`、层叠上下文或定位规则干扰：

```tsx
import type { ReactNode } from 'react';
import { createPortal } from 'react-dom';

interface ModalProps {
  title: string;
  onClose: () => void;
  children: ReactNode;
}

export function Modal({ title, onClose, children }: ModalProps) {
  return createPortal(
    <div className="modal-backdrop" onClick={onClose}>
      <section
        role="dialog"
        aria-modal="true"
        aria-label={title}
        className="modal"
        onClick={(event) => event.stopPropagation()}
      >
        <h2>{title}</h2>
        {children}
        <button type="button" onClick={onClose}>关闭</button>
      </section>
    </div>,
    document.body,
  );
}
```

Portal 只改变物理 DOM 的挂载位置。它仍然是原 React 树中的子节点，因此：

- Portal 内部仍能读取原树上方提供的 Context。
- 事件按 React 树传播，而不是按最终 DOM 树传播。
- 点击 Portal 内容可能触发原 React 父节点的事件，需要时应在正确位置停止传播。

生产级对话框还需要焦点圈定、打开后聚焦、关闭后归还焦点、Escape 关闭和背景滚动锁定。Portal 解决的是挂载位置，不会自动完成可访问性。

## 样式方案

CSS Modules、CSS-in-JS 和 Tailwind 都不是 React 内置的样式系统。它们由构建工具或第三方库提供，React 只负责输出 `className`、`style` 等 DOM 属性。

### CSS Modules：构建期局部类名

在 Vite 等工具中，把文件命名为 `*.module.css` 即可导入类名映射：

```css
/* Button.module.css */
.button {
  border: 0;
  padding: 8px 14px;
  background: #1677ff;
  color: white;
}

.danger {
  background: #d4380d;
}

:global(.legacy-focus-ring) {
  outline: 2px solid currentColor;
}
```

```tsx
import styles from './Button.module.css';

export function DeleteButton() {
  return (
    <button className={`${styles.button} ${styles.danger}`} type="button">
      删除
    </button>
  );
}
```

构建工具会把局部类名转换为带哈希或作用域信息的名称，以降低冲突概率。`:global(...)` 是显式逃生口，应只用于全局契约或第三方类名，不能把整个模块重新变成全局 CSS。

### CSS-in-JS：样式与组件逻辑共置

以 `styled-components` 为例，库会创建带样式的 React 组件，并可根据 Props 计算动态样式：

```tsx
import styled from 'styled-components';

const ActionButton = styled.button<{ $tone: 'primary' | 'danger' }>`
  border: 0;
  padding: 8px 14px;
  color: white;
  background: ${({ $tone }) => ($tone === 'danger' ? '#d4380d' : '#1677ff')};
`;

export function Toolbar() {
  return <ActionButton $tone="primary">保存</ActionButton>;
}
```

这类方案适合强动态主题和组件级样式 API，但需要考虑依赖体积、运行时插入样式、SSR 配置和调试体验。不同 CSS-in-JS 库的实现差异很大，有些依赖运行时，有些会在构建期提取，不能一概而论。

### Tailwind CSS：原子类组合

Tailwind 把常用声明映射为小粒度工具类。以 Tailwind CSS 4 和 Vite 为例：

```bash
npm install tailwindcss @tailwindcss/vite
```

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import tailwindcss from '@tailwindcss/vite';

export default defineConfig({
  plugins: [react(), tailwindcss()],
});
```

```css
/* src/index.css */
@import "tailwindcss";
```

```tsx
export function HeroAction() {
  return (
    <button
      type="button"
      className="rounded bg-blue-600 px-4 py-2 font-semibold text-white hover:bg-blue-700"
    >
      开始使用
    </button>
  );
}
```

工具类能减少命名成本，并让响应式和状态变体靠近组件；代价是 JSX 类名较长、设计约束需要团队治理。重复组合应提取成组件，而不是用字符串常量重新发明一层难追踪的样式系统。

### 如何选择

| 方案 | 隔离方式 | 动态能力 | 主要代价 |
|---|---|---|---|
| CSS Modules | 构建期类名映射 | 通过条件类名 | 样式与组件分文件 |
| CSS-in-JS | 库生成类名与样式 | Props、主题能力强 | 依赖与潜在运行时成本 |
| Tailwind CSS | 原子工具类约定 | 条件拼接与变体 | JSX 类名密集 |

选择标准应是项目现状、设计系统和运行环境，而不是“哪一种最像 React”。React 本身不替项目做这个决定。

## 组件库构建

Tree 组件同时涉及类型设计、递归渲染、入口导出、库模式构建、声明文件和 npm 包验证。真正的组件库不只是“能显示”，还要给消费方提供稳定的运行时代码、类型和样式入口。

### 目录与公共入口

```text
packages/
  components/
    tree/
      Tree.tsx
      Tree.css
      types.ts
      index.ts
    index.ts
  index.ts
example/
  App.tsx
vite.config.ts
package.json
```

组件自己的 `index.ts` 管理局部出口，总入口汇总公共 API：

```ts
// packages/components/tree/index.ts
export { Tree } from './Tree';
export type { TreeNode, TreeProps } from './types';

// packages/index.ts
export * from './components/tree';
```

公共类型也必须导出。否则消费方虽然能渲染组件，却无法复用组件所要求的数据结构。

### 一个受控的递归 Tree

```ts
// packages/components/tree/types.ts
export interface TreeNode {
  id: string;
  label: string;
  children?: readonly TreeNode[];
}

export interface TreeProps {
  data: readonly TreeNode[];
  checkedKeys: readonly string[];
  onCheckedChange: (id: string, checked: boolean) => void;
}
```

```tsx
// packages/components/tree/Tree.tsx
import { useMemo } from 'react';
import type { TreeNode, TreeProps } from './types';
import './Tree.css';

interface BranchProps {
  nodes: readonly TreeNode[];
  checked: ReadonlySet<string>;
  onCheckedChange: TreeProps['onCheckedChange'];
}

function Branch({ nodes, checked, onCheckedChange }: BranchProps) {
  return (
    <ul className="ui-tree__list">
      {nodes.map((node) => (
        <li key={node.id} className="ui-tree__node">
          <label>
            <input
              type="checkbox"
              checked={checked.has(node.id)}
              onChange={(event) => onCheckedChange(node.id, event.target.checked)}
            />
            {node.label}
          </label>

          {node.children?.length ? (
            <Branch
              nodes={node.children}
              checked={checked}
              onCheckedChange={onCheckedChange}
            />
          ) : null}
        </li>
      ))}
    </ul>
  );
}

export function Tree({ data, checkedKeys, onCheckedChange }: TreeProps) {
  const checked = useMemo(() => new Set(checkedKeys), [checkedKeys]);
  return <Branch nodes={data} checked={checked} onCheckedChange={onCheckedChange} />;
}
```

递归成立需要两个条件：存在子节点时调用自身，没有子节点时停止。组件选择状态由调用方持有，因此它遵守受控组件契约，不会在内部复制一份容易失同步的数据。

父子级联勾选属于业务策略：有的树要求选父即全选子，有的树允许半选，有的树只允许叶子节点。组件库应把策略写进契约或提供可选能力，而不是暗中修改传入的 `data`。

### Vite 库模式与类型声明

```ts
// vite.config.ts
import { resolve } from 'node:path';
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import dts from 'vite-plugin-dts';

export default defineConfig({
  plugins: [
    react(),
    dts({
      include: ['packages'],
      insertTypesEntry: true,
    }),
  ],
  build: {
    lib: {
      entry: resolve(import.meta.dirname, 'packages/index.ts'),
      formats: ['es', 'cjs'],
      fileName: (format) => format === 'es' ? 'index.js' : 'index.cjs',
      cssFileName: 'style',
    },
    rolldownOptions: {
      external: ['react', 'react-dom', 'react/jsx-runtime'],
    },
  },
});
```

`react` 和 `react-dom` 应由消费项目提供。把它们外置并声明为 `peerDependencies`，可以避免包体重复和页面中出现两份 React。若要输出 UMD，还要配置全局变量名；现代包管理器场景通常优先提供 ESM，并按兼容目标决定是否保留 CJS 或 UMD。

### `package.json` 出口契约

```json
{
  "name": "@acme/ui",
  "version": "0.1.0",
  "type": "module",
  "files": ["dist"],
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./style.css": "./dist/style.css"
  },
  "peerDependencies": {
    "react": ">=19",
    "react-dom": ">=19"
  },
  "sideEffects": ["**/*.css"]
}
```

`exports` 是消费方真正看到的公共边界。未列出的内部文件不应被业务代码深层导入。样式如果由构建产物单独输出，也要给出稳定入口，并避免被错误的 Tree Shaking 当成无副作用代码移除。

### 发布前先验证包，而不是只验证源码

```bash
npm run build
npm pack --dry-run
npm pack
```

把生成的 `.tgz` 安装到一个干净示例项目，验证以下内容：

- ESM 或 CJS 入口能被解析。
- TypeScript 能找到声明文件和导出的公共类型。
- CSS 入口存在且样式生效。
- `react` 没有被重复打进组件库。
- 递归渲染、事件回调和受控更新符合契约。

确认 tarball 内容与消费测试都通过后，再执行 `npm publish`。包名冲突只是发布失败的一种原因；权限、二次验证、Registry 和版本号也都可能导致发布失败。

## 常见问题

### Props 层层透传越来越深

先检查组件边界是否合理。真正跨越很多层且多处消费的数据，再考虑 Context 或外部 Store，不要因为两层传递就立刻全局化。

### 输入框偶尔出现受控切换警告

保证文本值始终是字符串、勾选值始终是布尔值。接口数据未到时使用 `value={name ?? ''}`，不要先传 `undefined`。

### 懒加载组件每次交互都丢失状态

检查是否在组件函数内部声明了 `lazy`。将其移到模块顶层，让 React 在多次渲染间识别为同一个组件类型。

### Portal 内点击触发了外层页面事件

Portal 的事件按 React 树冒泡。根据交互设计在 Portal 内停止传播，或调整 Portal 在 React 树中的位置。

### 换了样式工具后仍然冲突

CSS 方案不是 React 自动提供的隔离。检查构建配置、全局选择器、第三方类名和 CSS 引入顺序，不要只看文件后缀。

### 源码项目正常，发布后类型或样式丢失

消费方读取的是构建产物与 `package.json` 出口，不是源码目录。用 `npm pack` 生成的真实 tarball 做安装测试，逐项核对 JS、声明文件和 CSS。
