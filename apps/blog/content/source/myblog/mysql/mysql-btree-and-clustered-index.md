几百万行数据里定位一个工号，没有索引就得从头到尾全表扫描，延迟随数据量线性恶化。索引是存储引擎维护的有序辅助结构，用额外的磁盘空间和写入维护成本，换取查询时迅速缩小扫描范围。理解 InnoDB 为什么选 B+ 树、叶子节点如何区分聚簇索引与二级索引，是写出高性能 SQL 的前提。

## 为什么磁盘索引选用 B+ 树而不是二叉树或 B 树

普通二叉搜索树（BST）在主键自增插入时会直接退化成单链表；红黑树或 AVL 树虽然能维持平衡，但每个节点最多只有两个分支，百万级数据需要约 20 层树高——在磁盘 I/O 场景下，每向下找一层就可能触发一次随机读页，20 次磁盘寻道根本无法接受。

要压低树高，唯一办法是**让单个树节点填满一个 16 KiB 磁盘页，大幅提高扇出（每个节点的分支数）**。B 树实现了多路平衡，先看一棵五阶 B 树（约定每个节点最多 4 个键、5 个子节点）的分裂过程来理解多路平衡树如何控制高度：

1. 依次插入 `234, 345, 23, 899`，根节点内按键有序排列为 `[23, 234, 345, 899]`。
2. 继续插入 `1200`，节点暂时溢出为 5 个键，必须将中间键 `345` 提升为新根，拆出左右子页：

```text
          [345]
         /     \
 [23, 234]     [899, 1200]
```

3. 右子页继续插入 `1234, 1500, 1000` 后再次溢出，中间键 `1200` 向上提升进入根节点，根变成 `[345, 1200]`（2 个分隔键切分出 3 个子节点指针）。
4. 随后左子页插入 `123, 245, 12` 提升 `123`，右子页继续插入并两次分裂提升 `1567` 与 `1980`；此时根本身集齐 `[123, 345, 1200, 1567, 1980]` 五个键也发生分裂，`1200` 升为新根，树高才从 2 层长到 3 层：

```text
[1200]
├─ 左侧内部节点 [123, 345]
│  ├─ [12, 23]
│  ├─ [234, 245]
│  └─ [899, 1000]
└─ 右侧内部节点 [1567, 1980]
   ├─ [1234, 1500]
   ├─ [1800, 1888]
   └─ [2000, 2456]
```

**B+ 树在 B 树的基础上更进一步：非叶子节点彻底剥离整行数据，只存路由键与子页指针；所有完整索引记录全部下沉到叶子节点，并用双向链表串联。**

```text
                 非叶子页：仅存分隔键 + 子页指针（扇出极高）
                 /                  |                 \
叶子页：    [10, 20]  <------>  [30, 40]  <------>  [50, 60]
```

这种结构带来两项决定性收益：

- **树矮且 I/O 稳定**：同样 16 KiB 的非叶子页，因为不背负整行业务数据，一页能塞进上千个子页指针。以非叶子页扇出 $F=1000$、叶子页存 $R=16$ 行估算，容量按 $F^{h-1} \times R$ 增长——2 层能装约 1.6 万行，3 层即可容纳约 **1600 万行**（实际受行宽与主键长度影响），而根页和上层非叶子页常驻内存，等值查询通常只需极少次甚至 1 次叶子页读取。
- **范围扫描极快**：执行 `WHERE id BETWEEN 25 AND 55` 时，只需从根下降一次定位到第一个不小于 25 的键（`30`），之后直接顺着叶子页双向指针顺序向后扫描到 `50` 即停，遇到 `60` 越界结束，无需反复回溯上层节点。

至于 Hash 索引，虽然单次等值定位接近 $O(1)$，但哈希函数打乱了键值顺序，无法支持 `>`、`BETWEEN`、`ORDER BY` 和前缀模糊匹配。InnoDB 常规索引全部采用 B+ 树，仅在内部针对热点等值页自动维护自适应哈希索引（AHI）加速内存定位。

## 聚簇索引与二级索引的组织方式

InnoDB 表的行数据直接存放在聚簇索引（Clustered Index）的叶子节点中，因此**每张 InnoDB 表有且只有一棵聚簇索引**。它的选择优先级非常明确：

1. 表显式定义了主键（`PRIMARY KEY`），则主键索引就是聚簇索引。
2. 表没有主键，则挑选第一个所有列均声明为 `NOT NULL` 的 `UNIQUE` 索引。
3. 两者都没有，InnoDB 会在底层自动生成一列 6 字节的隐藏 `DB_ROW_ID` 作为聚簇索引。

与聚簇索引相对的是二级索引（辅助索引）。在 `emp` 表上执行 `CREATE INDEX idx_emp_name ON emp(name);` 后，这棵新索引的叶子节点只存两样东西：**索引列值 `name`** 与 **对应的主键值 `id`**。

**二级索引叶子存主键值而不存物理磁盘偏移，是因为页分裂和记录移动时行地址会频繁变动，存主键能让二级索引免于跟着大面积重算。**

## 二级索引为什么会回表，以及怎么用覆盖索引避开

聚簇索引与二级索引的存储分工，直接决定了一条查询走索引后的真实读取路径。对 `emp(name)` 建索引后，下面三条查询的执行代价截然不同：

| 查询 SQL | 命中索引路径 | 是否回表 | 原因 |
| :--- | :--- | :--- | :--- |
| `SELECT id, name, salary FROM emp WHERE id = 1` | 聚簇索引 | 否 | 主键叶子节点直接存有整行全部列 |
| `SELECT id, name FROM emp WHERE name = '柳岩'` | `idx_emp_name` | 否（覆盖索引） | `name` 和主键 `id` 都在二级索引叶子里 |
| `SELECT id, name, salary FROM emp WHERE name = '柳岩'` | `idx_emp_name` → 聚簇索引 | **是** | 拿到 `id = 1` 后必须再查一遍主键树才能取出 `salary` |

从二级索引拿到主键值再去聚簇索引定位整行数据的二次查找，称为**回表**。而“覆盖索引”指某条查询所需的全部列刚好都能从同一棵二级索引中取齐，免除了回表开销——它是索引与查询之间的匹配性质，不是一种独立创建的索引类型。

**线上禁止随手写 `SELECT *`，最直接的工程原因就是它会把原本能走覆盖索引的查询强行打回表。**

如果一条高频列表接口只需要 `name` 和 `salary`，把单列索引 `(name)` 扩成联合索引 `(name, salary)` 就能直接消除回表；实操时通过 `EXPLAIN` 观察 `Extra` 列，出现 `Using index` 即确认走上了覆盖索引。当匹配行只有寥寥几条且热页都在 Buffer Pool 中时，回表代价极低；一旦查询一次扫出几万行又伴随大量随机磁盘读，回表 I/O 会迅速打满磁盘队列，优化器甚至会直接放弃索引退回全表扫描。

## 索引分类维度与主键设计代价

日常讨论中常把索引按不同视角叠在一起称呼，例如一个 `(dept_id, age)` 索引同时是“普通索引 + 联合索引 + 二级索引”，各维度互不冲突：

| 分类视角 | 常见类别 | 说明 |
| :--- | :--- | :--- |
| 约束与用途 | 主键索引、唯一索引、普通索引、全文索引 | 主键与 `UNIQUE` 建表时自动生成对应索引，勿重复手动创建 |
| 包含列数 | 单列索引、联合索引 | 联合索引按声明顺序排序，`SHOW INDEX` 中 `Seq_in_index` 依次递增 |
| 存储组织 | 聚簇索引、二级索引 | 聚簇索引叶存整行，二级索引叶存索引列 + 主键值 |

**主键字段越长，整张表的所有二级索引叶子都会跟着等比例膨胀，从而拉低单页扇出、拔高树高并放大写入维护成本。**

因此业务主键应尽量保持紧凑且单调递增（如 `BIGINT` 自增或有序 ID），避免用超长随机字符串（如 36 字节随机 UUID）做聚簇主键——随机主键既会让每一棵二级索引都背负冗长的键值，又会在插入时频繁触发中间叶子页的随机分裂与碎片化。
