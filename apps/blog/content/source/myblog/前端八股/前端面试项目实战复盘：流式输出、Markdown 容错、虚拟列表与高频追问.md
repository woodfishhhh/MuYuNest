一条 SSE 消息格式不对，不该让后面的内容全没了；一段还没传完的 Markdown，也不能因为代码块没闭合就让页面报错。列表卡顿是另一类问题：先确认瓶颈是不是 DOM 数量，再决定要不要上虚拟列表。

这三个场景分别对应协议容错、增量渲染和性能验证。处理方式各不一样，但都是先保住能用，再缩小问题范围。

## 一、流式输出先保证链路不断

SSE 是长连接。单条脏数据要是直接抛异常，后面的消息可能都进不了页面。接收层要按事件类型处理数据，并给解析失败留一个降级的分支。

一个实用的处理顺序：

1. 接收并识别事件类型。
2. 按约定的格式解析数据。
3. 解析失败时保留原始文本，别中断整条流。
4. 记下异常的样本，推动服务端把协议收敛。

容错不是忽略错误。前端继续展示内容，同时把错误事件、原始数据和连接状态留在日志里，才能判断问题出在单条消息还是整个连接。

## 二、Markdown 容错的底线是内容不丢

流式的 Markdown 一定会经过不完整的状态：代码块暂时没闭合，表格只收到了前几列，列表也可能还在往下写。中间态解析失败，不能就此判断最终的内容无效。

### 1. 中间态与最终态分开处理

接收过程中先把文本累加起来，允许结构暂时不完整。流结束后再完整解析一次；最后还是失败的话，回退成纯文本。

回退成纯文本会丢掉标题、列表、代码块和表格的样式，但实际内容都在。比起整条消息一片空白，这个结果更能用，也更好排查。

### 2. 渲染与安全分层

Markdown 解析成功了，不代表内容可以直接进 DOM。消息里可能有 HTML 或危险的标签，所以渲染链路还要一层独立的安全处理：

"流式接收 -> 文本组装 -> Markdown 解析 -> sanitize -> DOM 更新"。

解析失败管回退，sanitize 管隔离风险。两者解决的问题不一样，别合成一个含糊的 try/catch。

## 三、虚拟列表要先证明 DOM 是瓶颈

列表项很多时，浏览器要负责 DOM 创建、样式计算、布局、绘制、事件绑定和状态维护。虚拟列表只渲染视口附近的节点，其他区域用占位高度模拟，把渲染的规模从全部数据降到可视区那么大。

但卡顿不一定是节点数量造成的。图片解码、复杂计算、频繁的状态更新和网络请求，都可能占着主线程。

### 1. 先记录现象

- 在 DevTools Performance 里看长任务和主线程的占用。
- 看 FPS 是不是低于 60。
- 检查 Memory 和 Detached DOM 是不是一直在涨。
- 对照 Lighthouse、Web Vitals 和真实用户的卡顿记录。

### 2. 再做对照实验

把列表从 1000 条降到 20 条，把 item 临时简化成纯文本，再比较开虚拟列表前后的首屏时间、内存、帧率和长任务。

这些指标明显变好了，才能说明 DOM 规模确实是主要的瓶颈。不然上虚拟列表只会多一层复杂度。

### 3. 计算虚拟化成本

虚拟列表要处理动态高度、滚动定位、锚点恢复和 overscan。overscan 太大会削弱收益，太小又可能在快速滚动时出现空白。数据量不大、或者单项渲染很轻的话，普通列表一般更合适。

## 四、登录鉴权的边界

常见的登录流程有四步：登录成功拿到 token，前端在后续请求里带上 token，服务端校验签名、过期时间和权限，token 失效时统一刷新或跳回登录。

选 JWT 之前，还要想清楚存在哪、怎么过期，以及 XSS、CSRF 的风险。鉴权靠不靠谱，最终取决于服务端的校验和权限模型，不能只看前端有没有存 token。

## 五、技术选型要写清约束

项目的 `wait.md` 里记了 WebSocket、心跳、localStorage、Tailwind，以及 React 和 Vue 这些选型问题。判断方案时，先说业务约束，再列代价：

- WebSocket 适合双向的实时通信，心跳用来发现断连和连接失效。
- 30 秒的心跳只是现在的配置，要结合网关超时、网络环境和服务端负载来调。
- localStorage 能持久化轻量的状态，但有同步读写、容量和安全上的限制。
- Tailwind 能减少切换样式的成本，但也要统一类名组合和组件规范。

方案成不成立，看的不是工具名，而是它满不满足通信方向、时延、状态持久化和维护成本这些约束。

## 六、把项目问题落回运行机制

流式 Markdown 会涉及 SSE、增量渲染和内容安全；虚拟列表会涉及 DOM 数量、回流重绘和状态更新；页面性能则要回到 Web Vitals、资源加载链路和缓存策略。

一些看着不相干的机制也会直接影响实现，比如 `nextTick` 决定什么时候读更新后的 DOM，`for...in` 和 `for...of` 遍历的对象不一样，节流会改变高频事件的执行频率。项目问题和语言机制就是在这些地方连起来的，不用再额外套一层答题模板。

## 七、记录方案时保留验证结果

一项工程改动至少要留下六类信息：背景、现象、原因、方案、权衡和验证。没有验证数据，就判断不了问题是不是真解决了；不写剩下的风险，后来维护的人也不知道方案的边界在哪。

流式输出要验证异常消息不会中断后面的内容，Markdown 回退要验证文本不丢、危险内容被隔离，虚拟列表则要比较开启前后的主线程、内存和帧率。这些结果比一句笼统的"体验更好"有用得多。
