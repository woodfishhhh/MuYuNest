服务器无法启动时先查错误日志；需要追踪数据变化时看 binlog；要找慢语句看慢查询日志。日志的用途不同，能在某个文件中找到一条 SQL，不代表它已经成功提交或可以拿来恢复全部数据。

## 错误日志用来定位服务器异常

```sql
SHOW VARIABLES LIKE 'log_error';
```

查询实际日志位置，再用操作系统工具查看该路径。Linux 安装可能把信息写入文件或服务日志，不能固定假设所有机器都在 `/var/log/mysqld.log`。

课程通过损坏 server_uuid 配置演示启动失败，错误日志指出 auto.cnf 中 UUID 无效。要学习的是“从错误时间、错误级别和具体对象定位配置”，无需在现有数据库中故意破坏 auto.cnf。遇到同类故障，应先保留原配置和日志，再按实际错误修复。

## binlog 记录可用于复制和恢复的数据变化事件

```sql
SHOW VARIABLES LIKE 'log_bin%';
SHOW VARIABLES LIKE 'binlog_format';
SHOW BINARY LOGS;
SHOW MASTER STATUS; -- 课程 MySQL 8.0.26 的命令
```

binlog 属于服务器层，记录相应的结构与数据变化事件，普通只读 SELECT 不作为数据变更记录进去。它与 InnoDB 的 redo 不同：redo 主要服务存储引擎的崩溃恢复，binlog 服务复制和基于日志的数据恢复。

| 格式 | 记录方式 |
| --- | --- |
| STATEMENT | 记录相应 SQL 语句，需要在目标端重新求值执行 |
| ROW | 记录受影响行的变化事件，具体行镜像由配置决定 |
| MIXED | 根据语句特性在相应方式之间选择 |

一条 UPDATE 改三行，在 STATEMENT 下可能对应一条语句，在 ROW 下对应行事件。ROW 不意味着所有事件都是行记录，DDL 仍有相应语句事件；也不能假设任何配置都保存每行全部前后字段。

恢复通常需要先还原一致性基线，再回放基线之后的完整日志链。只有最近一个 binlog 文件，未必能恢复数据库原有内容。复制也同样需要知道从哪个事务或哪个文件位置开始。

以 `UPDATE account SET balance=balance-100 WHERE id=1` 为例，语句格式表达的是这次操作，接收方需要按自己的执行环境重新应用它；行格式表达实际受影响记录的变化，复制围绕这些变化推进。两种格式记录的层次不同，这也是某些涉及非确定性表达式或环境差异的语句，需要特别考虑复制方式的原因。

binlog 与 redo 的职责也不能按“都是日志文件”混为一谈。redo 关注 InnoDB 页怎样恢复到需要的状态；binlog 面向服务器层的数据变化及复制。把 binlog 文件拷到另一个实例，不等于已经完成了 InnoDB 崩溃恢复；反过来，本机能依靠 redo 恢复，也不表示保留了足够的 binlog 来建立新从库或恢复到任意历史时间点。

## 日志清理必须保留恢复和复制需要的链

binlog 的编号不断增加，过期策略由 `binlog_expire_logs_seconds` 等实际配置决定。课程使用 30 天默认值演示，但保留时间应以当前实例查询结果和恢复需求为准。

MySQL 8.0 可用 `PURGE BINARY LOGS TO '文件名'` 清理指定文件之前的日志，或按 BEFORE 时间清理。执行前要确认备份基线、仍在追赶的从库和所需恢复窗口；这些信息缺失时，无法仅按文件年龄判断能否删除。

`RESET MASTER` 是课程旧版中的重置操作，会破坏已有日志链，并涉及 GTID 状态，不是普通日常清理命令。新版本语法还有变化。不要直接在文件系统中删除 binlog 或修改索引清单来代替受控清理。

按“完整备份加后续日志”恢复时，可以把时间轴分成三段：备份已经覆盖的历史状态、备份起点到目标时间之间的变化、目标时间之后不想恢复的变化。先恢复基线，再顺序应用中间那段完整日志链，才能得到目标状态。缺少中间任意一段，后面的事件即使还在，也可能无法在正确前提上继续应用。

例如误删发生在一个已经提交的事务中，目标是回到误删前，那么回放边界必须放在相关事务之前，并保证此前事务完整。不能只在文本中搜索一条 DELETE 后删掉几个看起来相关的行，就认定剩余事件仍构成有效恢复流。二进制日志中的事务边界和事件编码需要由合适工具处理。

## general log 记录接收到的操作

```sql
SHOW VARIABLES LIKE 'general_log%';
SHOW VARIABLES LIKE 'log_output';
```

general log 可以记录连接及收到的查询等操作，适合短时调查客户端到底发了什么。它通常默认关闭，因为日志量和写入开销都可能很大，SQL 中也可能带有业务数据。

“日志中出现了语句”只说明它进入相应记录流程，不自动证明执行成功或事务提交。调查结束后，应恢复原配置并按权限管理日志文件。

general log 更接近“服务器收到了哪些请求”的记录，慢日志更接近“哪些执行满足了特定诊断条件”，binlog 则服务相应的数据变化传播与恢复。一个客户端发来语句后执行失败，general log 中仍可能有它；一个成功的快速 SELECT 不会因为成功就写进数据变化 binlog；一个事务后来回滚，也不能仅凭曾经看见 UPDATE 请求就认定它改变了最终业务状态。

把日志类型选错，会让排查从一开始就问错问题。怀疑程序没有发送 SQL，先看请求与执行入口；怀疑慢在扫描和排序，结合慢日志及计划；需要恢复数据，先检查备份与可回放日志链。不同日志互相补充，不能由其中一份替代全部证据。

## 慢日志的阈值不只是一条时间线

```sql
SHOW VARIABLES WHERE Variable_name IN
  ('slow_query_log','long_query_time','min_examined_row_limit',
   'log_queries_not_using_indexes','log_slow_admin_statements');
```

long_query_time 设置耗时阈值，可以使用小数，不是最小只能为 1 秒。min_examined_row_limit 表示需要检查的最少行数门槛，不是“少于该值才记录”。因此解释一条语句为什么没进入日志时，需要同时看时间、检查行数和相关记录选项。

`log_queries_not_using_indexes` 可以额外记录符合条件的未使用索引查询，并不要求它们都超过 long_query_time。反过来，没有开启这个选项，也不意味着所有无索引慢查询都不会记录：正常慢查询条件仍可能捕获它们。

慢日志中的耗时、返回行数和检查行数用于定位候选问题，再结合 EXPLAIN、锁等待和业务延迟分析。它不是只凭日志行数就能给出优化结论的评分表。

记录条件可核对 [MySQL 慢查询日志说明](https://dev.mysql.com/doc/refman/8.0/en/slow-query-log.html)。
