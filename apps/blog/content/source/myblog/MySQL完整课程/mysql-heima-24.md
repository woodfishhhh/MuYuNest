事务提交后，数据页不一定已经全部写回最终文件。InnoDB 通过缓冲池处理页面，通过日志保证恢复，再由后台任务逐步刷新脏页。这把“尽快完成一次提交”和“把所有页面写回磁盘”分开了。

## 缓冲池保存页面，日志缓冲保存 redo

查询需要的页已在 Buffer Pool 中时，可直接访问；不在时才从存储读取并缓存。更新先修改缓冲池中的页，使它与磁盘页暂时不同，这样的页称为脏页。干净页与磁盘内容一致，空闲页则尚可分配。

日志缓冲 Log Buffer 主要存放待写出的 redo 记录。它不是把 redo、undo 和所有业务日志混装的统一仓库。相关大小由不同参数控制：

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'innodb_log_buffer_size';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

缓冲池应给数据库工作集足够空间，同时给操作系统、连接和其他结构留空间。课程中专用服务器的内存比例是环境经验，不适合作为所有机器直接套用的设置。

Change Buffer 用于延迟合并某些不在缓冲池中的非唯一二级索引页变更，减少立即随机读页的成本。唯一性检查通常需要及时访问对应索引页，不能按同一方式处理。后续读取目标页或后台合并时，会把这些变更合入页。它并不是所有 DML 都先经过的通用缓存。

自适应哈希索引针对某些热点页访问自动建立辅助结构，减少反复沿 B+ 树查找的成本。是否启用、是否受益取决于版本、配置和负载，不能把 InnoDB 常规索引因此称为 HASH 索引。

缓冲池需要决定哪些页继续保留，哪些页可以让出空间。若只按“刚访问过就长期放在最热位置”的简单思路，一次扫描大表可能读入大量只用一次的页，把平时频繁访问的小范围热点挤出去。InnoDB 的页面管理会区分较新、较旧的访问区域，并结合相关策略判断页面是否应晋升，从而减轻这种扫描污染。不要把“读入过一次”直接理解成“以后都会一直缓存”。

干净页和脏页被替换时的要求也不同。干净页丢出缓冲池后，需要时可以从磁盘重新读；脏页的最新变化还没写回最终页面，不能简单当作无用缓存直接丢弃。后台刷新把脏页写回存储，既服务恢复和检查点，也为缓冲池腾出可复用空间。

Change Buffer 解决的是另一段成本。修改一个不在缓冲池中的合适二级索引页时，如果必须先随机读取它，再做一个很小的变更，立即读页的成本可能很高。先记下可延迟的变更，等页面被读入或后台合并时一起处理，可以减少这类随机读取。它不替代行数据更新、事务日志和唯一性检查，因此不能把所有写操作都画成先进入同一个 change buffer。

## 表空间把页面组织到文件中

数据结构按表空间、段、区、页和记录组织。表空间是文件层面的存储容器，段服务于索引等结构，区管理一批连续页面。默认 16 KiB 页下，常见区大小为 1 MiB，即 64 页；分配策略还有小段等情况，不宜认为任何分配都固定申请同样数量的区。

| 区域 | 主要用途 |
| --- | --- |
| 系统表空间 | 系统级存储，包括相应版本中的 change buffer 等内容 |
| 独立表空间 | 通常以表的 `.ibd` 文件保存数据与索引页 |
| 通用表空间 | 用户创建，可供多张表共享 |
| undo 表空间 | 保存撤销记录所需页面 |
| 临时表空间 | 服务于相应临时对象，生命周期与持久表不同 |

通用表空间的语法示例为：

```sql
CREATE TABLESPACE notes_ts ADD DATAFILE 'notes_ts.ibd' ENGINE=InnoDB;
CREATE TABLE tablespace_demo(id INT PRIMARY KEY,name VARCHAR(20))
  TABLESPACE notes_ts ENGINE=InnoDB;
```

这需要相应管理权限，并会创建持久文件，普通 SQL 学习并不要求执行。表空间文件、undo 和 redo 都有自己的管理规则，不能直接删除看起来“旧了”的日志文件释放空间。

## redo 为什么能够保护尚未刷新的页面

一条更新执行时，会产生描述页面修改的 redo，先进入相应缓冲，再按策略写入和刷新到持久介质。若事务已经确认提交，而数据页还没来得及全部落盘就发生崩溃，恢复时可以依据日志重做必要的修改。

这个机制称为 WAL，Write-Ahead Logging：页面持久化之前，必须保证恢复所需的日志已经满足写前要求。redo 不只在 COMMIT 那一刻才产生，也不是把原始 UPDATE SQL 原样抄一份。

相较于每次提交都强制随机刷新所有修改的数据页，日志顺序写入通常更高效。随后后台刷新脏页、推进检查点，已经不再需要的 redo 区域才可复用。事务提交成功并不意味着其 redo 立即没用了，尚未持久化的数据页仍可能依赖它。

课程的 8.0.26 使用旧式 `ib_logfile0` 等布局；MySQL 8.0.30 起 redo 容量与文件管理发生变化，常见 `#innodb_redo` 目录。文件名与数量必须按实际版本核对，不能把旧目录截图当作所有版本的固定结构。

可以把一次修改拆成三个时点：A 是内存数据页已被修改且产生了恢复所需日志，B 是事务按提交策略满足确认条件，C 是相关数据页后来被刷新到其最终位置。B 不必等到 C，正是日志能缩短提交关键路径的原因。

在 A 与 B 之间崩溃，事务尚未成功提交，恢复不能把它当作已完成业务留下来；在 B 与 C 之间崩溃，磁盘数据页可能仍旧，但已经按相应持久性条件确认的修改需要由恢复机制重建；C 之后，页面本身已经包含这些变化。实际恢复可能先重做必要的页修改，再结合事务状态撤销未完成的修改，所以 redo 不能只理解成“仅记录已经提交的事务”。

检查点推进的目的，是让恢复需要追溯的日志范围与脏页状态相协调。假设一段 redo 对应的页变化还没有安全写回，却提前复用覆盖了这段日志，故障时就可能同时缺失新数据页和恢复信息。因此 redo 的循环复用必须受恢复进度约束，不是一个无条件覆盖最旧记录的普通环形文本文件。

## undo 保存回滚与历史重建所需的信息

把年龄从 30 改成 3 之前，数据库要保存足以恢复旧值的信息。ROLLBACK 根据这些撤销记录还原操作，MVCC 也借助它们重建读者需要的历史版本。

可以用“反向操作”帮助理解，但 undo 并不是一份可直接执行的反向 SQL 文本清单，也未必为每个版本保存完整行副本。修改记录中的回滚指针连接到相应 undo，历史行可沿这些信息重建。

更新事务提交后，旧版本可能仍被其他活跃读视图需要，因此不能立刻清除。Purge 等后台工作只有确认不再需要时才回收相关历史。长事务会延长旧版本保留，单看已经提交多少写事务无法推断 undo 已可清空。

以年龄 30 改成 3 为例，redo 支持把需要恢复的修改重做到页面上，undo 提供撤销或重建旧版本所需的信息。两者服务的方向不同，并不意味着把同一条 SQL 分别正写、倒写两遍。原 SQL 中的条件、表达式与实际页面修改，也不总是一一对应。

提交后 undo 何时可以清理，要看是否还存在需要旧版本的读者。一个 RR 事务早已建立读视图，它可能仍要读到年龄 30；写事务虽然已经提交，系统仍不能仅凭这一点删掉旧版本重建所需的信息。长事务让历史保留变长，原因就在这个尚未结束的读取需求。

## doublewrite 与 redo 解决不同故障

页面写入途中故障，可能得到一张只写了一部分的损坏页。Doublewrite 先保存可用于恢复的页副本，再写最终位置，用于应对相应的部分页写问题。redo 则描述修改，两者共同服务恢复，但并不互相替代。

后台有页面清理、读写 I/O、日志写入、purge 等任务。其线程划分和数量随版本与配置变化，课程里的“固定十个线程”不能作为通用结论。可通过 `SHOW ENGINE INNODB STATUS` 查看当前引擎状态，再结合配置解释。

提交持久性还受 `innodb_flush_log_at_trx_commit` 控制：1 通常表示每次提交写日志并刷新；2 通常每次提交写到操作系统缓存、按周期刷新；0 通常按周期写入与刷新。周期不是严格实时保证，后两者在故障时存在丢失近期已确认数据的可能。持久性还依赖存储系统是否兑现刷新要求，不能把文件存在当作恢复验收。

写入操作系统缓存与刷新到持久介质也需要分开。数据库进程把日志交给操作系统后，进程本身崩溃与整台机器掉电的影响可能不同；后者还可能丢失操作系统尚未刷出的数据。因此解释提交参数时必须说明故障边界，不能仅说“每秒写一次，最多丢一秒”就当作严格保证。

Doublewrite 则面对完整页面自身写坏的问题。设一个页面只完成了一部分写入，新旧内容混在一起，这时日志恢复不能假设已经有一张结构完好的基础页。先从受保护的页副本恢复可用页面，再利用日志推进到所需状态，才能把这两类恢复职责连起来理解。
