事务提交了，数据页不一定已经全部写回最终文件。InnoDB 用缓冲池处理页面，用日志保证能恢复，再由后台任务慢慢刷脏页。这样"尽快完成一次提交"和"把所有页面写回磁盘"就被拆开了。

## 缓冲池保存页面，日志缓冲保存 redo

查询要的页已经在 Buffer Pool 里就直接用；不在才从存储读进来缓存。更新先改缓冲池里的页，这时它和磁盘上的页不一样，叫脏页。干净页和磁盘一致，空闲页是还没分配的。

日志缓冲 Log Buffer 主要放待写出的 redo 记录，不是把 redo、undo 和各种业务日志混在一起的总仓库。大小由不同参数控制：

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'innodb_log_buffer_size';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

缓冲池要给数据库的工作集留够空间，也要给操作系统、连接和其他结构留空间。课程里专用服务器的内存比例是经验值，别直接套到所有机器上。

Change Buffer 用来延迟合并某些不在缓冲池里的非唯一二级索引页的变更，省掉立刻随机读页的开销。唯一性检查一般要马上访问对应的索引页，不能这样处理。之后读到目标页或者后台合并时，再把变更合进去。它不是所有 DML 都要先经过的通用缓存。

自适应哈希索引会针对某些热点页访问自动建辅助结构，少走几遍 B+ 树查找。要不要开、有没有收益，看版本、配置和负载。别因此把 InnoDB 的普通索引叫成 HASH 索引。

缓冲池还要决定哪些页留下、哪些页让出空间。如果简单地"刚访问过就放到最热的位置"，一次全表扫描读进来的大量一次性页面，会把平时常用的热点挤出去。InnoDB 会区分较新和较旧的访问区域，再结合策略判断页面要不要晋升，减轻这种扫描污染。所以"读进来过一次"不等于"以后一直缓存着"。

干净页和脏页被替换时要求也不一样：

- 干净页丢出缓冲池后，要用时可以从磁盘重新读。
- 脏页的最新改动还没写回最终页面，不能当成没用的缓存直接丢。后台刷新把脏页写回存储，既为恢复和检查点服务，也给缓冲池腾出空间。

Change Buffer 解决的是另一种开销：改一个不在缓冲池里的二级索引页，如果非得先随机读进来再做一点小改动，代价可能很高。先把可以延后的变更记下来，等页面被读入或后台合并时一起处理，就能少很多随机读。它不能替代行数据更新、事务日志和唯一性检查，所以别把所有写操作都画成先进同一个 change buffer。

## 表空间把页面组织到文件中

数据按表空间、段、区、页、记录来组织。表空间是文件层面的存储容器，段服务于索引等结构，区管理一批连续的页。默认 16 KiB 页的情况下，常见的区大小是 1 MiB，也就是 64 页；分配策略还有小段之类的情况，别以为每次都固定申请同样数量的区。

| 区域 | 主要用途 |
| --- | --- |
| 系统表空间 | 系统级存储，包括相应版本中的 change buffer 等内容 |
| 独立表空间 | 通常以表的 `.ibd` 文件保存数据与索引页 |
| 通用表空间 | 用户创建，可供多张表共享 |
| undo 表空间 | 保存撤销记录所需页面 |
| 临时表空间 | 服务于相应临时对象，生命周期与持久表不同 |

通用表空间的语法示例：

```sql
CREATE TABLESPACE notes_ts ADD DATAFILE 'notes_ts.ibd' ENGINE=InnoDB;
CREATE TABLE tablespace_demo(id INT PRIMARY KEY,name VARCHAR(20))
  TABLESPACE notes_ts ENGINE=InnoDB;
```

这要相应的管理权限，还会创建持久文件，学普通 SQL 不用执行。表空间文件、undo、redo 都有自己的管理规则，别把看起来"旧了"的日志文件直接删掉腾空间。

## redo 为什么能够保护尚未刷新的页面

执行一条更新时，会生成描述页面修改的 redo，先进缓冲，再按策略写到持久介质上。如果事务已经确认提交，数据页还没来得及全部落盘就崩了，恢复时可以按日志重做需要的修改。

这就是 WAL（Write-Ahead Logging）：页面持久化之前，恢复需要的日志得先写好。redo 不是只在 COMMIT 那一刻才生成，也不是把原始 UPDATE SQL 照抄一份。

比起每次提交都强制随机刷新所有改过的数据页，顺序写日志通常更快。之后后台刷脏页、推进检查点，不再需要的 redo 区域才能复用。事务提交成功不代表它的 redo 马上就没用了，还没持久化的数据页可能还靠它。

课程用的 8.0.26 是老式的 `ib_logfile0` 等布局；MySQL 8.0.30 起 redo 的容量和文件管理变了，常见的是 `#innodb_redo` 目录。文件名和数量要按实际版本确认，别把旧截图当成所有版本的固定结构。

把一次修改拆成三个时间点：

- A：内存里的数据页改好了，恢复需要的日志也生成了
- B：事务按提交策略满足了确认条件
- C：相关的数据页后来刷到了最终位置

B 不用等 C，这正是日志能缩短提交路径的原因。

- 在 A、B 之间崩溃：事务还没提交成功，恢复时不能当成已完成的业务留下来。
- 在 B、C 之间崩溃：磁盘上的数据页可能还是旧的，但已经按持久性条件确认的修改要由恢复机制重建。
- C 之后：页面本身已经包含了这些变化。

实际恢复可能先重做需要的页修改，再结合事务状态撤销没完成的修改，所以 redo 不能理解成"只记录已提交的事务"。

推进检查点，是为了让恢复要追溯的日志范围和脏页状态对得上。如果一段 redo 对应的页修改还没安全写回，就提前把这段日志复用覆盖掉，出故障时就可能新数据页和恢复信息一起丢。所以 redo 的循环复用受恢复进度约束，不是无条件覆盖最旧记录的普通环形文件。

## undo 保存回滚与历史重建所需的信息

把年龄从 30 改成 3 之前，数据库要先保存能恢复旧值的信息。ROLLBACK 靠这些撤销记录还原操作，MVCC 也靠它们重建读者需要的历史版本。

可以用"反向操作"来理解，但 undo 不是一份能直接执行的反向 SQL 清单，也不一定为每个版本存一整行。记录里的回滚指针连着对应的 undo，历史行顺着这些信息重建。

更新事务提交后，旧版本可能还被别的活跃读视图需要，不能马上删。Purge 等后台任务确认不再需要了才回收。长事务会让旧版本保留更久，光看已经提交了多少写事务，推不出 undo 能不能清空。

还是年龄 30 改成 3 的例子：redo 负责把需要恢复的修改重做到页面上，undo 提供撤销或重建旧版本需要的信息。两者方向不同，但不是把同一条 SQL 正着写一遍、倒着写一遍。原 SQL 里的条件、表达式和实际的页修改也不总是一一对应。

提交后 undo 什么时候能清，要看还有没有读者需要旧版本。一个 RR 事务早就建好了读视图，它可能还要读到年龄 30；写事务虽然提交了，系统也不能凭这一点就删掉重建旧版本需要的信息。长事务让历史保留变长，原因就在这个还没结束的读取需求。

## doublewrite 与 redo 解决不同故障

页面写到一半出故障，可能得到一张只写了一部分的坏页。Doublewrite 先存一份能用来恢复的页副本，再写到最终位置，专门对付这种部分页写入的问题。redo 描述的是修改。两者一起服务恢复，但不能互相替代。

后台有页面清理、读写 I/O、日志写入、purge 等任务。线程怎么划分、有几个，随版本和配置变化，课程里"固定十个线程"不是通用结论。可以用 `SHOW ENGINE INNODB STATUS` 看当前引擎状态，再结合配置分析。

提交的持久性还受 `innodb_flush_log_at_trx_commit` 控制：

- 1：通常每次提交都写日志并刷新
- 2：通常每次提交写到操作系统缓存，按周期刷新
- 0：通常按周期写入和刷新

周期不是严格的实时保证，后两种在故障时可能丢掉最近已确认的数据。持久性还依赖存储系统是否真的完成刷新，文件存在不能当作恢复验收。

写到操作系统缓存和刷到持久介质也要分开看。数据库进程把日志交给操作系统后，进程自己崩溃和整台机器掉电的影响不一样；掉电还可能丢掉操作系统还没刷出去的数据。所以解释提交参数时要说清楚是哪种故障，别一句"每秒写一次，最多丢一秒"就当成严格保证。

Doublewrite 面对的是整个页面本身写坏了。假如一个页面只写了一部分，新旧内容混在一起，这时日志恢复不能假设已经有一张完好的基础页。要先从受保护的页副本恢复出可用的页面，再用日志推进到需要的状态，这样就能把两种恢复职责连起来理解。
