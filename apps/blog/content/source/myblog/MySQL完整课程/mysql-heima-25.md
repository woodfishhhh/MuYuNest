在 REPEATABLE READ 事务里，别的连接已经把姓名改了并提交，当前连接的普通 SELECT 却可能还看到旧姓名。因为它按自己的读视图选可见版本，不是每次都去读最新的记录。

MVCC 是多版本并发控制，让一致性读能用合适的历史版本，减少读写互相阻塞。写写冲突还是靠锁来协调，MVCC 没有取消锁。

## 当前读和快照读看到的依据不同

常见的 InnoDB RC/RR 场景下，普通 SELECT 一般是一致性非锁定读，也叫快照读。`SELECT ... FOR SHARE`、`SELECT ... FOR UPDATE` 是锁定读，会按当前记录状态加必要的锁；遇到别的事务还没提交的冲突修改，可能要等。

注意几点：

- "当前读"不是随便读别人没提交的值，也不保证不等待。
- "快照读不加行锁"也不代表不需要元数据锁，或者完全没有别的等待。

可以接着用事务篇的两个连接做实验：A 在 RR 下先普通 SELECT 建立快照，B 修改并提交，A 再普通 SELECT 还是看到旧值；A 执行 FOR UPDATE 时，可能读到并锁住较新的状态。两种读法混着用，要清楚各自的规则，别以为它们看到的是同一份固定画面。

## 行记录怎样找到历史版本

InnoDB 聚簇记录里相关的隐藏信息：

| 字段 | 用途 |
| --- | --- |
| DB_TRX_ID | 最近插入或修改该记录的事务标识 |
| DB_ROLL_PTR | 指向用于撤销和重建旧版本的记录 |
| DB_ROW_ID | 缺少可用聚簇键时生成的隐藏行标识 |

DB_ROW_ID 不是每张表都有。有主键，或者有能被选作聚簇键的非空唯一索引时，就不用靠这个隐藏行标识。普通 SELECT * 不会显示这些内部字段。

课程用 id=30 的记录演示版本变化。初始值 age=30、name=A30；事务 2 把年龄改成 3，事务 3 把姓名改成 A3，事务 4 又把年龄改成 10。事务 3 提交、事务 4 接着完成更新后，逻辑上的版本链可以画成：

```text
当前：trx=4，age=10，name=A3
  ↓ 回滚信息
旧版：trx=3，age=3，name=A3
  ↓ 回滚信息
旧版：trx=2，age=3，name=A30
  ↓ 回滚信息
旧版：trx=1，age=30，name=A30
```

这是用重建出来的逻辑行解释版本链，不代表磁盘里给每一行都存了一份完整副本。更新同一行要协调写锁，图里各事务的修改是按能执行的先后完成的；"多个事务同时开着"不等于能同时随便改同一行。

## ReadView 记录创建时的可见性边界

快照不用把整个库复制一遍。ReadView 保存判断事务版本是否可见的信息，配合版本链决定返回哪个版本。课程用下面四个概念来讲：

| 概念名 | 含义 |
| --- | --- |
| creator_trx_id | 当前读视图所属事务的标识 |
| m_ids | 创建视图时仍活跃的相关读写事务标识集合 |
| min_trx_id | 活跃标识的下界 |
| max_trx_id | 创建时尚未分配给后续读写事务的高水位边界 |

这些是为了好理解起的名字，源码里的字段名可能不一样。max_trx_id 不是"活跃事务里最大的编号加一"：已经提交的事务也可能拿过更大的编号。事务编号具体什么时候分配，也不能简单等同于每次 BEGIN。

拿某个版本的事务标识 t 来判断：

1. t 是当前事务自己的修改：一般能看到。
2. t 小于视图的最小活跃边界：这个版本在建视图时已经够早，可见。
3. t 大于等于高水位：属于视图之后的事务，不可见。
4. t 在中间范围：查它在不在当时的活跃集合里，在就不可见，不在就可见。

一个版本不可见，就顺着 undo 找更旧的版本，直到找到可见的，或者确定当时还没有这一行。注意"等于高水位"也不可见，别漏了等号。

事务编号不是提交顺序。编号小的事务可能一直没提交，编号大的事务反而已经完成了。所以光比较"这个版本的编号比我小"判断不了它有没有提交，这才需要额外保存活跃集合。

高水位处理的是另一种情况：视图建好之后才拿到编号的新事务，肯定不属于这个视图要读的过去。统一排除掉，就不用为每个未来事务去更新旧视图。中间范围里既可能有已提交的事务，也可能有还活跃的，所以再查 m_ids 区分。

一次可见性判断可以拆成两个问题：这个版本是不是视图创建之后才有的；如果不是，创建视图时它是不是还没完成。自己的修改单独处理，所以先判断是不是当前事务的，别用判断别人的活跃状态那套规则，把自己刚写的值也遮住。

## 用同一条版本链比较 RC 和 RR

接着用课程的事务编号，读者是事务 5。第一次一致性读时，事务 2 已提交，3、4 还活跃；不算读者自己的标识，视图可以表示成：活跃集合 `{3,4}`，下界 3，高水位 6，创建者 5。

这个时候，事务 3 已经改了这一行但还没提交，事务 4 虽然开始了，但绕不过事务 3 的写锁去改同一行。第一次读能检查的链是 `trx=3 → trx=2 → trx=1`：trx=3 在活跃集合里，不可见；trx=2 小于下界 3，可见，所以返回 age=3、name=A30。

之后事务 3 提交并释放写锁，事务 4 才把年龄改成 10，先不提交。这时版本链才变成上图的 `4 → 3 → 2 → 1`。

- RC：第二次一致性读会建新视图，活跃集合变成 `{4}`，下界变成 4，高水位还是 6。trx=4 不可见，trx=3 小于新下界，返回 age=3、name=A3。所以 RC 下两次查询能看到不同的已提交版本。
- RR：第二次普通一致性读复用第一次的视图，顺着新链先跳过还活跃的 trx=4。事务 3 现在虽然提交了，但旧视图建立时它还活跃，所以旧视图还是不认它。最后继续返回事务 2 的版本，也就是 age=3、name=A30。

这里要分清两个时间：版本链会随着更新继续变长，ReadView 记的却是创建那一刻的可见性信息。某个事务后来提交了，旧视图里的活跃集合也不会自动跟着改。

把两次读放到一张时间表里会更清楚：

| 时点 | 写事务进展 | 版本链头部 | RC 的结果 | RR 的结果 |
| --- | --- | --- | --- | --- |
| 第一次普通读 | 2 已提交，3 已修改但未提交，4 尚未改该行 | 3 → 2 → 1 | 选择 2，`3,A30` | 选择 2，`3,A30` |
| 两次读取之间 | 3 提交，4 获得写入机会并修改，暂未提交 | 4 → 3 → 2 → 1 | 尚未发起新读 | 旧视图仍保留 |
| 第二次普通读 | 4 仍未提交 | 4 → 3 → 2 → 1 | 新视图选择 3，`3,A3` | 旧视图仍选择 2，`3,A30` |

表里的 `3,A30` 指年龄 3、姓名 A30，不是事务编号。第一次读的时候，事务 4 虽然已经活跃，但还没拿到写这一行的机会，所以那个时间点画不出它覆盖事务 3 的版本。版本链增长和视图创建是两条时间线，解释时要对齐。

RR 的第二次读不是把第一次 SELECT 的结果缓存起来原样返回。它还是要执行查询、找到记录、判断版本；之所以拿到同样的旧值，是因为用了同一个可见性边界和需要的 undo 信息。换个查询条件，也是按这个边界去找对应的记录，而不是去查什么"SQL 结果缓存"。

## 可重复读还有哪些边界

RR 一般在第一次一致性读时才建视图，不一定是 START TRANSACTION 那一刻。当前事务自己写的改动自己能看到，删除和插入也有各自的版本可见性规则；"可重复"不是说整个事务从此只看到一份绝对不变的副本。

还有读者需要旧版本时，purge 不能随便删对应的 undo。长时间不结束的事务会因此增加历史保留的开销。正常结束事务，既能释放锁，也让系统有机会回收不再需要的历史。

检验自己懂没懂：能顺着一个具体的 ReadView，说清楚为什么跳过 trx=4、trx=3，又为什么停在 trx=2。只会背"隐藏字段、undo、ReadView"三个名词，还没说明白读取结果是怎么定下来的。
