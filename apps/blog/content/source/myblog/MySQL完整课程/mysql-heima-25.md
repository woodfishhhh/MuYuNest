在 REPEATABLE READ 事务里，其他连接已经把姓名改了并提交，当前连接的普通 SELECT 却仍可能看到旧姓名。原因在于它按自己的读视图选择可见版本，而不是每次都读取当前最新记录。

MVCC 是多版本并发控制。它让一致性读可以使用合适的历史版本，减少读写之间的相互阻塞。写写冲突仍要靠锁协调，MVCC 没有取消锁。

## 当前读和快照读看到的依据不同

在常见 InnoDB RC/RR 场景中，普通 SELECT 通常是一致性非锁定读，也称快照读。`SELECT ... FOR SHARE`、`SELECT ... FOR UPDATE` 是锁定读，会根据当前记录状态获取必要的锁；遇到其他事务尚未提交的冲突修改时，可能等待。

“当前读”不代表随意读取别人未提交的值。它也不保证完全不等待。反过来，“快照读不加行锁”也不代表不需要元数据锁或完全没有其他等待来源。

可以沿用事务篇的两个连接实验：A 在 RR 中先普通 SELECT 建立快照，B 修改并提交，A 再普通 SELECT 仍看到旧值；A 执行 FOR UPDATE 时，可能读取并锁定较新的状态。混合使用两种读法必须理解各自语义，不能假设它们看到同一幅固定画面。

## 行记录怎样找到历史版本

InnoDB 聚簇记录中的相关隐藏信息包括：

| 字段 | 用途 |
| --- | --- |
| DB_TRX_ID | 最近插入或修改该记录的事务标识 |
| DB_ROLL_PTR | 指向用于撤销和重建旧版本的记录 |
| DB_ROW_ID | 缺少可用聚簇键时生成的隐藏行标识 |

DB_ROW_ID 不是所有表都有。存在主键，或存在可被选作聚簇键的非空唯一索引时，不需要依靠这个隐藏行标识。普通 SELECT * 不会直接显示这些内部字段。

课程用 id=30 的记录说明版本变化。初始值是 age=30、name=A30；事务 2 把年龄改成 3，事务 3 把姓名改成 A3，事务 4 又把年龄改成 10。在事务 3 提交、事务 4 随后完成更新之后，逻辑版本链可以画为：

```text
当前：trx=4，age=10，name=A3
  ↓ 回滚信息
旧版：trx=3，age=3，name=A3
  ↓ 回滚信息
旧版：trx=2，age=3，name=A30
  ↓ 回滚信息
旧版：trx=1，age=30，name=A30
```

这是用重建后的逻辑行解释版本链，不代表磁盘里为每一行都保存了一份完整表副本。更新同一行需要协调写锁，图中事务的修改按可执行的先后完成；“多个事务同时开启”不等于能同时不受限制地改同一行。

## ReadView 记录创建时的可见性边界

快照不需要把整库复制一遍。ReadView 保存判断事务版本是否可见的信息，结合版本链决定应该返回哪版记录。课程用下面四个概念解释：

| 概念名 | 含义 |
| --- | --- |
| creator_trx_id | 当前读视图所属事务的标识 |
| m_ids | 创建视图时仍活跃的相关读写事务标识集合 |
| min_trx_id | 活跃标识的下界 |
| max_trx_id | 创建时尚未分配给后续读写事务的高水位边界 |

这些是便于理解的命名，实际源码字段名可能不同。max_trx_id 不是“活跃事务里最大的编号再加一”：已经提交的事务也可能取得过更大编号。事务编号的实际分配时机也不能简单等同于每次 BEGIN。

拿某个版本的事务标识 t 判断：

1. 如果 t 属于当前事务自己的修改，当前事务通常可以看到它。
2. 如果 t 小于视图的最小活跃边界，该版本在创建视图时已经足够早，可见。
3. 如果 t 大于等于高水位边界，它属于视图之后的事务，不可见。
4. 如果 t 在中间范围内，就查它是否在当时的活跃集合中：在集合里则不可见，不在则可见。

一个版本不可见，就沿 undo 尝试更旧版本，直到找到可见版本或确定当时不存在这行。边界比较中的“等于高水位”也属于不可见，不能遗漏等号。

这里的事务编号并不是提交次序。编号较小的事务可以一直未提交，而后取得较大编号的事务已经完成。因此，仅比较“这个版本的编号比我小”不足以判断它是否已经提交，才需要同时保存活跃集合。

高水位处理的是另一类情况：视图建立以后才取得相应编号的新事务，显然不属于这个视图要读取的过去。把它们统一排除，可以不为每个未来事务不断更新旧视图。中间范围里既可能有已提交事务，也可能有仍活跃事务，所以再查 m_ids 区分。

可以把一次可见性判断当作两个问题：这个版本是否属于视图创建之后；如果不是，它在创建时是否仍未完成。自己的修改另有可见性处理，因此先判断是否属于当前事务，不应拿别人的活跃状态规则把自己刚写入的值也遮住。

## 用同一条版本链比较 RC 和 RR

沿用课程的事务编号示意，读者是事务 5。第一次一致性读时，事务 2 已提交，3、4 仍活跃；忽略读者自己的标识后，视图可表示为：活跃集合 `{3,4}`，下界 3，高水位 6，创建者 5。

这个时刻，事务 3 已修改该行但尚未提交，事务 4 虽已开始，却还不能越过事务 3 的写锁修改同一行。第一次读所能检查的链是 `trx=3 → trx=2 → trx=1`：trx=3 在活跃集合中，不可见；trx=2 小于下界 3，可见，因此返回 age=3、name=A30。

随后事务 3 提交并释放写锁，事务 4 才把年龄改为 10，暂不提交。此时版本链才成为上图中的 `4 → 3 → 2 → 1`。RC 下第二次一致性读创建新视图，活跃集合变为 `{4}`、下界变为 4、高水位仍为 6：trx=4 不可见，trx=3 小于新下界，因此返回 age=3、name=A3。这解释了为什么 RC 两次查询能看到不同的已提交版本。

RR 下，第二次普通一致性读复用第一次的视图，沿新链先跳过仍活跃的 trx=4。虽然事务 3 现在已经提交，但它在旧视图创建时仍活跃，因此仍不能被这个旧视图接受。最终继续返回事务 2 的版本，即 age=3、name=A30。

这个例子应区分两个时间：版本链可以随着更新继续增长，ReadView 记录的却是创建时的可见性信息。它不会因为某个事务后来提交，就自动修改旧视图里的活跃集合。

将两次读取放在一张时间表里，变化会更清楚：

| 时点 | 写事务进展 | 版本链头部 | RC 的结果 | RR 的结果 |
| --- | --- | --- | --- | --- |
| 第一次普通读 | 2 已提交，3 已修改但未提交，4 尚未改该行 | 3 → 2 → 1 | 选择 2，`3,A30` | 选择 2，`3,A30` |
| 两次读取之间 | 3 提交，4 获得写入机会并修改，暂未提交 | 4 → 3 → 2 → 1 | 尚未发起新读 | 旧视图仍保留 |
| 第二次普通读 | 4 仍未提交 | 4 → 3 → 2 → 1 | 新视图选择 3，`3,A3` | 旧视图仍选择 2，`3,A30` |

表中的 `3,A30` 表示年龄 3、姓名 A30，不是事务编号。第一次读取时，事务 4 虽然已经活跃，但尚未取得这一行的写入机会，所以不能在那个时点画出它已经覆盖事务 3 的行版本。版本链增长和视图创建是两条时间线，解释时必须对齐。

RR 的第二次读并不是缓存了第一次 SELECT 的结果然后原样返回。它仍要执行查询、找到相关记录并判断版本；之所以能得到相同旧值，是因为使用了同一个可见性边界和必要的 undo 信息。换一个查询条件，仍然需要根据这个边界寻找相应记录，而不是查一个“SQL 结果缓存”。

## 可重复读还有哪些边界

RR 一般在首次一致性读时建立视图，不一定在 START TRANSACTION 瞬间建立。当前事务自己写入的变化可以被自己看见，删除和插入也有对应的版本可见性规则；不能把“可重复”理解成整个事务从此永远只看到绝对不变的一份副本。

仍有读者需要旧版本时，purge 不能任意删除相应 undo。长时间保留的事务可能因此增加历史保留成本。正常结束事务既释放相应锁，也让系统有机会回收不再需要的历史。

要验证理解，应能沿一个具体 ReadView 解释为什么跳过 trx=4、trx=3，又为什么停在 trx=2；只背诵“隐藏字段、undo、ReadView”三个名词，还没有说明读取结果是怎样决定的。
