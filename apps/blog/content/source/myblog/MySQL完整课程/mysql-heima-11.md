一条 SELECT 从连接进来，先经过 SQL 层的解析和优化，再调用存储引擎读取记录。把这条路径搞清楚，才分得开“SQL 写错了”“执行计划不好”“存储读得慢”这几类问题。

## 一条查询经过哪些层

![一条 SQL 的职责分层](assets/query-execution.svg)

- 连接管理：通信和会话
- SQL 层：理解语句含义、选择计划、执行跨引擎的功能
- 存储引擎：表数据的组织、索引访问，以及相关的锁、事务等
- 文件系统：最底层，存数据和日志

这只是职责划分，不是说每次查询都要一层层访问到磁盘。页已经在缓冲池里，就直接从内存读。旧的架构图常画着“查询缓存”，MySQL 8.0 已经移除了旧的 Query Cache，它跟 InnoDB 缓冲池是两个东西。

以 `SELECT name FROM emp WHERE id=1` 为例：

1. 解析：识别出这是一条查询，检查关键字和表达式能不能组成合法语句；表和列要能对应到实际对象
2. 优化：考虑怎么取到 id=1，比如有没有主键、用主键定位代价多大
3. 执行：执行器按选好的计划请求 InnoDB 访问记录，拿到这一行后返回 name

出问题时，对应到不同的层：

- 列名写错：在能解释和执行计划之前就失败了
- SQL 合法但扫描了大量记录：问题多半在访问方式和数据规模
- 计划只定位一行，响应还是很久：还要查锁、存储、网络这些等待

分层的用处，就是把不同的故障放回各自负责的那一层。

SQL 层的“优化”也不会把写错的业务逻辑变对。`WHERE id=1` 和 `WHERE id>=1` 意思不同，优化器只能在不改变含义的前提下选执行方法，不会因为等值查找快就把范围查询改成等值。

## 引擎属于表，不属于整个数据库

```sql
SHOW ENGINES;
SHOW CREATE TABLE mysql_notes.emp;
SELECT @@default_storage_engine;
```

SHOW ENGINES 的 Support 列说明当前实例支持哪些引擎，标 DEFAULT 的是默认引擎。具体某张表用哪个引擎，要看 SHOW CREATE TABLE 里的 ENGINE。同一个库里不同的表可以用不同引擎。

```sql
CREATE TABLE engine_innodb (id INT PRIMARY KEY,name VARCHAR(20)) ENGINE=InnoDB;
CREATE TABLE engine_myisam (id INT PRIMARY KEY,name VARCHAR(20)) ENGINE=MyISAM;
CREATE TABLE engine_memory (id INT PRIMARY KEY,name VARCHAR(20)) ENGINE=MEMORY;
```

这几句只在支持相应引擎的练习实例上执行。省略 ENGINE 就用实例的默认值，别因为“我没写 ENGINE”就认定所有环境都一定是 InnoDB。

| 能力 | InnoDB | MyISAM | MEMORY |
| --- | --- | --- | --- |
| 事务 | 支持 | 不支持 | 不支持 |
| 行级锁 | 支持，另有其他锁 | 主要使用表级锁 | 表级锁 |
| 外键约束 | 支持 | 不支持执行外键约束 | 不支持执行外键约束 |
| 主要数据位置 | 持久化文件与内存缓冲 | 持久化文件 | 内存，重启丢失表中数据 |
| 常见索引 | B+ 树 | B+ 树等 | HASH 或 BTREE |

业务需要事务时，参与事务的表换成非事务引擎，就别指望 ROLLBACK 能撤销全部操作。也别因为“读多”就直接认定 MyISAM 更合适，恢复能力、并发写入、锁等待和运维成本都要一起考虑。本课程的普通业务实验用 InnoDB 就行。

## 文件与逻辑结构不是同一个层次

```sql
SHOW VARIABLES LIKE 'datadir';
SHOW VARIABLES LIKE 'innodb_file_per_table';
SHOW VARIABLES LIKE 'innodb_page_size';
```

datadir 是数据目录。开启独立表空间时，普通 InnoDB 表一般有一个对应的 `.ibd` 文件，里面存表和索引的页，还包含序列化字典信息等元数据。InnoDB 也支持别的表空间形式，所以不能说“每张表永远只有一个独立 ibd 文件”。

MyISAM 一般分别有 `.MYD` 数据文件、`.MYI` 索引文件，以及 MySQL 8.0 的 `.sdi` 元数据文件。MEMORY 的元数据是持久化的，但行数据不是。别用记事本改这些文件，也别以为运行中直接复制一份 ibd 就完成了可恢复的备份。

InnoDB 的逻辑结构按“表空间 → 段 → 区 → 页 → 行”来理解：

- 段：服务于某类数据结构，比如索引叶子页
- 区：成批管理页
- 页：主要的存储和缓冲管理单位
- 行：记录存在页里

默认页大小一般是 16 KiB，这个配置下一个 1 MiB 的区包含 64 页。实例可以选别的支持的页大小，所以 16 KiB 只是默认配置，不是哪个实例都不变的常数。

`ibd2sdi` 能提取表空间里的序列化字典信息，适合检查表元数据，但不会把整张表转换成能直接看的业务数据。平时学习看表结构，优先用 SHOW CREATE TABLE。

一页里有多个员工，查其中一个人的记录时，存储读取一般以页为单位，不是只从磁盘取出姓名那几个字节。之后再访问同一页的其他记录，就能复用已经读进来的页。所以数据局部性很重要，“返回一行”也不代表只读了一行大小的字节。

页里还要存管理信息，索引也占页，所以不能用“表文件大小 ÷ 每行字段字节数”直接算出精确行数。段、区这些上层结构负责组织和分配页，SQL 查询里的一行和磁盘上的某块文件空间并不是一一对应的。

## Linux 环境要把安装与连接分开排查

课程后面的演示用的是 Linux 上的 MySQL 8.0.26，安装用的是旧的 CentOS/RPM 环境。顺序理解了就行：

1. 准备和操作系统、架构匹配的安装包
2. 处理依赖
3. 安装服务端和客户端
4. 初始化数据目录
5. 启动服务
6. 设置管理员密码
7. 配置受限的远程账户

在已经装好 MySQL、服务名是 mysqld 的 Linux 实验机上：

```bash
systemctl status mysqld
sudo systemctl start mysqld
mysql -u root -p
```

有些发行版的服务名是 mysql，以实际安装包为准。旧 RPM 包的依赖名称和安装顺序，不能当成所有现代发行版的通用命令；优先用对应发行版支持的安装方式，别强制忽略依赖。

首次初始化可能生成临时密码，也可能走别的本地认证流程，看安装方式。临时密码在本机自己查看，尽快改掉。密码策略拒绝简单密码，就换一个符合策略的，不用为了跟示例去降低全局策略。

远程 DataGrip 连不上，按顺序确认：

1. 服务有没有在运行
2. 监听地址和端口对不对
3. 网络和防火墙是否放行这个客户端
4. 账户 Host 是否匹配
5. 这个账户有没有拿到所需权限

别把关防火墙、开放 root@'%'、授予 `*.*` 当成安装的固定步骤。后面讲的 SQL 机制都不需要把数据库暴露到公网。

手上有和课程一样的 RPM bundle 的话，安装流程可以再拆细：先在独立的 CentOS 实验机上核对系统和包的架构，把 bundle 解压到新目录，看清其中各个 RPM 的名字，再按依赖装通用组件、库、客户端和服务器。下面的命令只做检查，不会替你猜包版本：

```bash
cat /etc/os-release
uname -m
tar -tf /path/to/mysql-rpm-bundle.tar
rpm -qa | grep -Ei 'mysql|mariadb'
rpm -qp --requires /path/to/mysql-community-server.rpm
```

`/path/to/...` 换成已经下载的真实文件；上面的短文件名只是位置占位，不是能直接下载的包名。`tar -tf` 先列出包里的内容，`rpm -qp --requires` 查看这个还没安装的包依赖什么。已经装了别的数据库包的，先确认它现在的用途，别为了照着顺序跑就直接卸载。

RPM bundle 拆成多个包，是因为客户端、共享库和服务器之间有依赖关系。缺依赖报错时，看清具体的库名和版本要求，从匹配的系统软件源解决，再装原来的包。强制忽略依赖，安装记录可能显示成功，启动时却找不到动态库。

服务启动后，这类 RPM 安装一般会生成临时管理员密码，在实验机本地查 `/var/log/mysqld.log` 里的对应记录。用它第一次登录后执行 `ALTER USER 'root'@'localhost' IDENTIFIED BY '自己的新密码';`，退出再用新密码登录一次。第一次能登录说明临时凭据有效，重新登录才能确认新密码生效。

最后才处理远程访问：在服务器上确认监听端口，给明确的客户端来源建账户，授予练习库需要的权限，再在 DataGrip 里填服务器地址、端口和这个账户。操作系统能连上、数据库账户能访问，是两层独立的条件。原课配套的 RPM 清单没拿到，所以这里只写安装依赖和验证过程，不编一组没法确认是否匹配的完整包文件名。
