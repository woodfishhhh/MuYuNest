在几百万名员工中找一个工号，如果每次都检查整张表，成本会随行数增长。索引保存适合查找的额外结构，让数据库先缩小候选范围，再读取需要的记录。但维护结构要消耗空间、缓存和写入成本，索引并非越多越好。

## 为什么不直接用普通二叉搜索树

二叉搜索树每个节点最多有两个孩子。按递增顺序插入一组键，普通二叉搜索树可能退化成链表；平衡树能避免这种退化，但分叉仍然少。数据存在磁盘页上时，树太高可能意味着沿路径访问更多页面。

B 树让一个节点保存多个键并指向多个子节点。例如抽象的五阶 B 树最多有 5 个孩子、4 个分隔键。插入第 5 个键使节点超出容量，就需要分裂，并把分隔键传到父节点；父节点再满，可以继续向上传播，根分裂时树高增加。

B+ 树进一步把叶子数据与上层导航分开：非叶子页保存分隔键和子页位置，叶子页保存索引记录。这样同样大小的非叶子页可以容纳更多导航项。

不同教材对“阶”与节点容量的约定可能不同。理解磁盘索引时，应抓住“一个页能容纳多少导航项”，而不是把动画中的固定 4 个键直接当作 InnoDB 的实际容量。

### 把五阶 B 树实际插入一遍

先沿五阶 B 树的约定演示：一个节点最多四个键，内部节点最多五个孩子。这里解释普通 B 树的分裂，不把它混作 InnoDB 页面分裂的逐字实现。

依次插入 234、345、23、899，树还只有一个节点，内部按键排序：

```text
[23, 234, 345, 899]
```

再插入 1200，暂时得到五个键，超过容量。取中间的 345 提升为新的根，较小的两个键组成左孩子，较大的两个键组成右孩子：

```text
          [345]
         /     \
 [23,234]       [899,1200]
```

为什么要提升中间键？这样左右两边既保持大小关系，也不会把全部剩余键挤到一侧。根中的 345 把可选范围分成“小于 345”和“大于 345”两部分，后续查找可以直接选择分支。

继续插入 1234、1500，都进入右孩子，右侧变成 `[899,1200,1234,1500]`。再插入 1000，按顺序放在 899 与 1200 之间，节点再次达到五个键。这次中间键是 1200，它提升到已有根中：

```text
              [345,1200]
           /      |       \
     [23,234] [899,1000] [1234,1500]
```

根有两个分隔键，就形成三个范围：小于 345、介于 345 与 1200、大于 1200。指针比键多一个的原因就在这里：n 个分隔点把数轴切成 n+1 段。

再插入 123、245、12，左孩子最终超过容量，中间键 123 提升；插入 1567、1800、1980，右端孩子的中间键 1567 提升。这时根变成 `[123,345,1200,1567]`，已经达到四键上限。最后继续插入 2000、1888、2456，右端孩子分裂后，要把 1980 也交给根。

根此时暂时有 `[123,345,1200,1567,1980]` 五个键，自己也超限。于是 1200 再向上提升，产生新根，原来的根拆成左右两个内部节点：

```text
[1200]
├─ 左侧内部节点 [123,345]
│  ├─ [12,23]
│  ├─ [234,245]
│  └─ [899,1000]
└─ 右侧内部节点 [1567,1980]
   ├─ [1234,1500]
   ├─ [1800,1888]
   └─ [2000,2456]
```

最后一层有六个叶子，左内部节点连接较小的三个，右内部节点连接较大的三个。树高增加发生在根也容纳不下提升键的时候，不是每插入一条记录就增加一层。

普通 B 树的键与数据可以在非叶子节点出现。B+ 树把供范围扫描的数据项集中到叶子，非叶子主要负责导航；分隔值在叶子中仍有相应表示。不能把上面“中间键从叶子提走”的 B 树过程直接照搬成 B+ 树删除了该条业务记录。

## 等值查找和范围查找走不同的后半程

把主键 10、20、30、40、50、60 分布到三个叶子页：

```text
                 根页中的分隔键
                 /     |     \
叶子页：      [10,20] ↔ [30,40] ↔ [50,60]
```

找 40 时，先由根判断应该进入哪个子页，再在叶子页中定位 40。查询 `id BETWEEN 25 AND 55` 时，先定位第一个不小于 25 的位置，即 30，再沿叶子页的有序连接继续扫描 40、50，遇到 60 超过上界后结束。

InnoDB 的 B+ 树页面有相邻页链接。范围扫描可以沿有序叶子层推进，不必为区间内每个键都从根开始查找。树有几层也不等于一定发生几次真实磁盘读取：根和上层页往往已经缓存在内存中。

## HASH 快在等值定位，缺少全局顺序

哈希索引把键经过哈希函数映射到桶或槽位；多个键落到同一位置时，还要比较实际键来处理冲突。它不保存可直接用于大小比较的整体顺序，所以一般不适合直接支持 `>`、BETWEEN 或有序扫描。

MEMORY 支持显式 HASH 索引。InnoDB 的常规索引主要使用 B+ 树，同时可能在热点访问上维护自适应哈希结构；这不是用户把整个普通索引改成 HASH，也不是保证每次等值查询只需要一次物理 I/O。

MySQL 还支持全文索引、空间索引等专用结构。它们的类型、运算和引擎支持需要分别看，不能把“所有索引都是有序 B+ 树”当成定义。此后未特别说明时，讨论的是 InnoDB 普通 B+ 树索引。

## 聚簇索引的叶子就是行数据

对于有主键的 InnoDB 表，主键索引通常就是聚簇索引。聚簇描述的是行数据与这棵索引的存储组织方式：叶子记录包含行数据，因此一张表只有一份这种组织。

选择规则是：有主键就使用主键；没有主键时，寻找合适的全部列非空的唯一索引；再没有，InnoDB 生成隐藏行标识和内部聚簇索引。可空 UNIQUE 不能不加条件地视为第二种候选。

二级索引的叶子主要保存索引列值和对应聚簇键。用已知 emp 表建立一个索引：

```sql
CREATE INDEX idx_emp_name ON emp(name);
SELECT id,name,salary FROM emp WHERE name='柳岩';
```

如果计划选择 idx_emp_name，访问路径是：

```text
name 索引中定位“柳岩” → 得到主键 id=1
→ 进入主键索引定位 id=1 → 取得 salary 等所需列
```

从二级索引再去聚簇索引读取行的过程叫回表。二级索引不是直接存一份完整员工表，也不是简单保存随文件移动就失效的业务行地址。

若只查询 `SELECT id,name FROM emp WHERE name='柳岩'`，所需信息已在二级索引中，就有机会不回表，这叫覆盖索引。覆盖是某个索引相对于某条查询的性质，不是一种单独创建的神秘索引类型。

可以对照三种查询，明确究竟在哪一步取得了返回列：

| 查询条件与返回列 | 先走的结构 | 是否还缺返回信息 |
| --- | --- | --- |
| 按 id 查 name、salary | 聚簇索引 | 叶子已经有整行所需数据 |
| 按 name 查 id、name | name 二级索引 | 这两个字段已有机会直接取得 |
| 按 name 查 id、name、salary | name 二级索引 | salary 不在其中，需要沿 id 再找行 |

第二种情况叫覆盖，是因为这条查询需要的列恰好都在索引里。第三种增加一个 salary，查询形状只多了一列，访问过程却可能多出回表。优化时选择实际要展示的字段，可以影响真实读取成本，不只是代码风格。

“走两棵树”也不应简单等于“耗时恰好两倍”。页面是否在内存、匹配多少条记录、是否连续访问、是否等待锁都会影响时间。机制上多了一次定位，实际成本还要测量；不能拿它直接构造脱离环境的速度数字。

## 索引分类是多个维度

主键、唯一、普通、全文说明约束或用途；单列、联合说明包含几个列；聚簇、二级说明行数据组织。因此一个 `(dept_id,age)` 索引可以同时是“普通、联合、二级索引”，这些名称不冲突。

```sql
CREATE INDEX idx_emp_dept_age ON emp(dept_id,age);
SHOW INDEX FROM emp;
DROP INDEX idx_emp_dept_age ON emp;
```

SHOW INDEX 中联合索引会出现多行，Seq_in_index 依次表示字段顺序，不代表创建了多个独立索引。Index_type 显示 BTREE 是 MySQL 的类型名称，InnoDB 的实际结构按 B+ 树理解。

唯一索引写法为 `CREATE UNIQUE INDEX ...`，创建前必须检查现有数据是否满足唯一性。主键和 UNIQUE 约束已经隐含相应索引，不要再机械建立一份同列索引。

## 树高估算只是数量级解释

假设一个页约 16 KiB，每个叶子页粗略容纳 16 条行记录，每个非叶子页约有 1000 个子页位置。那么两层树能容纳约 1.6 万行，三层约 1600 万行。这说明高扇出结构能以较少层数管理大量记录。

实际页面还包含页头、记录头、目录、剩余空间等开销，键长、行长、填充程度和页大小都会改变容量。不能据此给出“所有表三层必定能放 2200 万行”的保证，也不能把某个固定行数当成必须分库分表的阈值。

主键越长，多个二级索引携带的主键信息通常也越大；索引越多，每次插入和删除要维护的结构也越多。后续设计索引时，要同时考虑读路径与写放大。

这个估算还可以写成一般式。设内部页平均能指向 F 个子页，叶子页平均容纳 R 行，根到叶子有 h 层，则大致容量按 `F^(h-1) × R` 增长。取 F=1000、R=16：一层只有叶子，约 16 行；两层约 16000 行；三层约 16000000 行。少增加一层，容量就可能扩大一个很大的倍数。

但 F 和 R 都不是固定业务常量。把主键变长，会减少同页能容纳的导航信息；把一行变宽，会减少叶子容量；页面没有填满，也会降低有效容量。因此“树矮”解释了它适合大量数据查找，却没有给出任何表都适用的精确容量承诺。
