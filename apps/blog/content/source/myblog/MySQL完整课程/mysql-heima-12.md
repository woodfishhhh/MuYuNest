在几百万名员工里找一个工号，每次都查整张表的话，成本随行数一起涨。索引是一份方便查找的额外结构，让数据库先缩小候选范围，再去读需要的记录。但维护它要占空间、占缓存、增加写入成本，索引不是越多越好。

## 为什么不直接用普通二叉搜索树

二叉搜索树每个节点最多两个孩子。按递增顺序插入一组键，普通二叉搜索树可能退化成链表；平衡树能避免退化，但分叉还是少。数据存在磁盘页上时，树太高就可能要沿路径访问更多页。

B 树让一个节点存多个键、指向多个子节点。比如抽象的五阶 B 树最多 5 个孩子、4 个分隔键。插入第 5 个键时节点超出容量，就要分裂，把分隔键传给父节点；父节点也满了就继续往上传，根分裂时树高增加。

B+ 树再进一步，把叶子数据和上层导航分开：非叶子页存分隔键和子页位置，叶子页存索引记录。这样同样大小的非叶子页能放下更多导航项。

不同教材对“阶”和节点容量的约定可能不一样。理解磁盘索引时抓住“一个页能放多少导航项”就行，别把动画里固定的 4 个键当成 InnoDB 的实际容量。

### 把五阶 B 树实际插入一遍

按五阶 B 树的约定演示：一个节点最多四个键，内部节点最多五个孩子。这里讲的是普通 B 树的分裂，别把它当成 InnoDB 页分裂的具体实现。

依次插入 234、345、23、899，树还只有一个节点，节点内按键排序：

```text
[23, 234, 345, 899]
```

再插入 1200，暂时有五个键，超过容量。取中间的 345 提升为新的根，较小的两个键组成左孩子，较大的两个键组成右孩子：

```text
          [345]
         /     \
 [23,234]       [899,1200]
```

为什么提升中间键？这样左右两边既保持大小关系，剩下的键也不会都挤到一边。根里的 345 把范围分成“小于 345”和“大于 345”两部分，后面查找直接选分支就行。

继续插入 1234、1500，都进右孩子，右边变成 `[899,1200,1234,1500]`。再插入 1000，按顺序放在 899 和 1200 之间，节点又到了五个键。这次中间键是 1200，提升到已有的根里：

```text
              [345,1200]
           /      |       \
     [23,234] [899,1000] [1234,1500]
```

根有两个分隔键，就分出三个范围：小于 345、345 到 1200 之间、大于 1200。指针比键多一个就是这个原因：n 个分隔点把数轴切成 n+1 段。

再插入 123、245、12，左孩子最终超过容量，中间键 123 提升；插入 1567、1800、1980，最右边孩子的中间键 1567 提升。这时根变成 `[123,345,1200,1567]`，已经到了四个键的上限。最后插入 2000、1888、2456，最右边的孩子分裂后，还要把 1980 交给根。

根这时暂时有 `[123,345,1200,1567,1980]` 五个键，自己也超了。于是 1200 再往上提升，产生新根，原来的根拆成左右两个内部节点：

```text
[1200]
├─ 左侧内部节点 [123,345]
│  ├─ [12,23]
│  ├─ [234,245]
│  └─ [899,1000]
└─ 右侧内部节点 [1567,1980]
   ├─ [1234,1500]
   ├─ [1800,1888]
   └─ [2000,2456]
```

最底层有六个叶子，左内部节点连较小的三个，右内部节点连较大的三个。只有根也放不下提升上来的键时树高才增加，不是每插入一条记录就加一层。

普通 B 树的键和数据可以出现在非叶子节点。B+ 树把用于范围扫描的数据项集中到叶子，非叶子主要负责导航，分隔值在叶子里仍有对应的表示。别把上面 B 树“中间键从叶子提走”的过程，照搬理解成 B+ 树把这条业务记录删了。

## 等值查找和范围查找走不同的后半程

把主键 10、20、30、40、50、60 分到三个叶子页：

```text
                 根页中的分隔键
                 /     |     \
叶子页：      [10,20] ↔ [30,40] ↔ [50,60]
```

- 找 40：先由根判断该进哪个子页，再在叶子页里定位 40
- 查 `id BETWEEN 25 AND 55`：先定位第一个不小于 25 的位置，也就是 30，再沿叶子页的有序链接往后扫 40、50，碰到 60 超过上界就结束

InnoDB 的 B+ 树页之间有相邻页链接，范围扫描可以沿有序的叶子层往前推进，不用为区间里每个键都从根查一遍。树有几层，也不一定就有几次真实的磁盘读取：根和上层页往往已经缓存在内存里了。

## HASH 快在等值定位，缺少全局顺序

哈希索引用哈希函数把键映射到桶或槽位；多个键落到同一个位置时，还要比较实际的键来处理冲突。它不保存能直接做大小比较的整体顺序，所以一般不适合直接支持 `>`、BETWEEN 或有序扫描。

MEMORY 支持显式的 HASH 索引。InnoDB 的常规索引主要用 B+ 树，也可能针对热点访问维护自适应哈希结构；但这不是用户把整个普通索引改成了 HASH，也不保证每次等值查询只要一次物理 I/O。

MySQL 还支持全文索引、空间索引等专用结构，它们的类型、运算和引擎支持要分别看，不能把“所有索引都是有序 B+ 树”当成定义。后面没特别说明的，讲的都是 InnoDB 普通 B+ 树索引。

## 聚簇索引的叶子就是行数据

有主键的 InnoDB 表，主键索引一般就是聚簇索引。“聚簇”说的是行数据和这棵索引怎么存：叶子记录里就是行数据，所以一张表只有一份这样的组织。

聚簇索引的选择规则：

1. 有主键就用主键
2. 没有主键，找一个合适的、所有列都非空的唯一索引
3. 还没有，InnoDB 生成隐藏的行标识和内部聚簇索引

可空的 UNIQUE 不能无条件算作第 2 种候选。

二级索引的叶子主要存索引列的值和对应的聚簇键。在已知的 emp 表上建一个索引：

```sql
CREATE INDEX idx_emp_name ON emp(name);
SELECT id,name,salary FROM emp WHERE name='柳岩';
```

如果计划选了 idx_emp_name，访问路径是：

```text
name 索引中定位“柳岩” → 得到主键 id=1
→ 进入主键索引定位 id=1 → 取得 salary 等所需列
```

从二级索引再去聚簇索引读行，这个过程叫回表。二级索引里没有一份完整的员工表，存的也不是文件一移动就失效的业务行地址。

如果只查 `SELECT id,name FROM emp WHERE name='柳岩'`，需要的信息二级索引里都有，就有机会不回表，这叫覆盖索引。“覆盖”是某个索引对某条查询来说的性质，不是一种要单独创建的特殊索引类型。

对照三种查询，看返回列到底是在哪一步拿到的：

| 查询条件与返回列 | 先走的结构 | 是否还缺返回信息 |
| --- | --- | --- |
| 按 id 查 name、salary | 聚簇索引 | 叶子已经有整行所需数据 |
| 按 name 查 id、name | name 二级索引 | 这两个字段已有机会直接取得 |
| 按 name 查 id、name、salary | name 二级索引 | salary 不在其中，需要沿 id 再找行 |

第二种叫覆盖，因为这条查询要的列刚好都在索引里。第三种多了一个 salary，查询只多一列，访问过程却可能多一次回表。只选实际要显示的字段，会影响真实的读取成本，不只是代码风格问题。

“走两棵树”也不是“耗时正好两倍”。页在不在内存、匹配多少条记录、是不是连续访问、有没有等锁，都会影响时间。机制上多了一次定位，实际成本还得测；别拿它凭空编出脱离环境的速度数字。

## 索引分类是多个维度

索引是从几个角度分类的：

- 主键、唯一、普通、全文：约束或用途
- 单列、联合：包含几个列
- 聚簇、二级：行数据怎么组织

所以一个 `(dept_id,age)` 索引可以同时是“普通、联合、二级索引”，这些叫法不冲突。

```sql
CREATE INDEX idx_emp_dept_age ON emp(dept_id,age);
SHOW INDEX FROM emp;
DROP INDEX idx_emp_dept_age ON emp;
```

SHOW INDEX 里联合索引会显示多行，Seq_in_index 依次表示字段顺序，不是建了多个独立索引。Index_type 显示的 BTREE 是 MySQL 的类型名称，InnoDB 的实际结构按 B+ 树理解。

唯一索引写成 `CREATE UNIQUE INDEX ...`，创建前要先检查现有数据是否满足唯一性。主键和 UNIQUE 约束已经隐含相应的索引，别再在同样的列上机械地重复建一个。

## 树高估算只是数量级解释

假设一页约 16 KiB，每个叶子页粗略放 16 条行记录，每个非叶子页大约有 1000 个子页位置。那么两层树能放约 1.6 万行，三层约 1600 万行。扇出高的结构，用较少的层数就能管理大量记录。

实际的页里还有页头、记录头、目录、剩余空间这些开销，键长、行长、填充程度和页大小都会改变容量。所以不能保证“所有表三层必定能放 2200 万行”，也别把某个固定行数当成必须分库分表的阈值。

主键越长，各个二级索引携带的主键信息通常也越大；索引越多，每次插入、删除要维护的结构也越多。后面设计索引时，读路径和写放大要一起考虑。

写成一般式：内部页平均能指向 F 个子页，叶子页平均放 R 行，根到叶子有 h 层，容量大致按 `F^(h-1) × R` 增长。取 F=1000、R=16：一层只有叶子，约 16 行；两层约 16000 行；三层约 16000000 行。多一层，容量就可能扩大很多倍。

但 F 和 R 都不是固定的业务常量：主键变长，同一页能放的导航信息就少了；一行变宽，叶子容量就小了；页没填满，有效容量也会降低。“树矮”说明了它为什么适合在大量数据里查找，但给不出一个哪张表都适用的精确容量承诺。
