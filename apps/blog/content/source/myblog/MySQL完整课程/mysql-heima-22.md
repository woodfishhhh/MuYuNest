备份要求多张表来自一致的状态，改表结构要求没有其他操作继续依赖旧结构。这两类问题保护的对象不同，因此不能只用“数据库被锁了”解释。排查时先看等待的是哪一种锁，再找持锁连接。

## 一致性备份为什么需要协调写入

假设下单操作先扣库存，再写订单和订单日志。如果备份先读到扣减前的库存，随后又读到已生成的订单，恢复后就会出现“有订单但库存没扣”的状态。即使每张表单独导出都成功，这组文件也不一定共同一致。

全局读锁可以限制实例上的相关写入与结构变更，为备份建立一个稳定窗口。它的影响范围很大，下面只作为独立实验实例的操作顺序：

```sql
-- 连接 A，保持连接，直到备份结束
FLUSH TABLES WITH READ LOCK;
-- 另一个终端完成备份后，再回到 A
UNLOCK TABLES;
```

备份工具在操作系统终端中运行，不在 mysql> 内执行。例如 PowerShell：

```powershell
mysqldump -h 127.0.0.1 -u root -p --skip-lock-tables --databases mysql_notes --result-file=D:/mysql-lab/mysql_notes.sql
```

这里假设目录已存在，连接 A 的全局读锁覆盖整个导出过程。`--result-file` 让工具直接写文件，减少 shell 重定向编码差异。备份失败时也要回到 A 释放锁，不能把业务一直留在等待状态。全局读锁的获得本身也可能等待，不能把命令刚发出当作已经持锁。

对 InnoDB 数据，常用一致性事务快照完成逻辑导出：

```powershell
mysqldump -h 127.0.0.1 -u root -p --single-transaction --routines --triggers --events --databases mysql_notes --result-file=D:/mysql-lab/mysql_notes.sql
```

这通常无需为整个导出期间持有全局读锁，但一致性保证有条件：非事务表不受同样快照保护，导出期间的并发 DDL 也会破坏假设。是否还需要日志坐标、GTID 信息和额外锁，要按恢复或复制目标配置。备份是否可用最终需要在隔离目标中恢复并检查，文件存在只是第一步。

备份为什么必须关注“同一个时刻”，可以把前面的例子列成时间线。导出工具先读库存，此时订单事务还没提交；订单事务接着完成扣库存、写订单并提交；导出工具随后读订单。这样导出的库存来自提交前，订单来自提交后，文件中的两部分从未在数据库里共同构成一个完整已提交状态。

全局读锁的思路是让相关写入暂时不能推进，给导出一个稳定窗口。一致性事务快照的思路则是让导出始终按同一个可见性边界读取：即使期间有事务提交，后面的表也不能随意换成更新的时间点。这两种方式都在解决跨表状态协调，但对并发写入的影响不同。

这也解释了为何对单张表执行成功的 SELECT 不足以证明整次备份一致。每次查询各自都可以读到合法结果，问题出在这些结果是否来自相容的整体状态。恢复测试必须检查库存与订单等关系，不能只看每张表都存在。

## 显式表锁限制整张表的访问

`LOCK TABLES 表 READ` 加表读锁，`WRITE` 加表写锁，`UNLOCK TABLES` 释放。以已有 score 为实验表，两个独立连接可观察：

| 连接 A 的操作 | A 自己 | 连接 B |
| --- | --- | --- |
| `LOCK TABLES score READ` | 可以读，不能写该表 | 可以读，写入等待 |
| `LOCK TABLES score WRITE` | 可以读写该表 | 读写该表都会等待 |

每轮结束由 A 执行 UNLOCK TABLES，再结束 B 的实验操作。表锁持有期间，持锁连接对其他未锁定表的访问也受规则约束；LOCK TABLES 还涉及事务提交语义，不应随便插到普通 InnoDB 业务事务中。

这个表里的“读被挡住”是显式 WRITE 表锁的行为，不能套用到所有行级排他锁上。InnoDB 的普通快照读往往可以读取旧版本，而不等待另一个事务的行写锁。

观察表锁时要把“等待”与“报错”分开。A 持 READ 锁后自己尝试写同一表，可能直接收到不允许该操作的错误；B 发送写入则可能停在等待，直到 A 释放锁。B 的终端没有立即返回，并不表示命令丢失了；它可能正在排队，A 一释放锁就会继续执行。

因此实验结束时，不能只关闭一个观察窗口就认为全部写入已取消。应确认等待中的语句是否已经完成，并在相应连接结束事务。想保留原始练习数据时，先设计用哪些记录测试、执行后怎样回滚，再开始制造等待。

## 元数据锁保护的是表定义

元数据包含列、索引和表定义。连接 A 开启事务并读取 score 后，它仍可能继续使用这张表，因此不能让连接 B 随意替换其结构。

```sql
-- A
START TRANSACTION;
SELECT id,name FROM score;
```

```sql
-- B：在独立实验中执行，可能等待 A 结束
ALTER TABLE score ADD COLUMN note VARCHAR(100);
```

A 提交或回滚后，B 才有机会完成所需的元数据锁阶段。具体在线 DDL 会使用多个锁阶段，不能把所有 ALTER 的全过程简单描述成始终持同一种排他锁。

有权限的观察连接可以检查：

```sql
SELECT OBJECT_SCHEMA,OBJECT_NAME,LOCK_TYPE,LOCK_DURATION,LOCK_STATUS,OWNER_THREAD_ID
FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA='mysql_notes';
```

LOCK_STATUS 区分已持有和等待。SELECT 通常需要相容的元数据访问锁，DML 也需要相应元数据锁；“普通 SELECT 不加行锁”并不等于“它完全不持有任何锁”。长时间不结束的只读事务也可能挡住 DDL，等待中的 DDL 又可能影响后续访问。

A 的 SELECT 结果已经返回，为什么还会挡住 B 的 ALTER？因为 SELECT 属于仍未结束的事务，A 后面还可能再次访问这张表。服务器需要维持这个事务对表定义的合法使用，相关 MDL 可以持续到事务结束，而不是随着结果网格显示完就立即全部释放。

这也是排查长事务的重要线索。一个连接看起来没有正在执行耗时 SQL，却可能持有早先取得的锁。检查当前语句之外，还要看连接是否开着事务、何时开始，以及它仍持有哪个对象的元数据锁。只盯住那条等待的 ALTER，可能找不到真正让它不能推进的连接。

## 意向锁把行锁意图提升到表级表达

当事务准备对某些记录加共享锁或排他锁时，会先取得对应表上的意向锁。IS 表示意向共享，IX 表示意向排他。它们让需要整表锁的操作能在表级检查兼容性，而不必逐行扫描锁状态。

| 请求与已有锁 | IS | IX | 表级 S | 表级 X |
| --- | --- | --- | --- | --- |
| IS | 兼容 | 兼容 | 兼容 | 冲突 |
| IX | 兼容 | 兼容 | 冲突 | 冲突 |

IS/IX 之间兼容，不代表它们各自涉及的行锁一定兼容。两个事务可以同时持 IX，分别修改不同员工；如果同时修改同一员工，记录锁仍会冲突。

意向锁由 InnoDB 管理，业务不需要手动调用“加 IX”命令。观察记录锁和意向锁用 `performance_schema.data_locks`，观察元数据锁用 metadata_locks，不能把两张表的结果混成一类。

可以从整表排他请求反推意向锁的意义。A 已经锁住表中一条记录准备更新，B 想取得与这种访问不兼容的整表排他锁。如果没有表级的意向信息，B 需要确认表里是否存在各种记录锁；有了 IX，就能先在表级知道“有人正在使用行级排他访问”，直接按兼容规则等待。

IX 本身并没有宣称“我独占整张表”，所以 A 和 C 可以各持 IX、分别修改不同记录。真正决定它们能否同时更新某一行的是记录锁。把 IX 当成整表写锁，就会错误地推导出所有 UPDATE 必须串行。
