备份要求多张表来自同一个一致的状态；改表结构要求没有别的操作还在用旧结构。这两种锁保护的东西不一样，别一概说成"数据库被锁了"。排查时先看在等哪种锁，再找是哪个连接持有它。

## 一致性备份为什么需要协调写入

假设下单是先扣库存，再写订单和订单日志。如果备份先读到扣减前的库存，后面又读到已经生成的订单，恢复后就会出现"有订单但库存没扣"。每张表单独导出都成功，合起来也不一定一致。

全局读锁可以挡住实例上的写入和结构变更，给备份一个稳定的时间窗口。它影响范围很大，下面只当作独立实验实例上的操作顺序：

```sql
-- 连接 A，保持连接，直到备份结束
FLUSH TABLES WITH READ LOCK;
-- 另一个终端完成备份后，再回到 A
UNLOCK TABLES;
```

备份工具在操作系统终端里跑，不是在 mysql> 里执行。比如 PowerShell：

```powershell
mysqldump -h 127.0.0.1 -u root -p --skip-lock-tables --databases mysql_notes --result-file=D:/mysql-lab/mysql_notes.sql
```

这里假设目录已经存在，连接 A 的全局读锁覆盖整个导出过程。`--result-file` 让工具直接写文件，少了 shell 重定向的编码问题。备份失败也要回到 A 把锁释放掉，别让业务一直卡着。加全局读锁本身也可能要等，命令发出去不代表已经拿到锁。

InnoDB 数据常用一致性事务快照做逻辑导出：

```powershell
mysqldump -h 127.0.0.1 -u root -p --single-transaction --routines --triggers --events --databases mysql_notes --result-file=D:/mysql-lab/mysql_notes.sql
```

这样一般不用在整个导出期间持有全局读锁，但有前提：非事务表不受快照保护，导出期间有并发 DDL 也会出问题。要不要日志坐标、GTID 信息和额外的锁，看恢复或复制的需要。备份能不能用，最终要在隔离环境里恢复一遍检查，文件生成只是第一步。

为什么备份要盯着"同一个时刻"，把上面的例子按时间排一下：导出工具先读库存，这时订单事务还没提交；订单事务接着扣库存、写订单、提交；导出工具再读订单。结果导出的库存是提交前的，订单是提交后的，这两部分在数据库里从来没有同时存在过。

- 全局读锁：让相关写入暂时停下，给导出一个稳定窗口。
- 一致性快照：导出全程按同一个时间点的可见性来读，期间就算有事务提交，后面的表也不会换成更新的版本。

两种都是解决跨表一致，对并发写入的影响不同。

所以单张表的 SELECT 成功，证明不了整次备份是一致的。每次查询各自都能读到合法结果，问题在于这些结果是不是来自同一个整体状态。恢复测试要检查库存和订单这类关系，不能只看每张表都在。

## 显式表锁限制整张表的访问

`LOCK TABLES 表 READ` 加表读锁，`WRITE` 加表写锁，`UNLOCK TABLES` 释放。拿已有的 score 当实验表，开两个连接观察：

| 连接 A 的操作 | A 自己 | 连接 B |
| --- | --- | --- |
| `LOCK TABLES score READ` | 可以读，不能写该表 | 可以读，写入等待 |
| `LOCK TABLES score WRITE` | 可以读写该表 | 读写该表都会等待 |

每轮结束由 A 执行 UNLOCK TABLES，再结束 B 的操作。持有表锁期间，持锁连接访问其他没锁的表也受限制；LOCK TABLES 还牵涉事务提交，别随手插进普通的 InnoDB 业务事务里。

表里"读被挡住"是显式 WRITE 表锁的行为，不能套到所有行级排他锁上。InnoDB 普通的快照读一般能读旧版本，不用等别的事务的行写锁。

观察表锁时，"等待"和"报错"要分开看。A 持 READ 锁后自己去写同一张表，可能直接报错，不允许这个操作；B 去写则可能一直等，直到 A 释放锁。B 的终端没返回不代表命令丢了，它可能在排队，A 一释放就会继续执行。

所以实验结束时，别以为关掉一个窗口所有写入就都取消了。要确认在等的语句有没有执行完，并在对应连接里结束事务。想保留原始练习数据的话，先想好用哪些记录测试、测完怎么回滚，再去制造等待。

## 元数据锁保护的是表定义

元数据就是列、索引、表定义这些。连接 A 开了事务并读过 score 后，它可能还会继续用这张表，所以不能让连接 B 随便改表结构。

```sql
-- A
START TRANSACTION;
SELECT id,name FROM score;
```

```sql
-- B：在独立实验中执行，可能等待 A 结束
ALTER TABLE score ADD COLUMN note VARCHAR(100);
```

A 提交或回滚后，B 才能拿到需要的元数据锁。在线 DDL 实际会分好几个锁阶段，不是所有 ALTER 全程都持同一种排他锁。

有权限的连接可以这样查看：

```sql
SELECT OBJECT_SCHEMA,OBJECT_NAME,LOCK_TYPE,LOCK_DURATION,LOCK_STATUS,OWNER_THREAD_ID
FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA='mysql_notes';
```

LOCK_STATUS 区分已持有和等待中。SELECT 一般要拿相容的元数据锁，DML 也要拿对应的元数据锁，"普通 SELECT 不加行锁"不代表它什么锁都不持有。一直不结束的只读事务也可能挡住 DDL，而等着的 DDL 又可能挡住后面的访问。

A 的 SELECT 结果都返回了，为什么还挡着 B 的 ALTER？因为这个 SELECT 所在的事务还没结束，A 之后还可能再访问这张表。服务器要保证这个事务能正常使用表定义，相关的 MDL 会一直持有到事务结束，而不是结果显示完就全部释放。

这也是排查长事务的重要线索：一个连接看起来没在跑耗时的 SQL，但可能还持有之前拿到的锁。除了看当前语句，还要看连接有没有开着事务、什么时候开的、还持有哪些对象的元数据锁。只盯着那条在等的 ALTER，可能找不到真正卡住它的连接。

## 意向锁把行锁意图提升到表级表达

事务要给某些记录加共享锁或排他锁之前，会先在表上加对应的意向锁：IS 是意向共享，IX 是意向排他。有了它，要加整表锁的操作在表级就能检查兼容性，不用逐行扫描锁状态。

| 请求与已有锁 | IS | IX | 表级 S | 表级 X |
| --- | --- | --- | --- | --- |
| IS | 兼容 | 兼容 | 兼容 | 冲突 |
| IX | 兼容 | 兼容 | 冲突 | 冲突 |

IS/IX 之间互相兼容，但它们背后的行锁不一定兼容。两个事务可以同时持有 IX，分别改不同的员工；同时改同一个员工，记录锁照样冲突。

意向锁由 InnoDB 自己管理，业务不用手动"加 IX"。看记录锁和意向锁用 `performance_schema.data_locks`，看元数据锁用 metadata_locks，别把两张表的结果混在一起。

反过来想想意向锁有什么用：A 已经锁住表里一条记录准备更新，B 想拿一个和它冲突的整表排他锁。没有表级的意向信息，B 得去确认表里有没有各种记录锁；有了 IX，在表级就知道"有人在用行级排他访问"，直接按兼容规则等待。

IX 本身并不表示独占整张表，所以 A 和 C 可以各自持有 IX、分别改不同的记录。真正决定它们能不能同时改某一行的是记录锁。把 IX 当成整表写锁，就会推出所有 UPDATE 都得串行这种错误结论。
