## 从一条查询看路由与合并

沿用状态枚举分片：状态 1 在节点 0，状态 2 在节点 1，状态 3 在节点 2。

```sql
SELECT id,status FROM tb_user WHERE status IN (1,3) ORDER BY id;
```

Mycat 先解析逻辑表和条件，查到分片字段为 status，再根据 1、3 找到两个目标节点。后端返回的记录还需要按 id 形成全局顺序，之后才能交给客户端。

若去掉 WHERE，代理无法根据状态排除节点，就需要访问全部分片。若改为按非分片字段过滤，通常也不能仅凭这个字段推断目标分片。

课程将排序描述为“只能在 Mycat 做，后端排序没有意义”，这个说法过于绝对。各片局部有序，可以成为代理归并全局有序结果的基础；需要强调的是，仅有各片的局部顺序，不足以代表整个结果集的顺序。没有 ORDER BY 时，也不要依赖本次恰好按节点顺序拼接的输出。

跨片分页同样不能让每片各自取第 101–120 行，再把结果拼起来。全局位置需要考虑所有目标分片的数据，所以大偏移量分页可能让代理和后端共同处理大量记录。这也说明单机索引优化和分片路由优化要一起看。

跨片聚合也需要保留正确的中间信息。用已有八名员工说明，假设只为理解计算过程按 id%3 分组：下标 0 的两人总工资 19000，下标 1 的三人总工资 37000，下标 2 的三人总工资 31000。整体平均工资应为 `(19000+37000+31000)/(2+3+3)=10875`。

若先算各片平均值，再把三个平均值等权相加除以 3，就把两人的分片和三人的分片赋予同样权重，得不到上述结果。因此代理要处理的不是简单“把三行平均值再 AVG 一次”，而是按聚合语义取得足够的总和与数量。这个例子解释合并原理，不代表当前基础员工表已经实际迁移到 Mycat。

排序同样要求全局比较。第一片最小 id 不一定小于第二片最小 id，不能把第一片全部结果放完再追加第二片，就声称已经按 id 排序。各片有序时可以归并，只有拿到并比较各片的候选头部，才能决定全局下一条是谁。

## 数据端口与管理端口分工不同

课程使用默认端口 8066 执行业务 SQL，9066 查看和管理 Mycat。本机实际端口以 `server.xml` 为准。

```bash
mysql -h MYCAT_HOST -P 9066 -u MYCAT_ADMIN -p
```

进入管理端后，先查询该版本支持的指令：

```sql
SHOW @@HELP;
SHOW @@VERSION;
SHOW @@DATASOURCE;
SHOW @@DATANODE;
SHOW @@THREADPOOL;
SHOW @@SQL;
SHOW @@SQL.SUM;
```

`DATASOURCE` 对应实际后端连接，`DATANODE` 对应逻辑节点与物理库映射。查这两者，可以发现“逻辑节点名字正确，但连到了错误数据库”的问题。线程池反映请求处理资源，SQL 统计则用来定位最近执行的语句和耗时。统计是否可见还取决于该版本的统计开关及采集条件，空列表不等于没有业务请求。

可以在 8066 连接中执行一条带明确表名和条件的查询，再回到 9066 看统计是否增加。比较时记录执行时间和用户，不要只凭一条相似的 SQL 就认定是刚才的请求。

用管理输出定位请求时，可以先画一条预期路径：某个带分片条件的 SELECT，应该进入哪个 dataNode；这个 dataNode 应关联哪个 dataHost 和物理库；该物理主机上的读计数是否变化。名字、连接目标和统计三者对不上，说明至少有一层需要继续排查。

如果 SQL 解析页显示命中三片，而业务本来只想查一片，先检查条件是否真的包含分片字段，值的类型是否符合规则，再看算法是否能从该条件推出节点。不要在尚未确定路由范围前，就只给每个后端增加相同索引并期待消除所有跨片成本。

## 配置重载需要验证具体变更

课程通过管理命令 `RELOAD @@CONFIG` 让新增逻辑表出现在数据端。它说明部分配置可以重载，不代表每个参数都能热更新。

执行前保存当前配置，按 `SHOW @@HELP` 核对该版本的重载命令与范围。重载后检查返回结果、日志以及数据端的实际行为。新增逻辑表能被 `SHOW TABLES` 列出，只验证了配置识别；仍需检查后端物理表、权限和实际读写。

修改已有表的分片函数尤其不能以“重载成功”为终点。新函数可能把旧键指向另一台机器，必须先安排迁移和切换方案。

例如修改 table 的 dataNode 后，SHOW TABLES 仍可能显示同一个表名，完全看不出路由已经变化。需要再执行带代表性主键的查询，观察其目标节点，并直连确认记录位置。相反，只新增一张逻辑表的名字，也不会因为管理命令返回成功就自动拥有原本不存在的业务数据。

因此配置验收至少要对应到本次修改的行为：改权限就测试被允许与被拒绝的操作，改节点就核对路由，改分片规则就测试边界键。重载成功只是服务器接受了某种配置更新，不是这些行为已经全部得到证明。

## 图形监控怎样接起来

课程的 Mycat-web（界面显示 Mycat-eye）使用 ZooKeeper 保存相关配置，提供 Mycat、JVM、物理节点和 SQL 的图形监控。它是独立服务，不是启动 Mycat 后自然出现的页面。

课程安装包和独立安装文档没有包含在此次拿到的字幕材料中，因此这里保留可复核的安装流程，不虚构下载地址或声称当前包仍与旧界面相同。若已有课程配套包，应在隔离 Linux 环境中按以下顺序操作：

1. 检查两份压缩包的来源和目录结构，分别解压到独立目录。先确认 Java 与对应旧版软件兼容，不覆盖已有服务目录。
2. 在 ZooKeeper 目录创建持久数据目录，将 `conf/zoo_sample.cfg` 复制为 `conf/zoo.cfg`，把 `dataDir` 改为该数据目录的绝对路径。课程单机演示保留 `clientPort=2181`。
3. 在 ZooKeeper 根目录执行 `bin/zkServer.sh start`，再执行 `bin/zkServer.sh status`。课程单机模式预期为 `standalone`；报错时先查进程、端口、Java 与日志，不能只看启动命令是否返回。
4. 在 Mycat-web 包内找到 `mycat.properties`，核对 ZooKeeper 地址。课程包默认连接 `localhost:2181`，只在它与 ZooKeeper 同机时成立。按包内实际配置键修改，不猜测属性名。
5. 从 Mycat-web 根目录执行课程提供的 `sh start.sh`，查看日志；课程通过 `http://服务器地址:8082/mycat` 访问。实际端口和上下文路径以手中的发行包为准。
6. 在服务管理页面添加 Mycat 地址、管理端口 9066、数据端口 8066、已有逻辑库以及有权访问它的账户。页面能打开只说明 Web 服务可访问，连接成功后才有条件采集 Mycat 数据。

随后在数据端执行可识别的查询，选对监控时间范围，再检查 SQL 列表、次数和响应时间。课程还演示了“SQL 解析”页面，用来观察 SQL 被路由到哪些节点。状态等于 1 应只命中第一片，状态属于 1、3 应命中第一、第三片；无分片条件则会扩大路由范围。

如果解析结果被追加 `LIMIT 100`，先检查逻辑库的 `sqlMaxLimit`，不要把它误认为用户原始 SQL。监控页面也可能滞后采集；将时间范围、代理统计与后端执行证据对齐，才能判断请求走向。
