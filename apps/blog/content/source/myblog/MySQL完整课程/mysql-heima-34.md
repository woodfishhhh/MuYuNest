应用拿到了正确结果，不代表查询只访问了必要的节点，也不代表中间件没成为瓶颈。Mycat 的管理端口和图形监控能帮你搞清楚：SQL 发给了谁、跑了多久、连接和线程有没有堵。

## 从一条查询看路由与合并

接着用状态枚举分片：状态 1 在节点 0，状态 2 在节点 1，状态 3 在节点 2。

```sql
SELECT id,status FROM tb_user WHERE status IN (1,3) ORDER BY id;
```

Mycat 先解析逻辑表和条件，查到分片字段是 status，再按 1、3 找到两个目标节点。后端返回的记录还要按 id 排成全局顺序，才能交给客户端。

去掉 WHERE 的话，代理没法按状态排除节点，就要访问全部分片。改成按非分片字段过滤，一般也推不出目标分片。

课程说排序"只能在 Mycat 做，后端排序没意义"，这话太绝对了。各片局部有序，正好可以让代理归并出全局有序的结果；要强调的是，只有各片的局部顺序，代表不了整个结果集的顺序。没写 ORDER BY 的话，也别依赖这次碰巧按节点顺序拼出来的输出。

跨片分页也不能让每片各取第 101–120 行再拼起来。全局位置要考虑所有目标分片的数据，所以大偏移量分页可能让代理和后端一起处理大量记录。单机的索引优化和分片的路由优化要放在一起看。

跨片聚合要保留正确的中间信息。拿已有的八名员工举例，假设按 id%3 分组（只为说明计算过程）：下标 0 的两人总工资 19000，下标 1 的三人总工资 37000，下标 2 的三人总工资 31000。整体平均工资是 `(19000+37000+31000)/(2+3+3)=10875`。

要是先算各片平均值，再把三个平均值加起来除以 3，就等于给两人的分片和三人的分片同样的权重，结果就不对了。所以代理要按聚合语义拿到足够的总和和数量，不是把三个平均值再 AVG 一次。这个例子讲的是合并原理，不代表当前员工表已经迁到了 Mycat。

排序也要全局比较。第一片最小的 id 不一定比第二片最小的 id 小，不能把第一片全放完再接第二片就说排好序了。各片有序时可以归并：拿到各片的候选头部比较，才能决定全局下一条是谁。

## 数据端口与管理端口分工不同

课程用默认端口 8066 执行业务 SQL，9066 查看和管理 Mycat。本机的实际端口以 `server.xml` 为准。

```bash
mysql -h MYCAT_HOST -P 9066 -u MYCAT_ADMIN -p
```

进入管理端后，先查这个版本支持哪些指令：

```sql
SHOW @@HELP;
SHOW @@VERSION;
SHOW @@DATASOURCE;
SHOW @@DATANODE;
SHOW @@THREADPOOL;
SHOW @@SQL;
SHOW @@SQL.SUM;
```

- `DATASOURCE`：实际的后端连接
- `DATANODE`：逻辑节点和物理库的映射

查这两个，能发现"逻辑节点名对了，却连到了错的数据库"这种问题。线程池反映请求处理资源，SQL 统计用来找最近执行的语句和耗时。统计能不能看到还取决于版本的统计开关和采集条件，列表为空不代表没有业务请求。

可以在 8066 的连接里执行一条带明确表名和条件的查询，再回 9066 看统计有没有增加。比对时记下执行时间和用户，别凭一条相似的 SQL 就认定是刚才那个请求。

用管理输出定位请求时，先画出预期路径：某个带分片条件的 SELECT 应该进哪个 dataNode，这个 dataNode 关联哪个 dataHost 和物理库，那台物理主机的读计数有没有变。名字、连接目标、统计三者对不上，说明至少有一层还要接着查。

SQL 解析页显示命中了三片，而业务本来只想查一片：先查条件里到底有没有分片字段、值的类型符不符合规则，再看算法能不能从这个条件推出节点。路由范围还没搞清楚之前，别急着给每个后端加一样的索引，指望消掉所有跨片开销。

## 配置重载需要验证具体变更

课程用管理命令 `RELOAD @@CONFIG` 让新加的逻辑表出现在数据端。这说明部分配置能重载，不代表每个参数都能热更新。

执行前先保存当前配置，用 `SHOW @@HELP` 核对这个版本的重载命令和范围。重载后看返回结果、日志和数据端的实际行为。新加的逻辑表能被 `SHOW TABLES` 列出来，只验证了配置被识别；后端的物理表、权限和实际读写还要另外查。

改已有表的分片函数，更不能以"重载成功"收尾。新函数可能把旧键指到另一台机器，得先安排好迁移和切换方案。

比如改了 table 的 dataNode，SHOW TABLES 可能还是显示同一个表名，完全看不出路由已经变了。要再用有代表性的主键查一下，看它去了哪个节点，并直连确认记录位置。反过来，只新加一个逻辑表名，也不会因为管理命令返回成功就凭空有了业务数据。

所以配置验收要对应到这次改的行为：

- 改权限：测试允许的操作和被拒绝的操作
- 改节点：核对路由
- 改分片规则：测试边界键

重载成功只说明服务器接受了配置更新，不代表这些行为都已经验证过了。

## 图形监控怎样接起来

课程的 Mycat-web（界面上显示 Mycat-eye）用 ZooKeeper 存相关配置，提供 Mycat、JVM、物理节点和 SQL 的图形监控。它是独立的服务，不是启动 Mycat 就自带的页面。

这次拿到的字幕材料里没有课程安装包和独立的安装文档，所以这里只保留能复核的安装流程，不编下载地址，也不保证现在的包和旧界面一样。手上有课程配套包的话，在隔离的 Linux 环境里按这个顺序来：

1. 检查两个压缩包的来源和目录结构，分别解压到独立目录。先确认 Java 和对应的旧版软件兼容，别覆盖已有的服务目录。
2. 在 ZooKeeper 目录建一个持久的数据目录，把 `conf/zoo_sample.cfg` 复制成 `conf/zoo.cfg`，`dataDir` 改成这个数据目录的绝对路径。课程单机演示保留 `clientPort=2181`。
3. 在 ZooKeeper 根目录执行 `bin/zkServer.sh start`，再执行 `bin/zkServer.sh status`。课程单机模式预期是 `standalone`；报错就先查进程、端口、Java 和日志，别只看启动命令有没有返回。
4. 在 Mycat-web 包里找到 `mycat.properties`，核对 ZooKeeper 地址。课程包默认连 `localhost:2181`，只有和 ZooKeeper 在同一台机器上才成立。按包里实际的配置键改，别猜属性名。
5. 在 Mycat-web 根目录执行课程提供的 `sh start.sh`，看日志；课程通过 `http://服务器地址:8082/mycat` 访问。实际端口和上下文路径以手上的发行包为准。
6. 在服务管理页面添加 Mycat 地址、管理端口 9066、数据端口 8066、已有的逻辑库和有权限访问它的账户。页面能打开只说明 Web 服务能访问，连接成功后才可能采集到 Mycat 的数据。

然后在数据端执行一条能认出来的查询，选对监控的时间范围，再看 SQL 列表、次数和响应时间。课程还演示了"SQL 解析"页面，看 SQL 被路由到哪些节点：状态等于 1 应该只命中第一片，状态属于 1、3 应该命中第一、第三片；没有分片条件就会扩大路由范围。

解析结果里被加了 `LIMIT 100` 的话，先查逻辑库的 `sqlMaxLimit`，别以为是用户原来的 SQL。监控页面也可能延迟采集；把时间范围、代理统计和后端执行情况对齐，才能判断请求走了哪里。
