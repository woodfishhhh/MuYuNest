建表定义了每一列能存什么，`INSERT` 才把记录放进去。查询、分组和连接都要建立在确定的数据上，因此后续基础示例统一使用 `mysql_notes.emp`。这份八人数据集是为贯通练习重建的教学数据，沿用部分课程角色；字段值与人数不声称逐项复原视频中的表。

## 插入值必须与列对应

为了不改动上述数据，增删改练习使用一张副表：

```sql
USE mysql_notes;
CREATE TABLE employee_edit LIKE emp;
INSERT INTO employee_edit (id, work_no, name, gender, age, entry_date)
VALUES
  (101, '00101', '小昭', '女', 18, '2024-01-01'),
  (102, '00102', '杨逍', '男', 40, '2020-05-01');
SELECT id, work_no, name, age FROM employee_edit ORDER BY id;
```

`CREATE TABLE ... LIKE` 复制表结构，不复制表中数据。`INSERT` 后的列名决定值的对应关系：101 对应 id，`'00101'` 对应 work_no。每组括号是一行，两组之间用逗号分隔。字符串和日期用引号包围，`NULL` 不加引号；`'NULL'` 是四个字母组成的字符串。

省略列名的 `INSERT INTO employee_edit VALUES (...)` 要提供与表结构顺序匹配的所有值。表结构一改，旧语句就可能出错，所以通常显式列出需要写入的列。

未列出的可空字段采用默认值；这里 `salary` 等列默认为 `NULL`。如果漏掉没有默认值的非空字段，严格模式下会报错。向无符号年龄写入 -1、写入过长字符串或重复主键也会失败；不要靠关闭严格模式掩盖数据错误。

可以把 INSERT 的列和值竖着对齐，检查是否真的写对：

| 列名 | 第一行输入 | 写入后的含义 |
| --- | --- | --- |
| id | 101 | 这条记录的编号 |
| work_no | `'00101'` | 保留五位格式的工号 |
| name | `'小昭'` | 员工姓名 |
| gender | `'女'` | 本例的性别值 |
| age | 18 | 数值年龄 |
| entry_date | `'2024-01-01'` | 按 DATE 类型解析的日期 |

若把姓名和年龄两个值交换，而列名顺序不改，服务器不会根据“这看起来像姓名”帮你自动纠正。它仍按位置把值交给列，再检查能否转换、是否符合约束。因此插入错误先检查列数、对应顺序和类型，再检查重复键与非空要求。

多行 INSERT 仍是一条 SQL，不是多个独立的输入框。对本例 InnoDB 表，普通 INSERT 的一行发生重复主键等错误，通常会使这条语句失败。不要看到前面几组值格式正确，就认为它们肯定已经保存。执行后用主键查询实际结果，比只看编辑器里哪些行被选中更可靠。

## 更新修改字段，删除移除整行

```sql
UPDATE employee_edit
SET name = '小昭同学', age = 19
WHERE id = 101;

DELETE FROM employee_edit WHERE id = 102;

SELECT id, name, age FROM employee_edit ORDER BY id;
```

预期只剩 `101, 小昭同学, 19`。`SET` 决定改哪些列，`WHERE` 决定改哪些行；多个赋值用逗号分隔。没有 `WHERE` 就会更新或删除整张表的数据。

若只想清空某列，用 `UPDATE ... SET salary = NULL`，前提是该列允许为空。`DELETE` 的粒度是行，不存在“用 DELETE 删除一行里的某个字段值”的写法。删除列则是 DDL 的 `ALTER TABLE ... DROP COLUMN`，含义完全不同。

修改前可以先执行同条件的 `SELECT`，核对目标行。客户端的“影响行数”也要结合连接选项和实际修改理解，不应一律等同于匹配行数。

## SELECT 决定返回什么，WHERE 决定保留谁

```sql
SELECT name, work_no, age FROM emp;
SELECT work_address AS 工作地址 FROM emp;
SELECT DISTINCT work_address FROM emp;
```

第一句只返回三列，第二句给结果列起别名，不修改表里的字段名。第三句去除结果中的重复地址，得到北京、上海、西安、天津四种值；没有排序时，不保证出现顺序。

`DISTINCT` 作用于整个选择列表。例如 `SELECT DISTINCT work_address, gender` 去重的是“地址和性别”的组合，不能理解成只对地址去重。`SELECT *` 适合临时查看，业务查询应明确字段，避免取回用不上的大列及表结构变化带来的影响。

条件查询的基本形状是：

```sql
SELECT id, name, age
FROM emp
WHERE age BETWEEN 18 AND 20
ORDER BY id;
```

结果是 id 1、2、3、7。`BETWEEN 18 AND 20` 包含两端，相当于 `age >= 18 AND age <= 20`。反写成 `BETWEEN 20 AND 18` 不会自动交换边界。

| 需求 | 条件 | 在初始数据中的结果 |
| --- | --- | --- |
| 年龄等于 88 | `age = 88` | 张三丰 |
| 年龄不等于 88 | `age <> 88` 或 `age != 88` | 其余 7 人 |
| 年龄在给定列表中 | `age IN (18,20,40)` | 柳岩、张无忌、周芷若、赵敏 |
| 女性且小于 25 岁 | `gender='女' AND age<25` | 柳岩、周芷若、赵敏 |
| 姓名恰好两个字符 | `name LIKE '__'` | 柳岩、灭绝、赵敏 |
| 证件串以 X 结尾 | `id_card LIKE '%X'` | 胡青牛 |

`LIKE` 中 `_` 匹配一个字符，`%` 匹配零个或多个字符。`'%张%'` 是包含张，`'张%'` 是以张开头。它们不等价。是否区分英文大小写，还取决于字符串的排序规则。

多个条件混用 `AND`、`OR` 时，用括号写清业务含义：

```sql
SELECT name FROM emp
WHERE gender = '女' AND (age = 18 OR age = 20);
```

它要求女性同时满足两个年龄之一。若省略括号，`AND` 比 `OR` 优先，年龄 20 的男性也可能被选中。

WHERE 可以按逐行判断理解。对于 `gender='女' AND (age=18 OR age=20)`，柳岩先满足女性，再满足年龄 20，所以保留；张无忌虽满足年龄 18，却不满足女性，所以排除；灭绝满足女性，但年龄既不是 18 也不是 20，所以排除。括号内部先给出年龄选择，AND 再把它与性别要求合在一起。

查询也可以从中文需求逐步写出来。例如“找北京、20 岁以下的员工，只展示姓名和入职日期”，先确定数据来自 emp，再把两个条件用 AND 连接，最后决定展示列：

```sql
SELECT name,entry_date
FROM emp
WHERE work_address='北京' AND age<20
ORDER BY id;
```

初始表中只有张无忌符合。柳岩和赵敏恰好 20 岁，都被 `<20` 排除；若需求是“20 岁及以下”，应改为 `<=20`，这时有三个人。一个等号改变了业务边界，不能把它当作无关紧要的语法差异。

## NULL 表示缺少值，不是零或空字符串

```sql
SELECT name FROM emp WHERE id_card IS NULL;
SELECT name FROM emp WHERE id_card IS NOT NULL;
```

第一句返回周芷若，第二句返回其余 7 人。`id_card = NULL` 不会得到同样结果，因为普通比较遇到 NULL 得到“未知”，而 `WHERE` 只保留条件为真的行。`NULL <> 88` 同样不会变成真；如果年龄可能为空，查询“不是 88 或未填写”要写 `age <> 88 OR age IS NULL`。

这个规则也影响后面的聚合函数：统计员工总数与统计已填写证件的人数，是两个问题。

用三个表达式能看清差别：`0=0` 为真，`''=''` 为真，`NULL=NULL` 的结果仍是 NULL，表示未知。NULL 不是一种“特殊文字”，而是没有确定值。既然两边都没有确定值，就不能据此断定它们相等。

在复合条件里，未知也会继续参与判断。例如 `FALSE AND NULL` 已经能确定为假，因为左侧要求不成立；`TRUE OR NULL` 已经能确定为真，因为至少一个条件成立；但 `TRUE AND NULL` 仍不能确定为真。WHERE 只保留真，所以在筛选缺失值时要使用 `IS NULL`，不要依赖普通等号。

如果确实需要“两个值都缺失也视为相等”的比较，MySQL 还有 NULL 安全等号 `<=>`：`NULL <=> NULL` 返回 1，`1 <=> NULL` 返回 0。它适用于明确有这种语义的比较，不应拿来替换所有普通等号。
