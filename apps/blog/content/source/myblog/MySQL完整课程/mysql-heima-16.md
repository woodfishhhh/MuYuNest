写入性能受网络往返、事务提交影响，也受索引页维护影响。单条 INSERT 改成批量能减少往返，但批次无限放大，又会拉长持锁时间、增加日志和失败重试的成本。

## 批量语句与事务边界

```sql
CREATE TABLE batch_demo (id INT PRIMARY KEY,name VARCHAR(30)) ENGINE=InnoDB;
START TRANSACTION;
INSERT INTO batch_demo VALUES (1,'a'),(2,'b'),(3,'c');
INSERT INTO batch_demo VALUES (4,'d'),(5,'e');
COMMIT;
```

跟五次单行自动提交比，这里减少了语句往返和提交次数。复用连接时，单条 INSERT 也不是每条都重新建网络连接；省掉的一般是请求往返和反复提交这些成本。

批次多大，看行宽、包大小、事务日志、锁占用和超时。500～1000 行可以当作某些环境的试验起点，不是数据库的通用最优值。任何一步失败，应用都要回滚这一批，按明确的幂等策略重试。

一次写入的耗时可以拆成几段：客户端发请求、服务器执行并维护索引、事务提交的处理、返回结果。

- 五条记录合成一条多值 INSERT：减少一部分请求往返和语句处理
- 多条语句放进同一个事务：减少逐条提交的次数

两种优化作用在不同的地方，不能互相替代。

批次变大，失败的单位也跟着变大。一批写很久、中途出错，回滚和重试要处理的数据更多，事务持锁的时间也可能更长。可以先记录一批的实际条数、耗时和出错时的表现，再选合适的大小；不是 VALUES 越多就一定越快。

## LOAD DATA 读取的是数据文件

准备 UTF-8 文件 `D:/mysql-lab/batch.csv`，三行内容，不带表头：

```csv
11,Alice
12,Bob
13,Carol
```

文件放在运行 mysql 客户端的机器上。客户端和服务器都允许 LOCAL 加载时执行：

```sql
LOAD DATA LOCAL INFILE 'D:/mysql-lab/batch.csv'
INTO TABLE batch_demo
CHARACTER SET utf8mb4
FIELDS TERMINATED BY ','
OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\r\n'
(id,name);
SHOW WARNINGS;
SELECT * FROM batch_demo WHERE id>=11 ORDER BY id;
```

这里假设是 Windows 的 CRLF 换行；实际文件是 LF 的话改成 `\n`。预期新增 id 11、12、13。带 LOCAL 读的是客户端的文件；不带 LOCAL 读的是服务器上允许位置的文件，权限和 secure_file_priv 规则也不一样。

客户端用 `mysql --local-infile=1 -u 用户 -p` 开启对应功能，服务器允不允许由 local_infile 等配置决定。只对可信的连接和自己控制的输入开启，别为了一条示例就无条件去改共享实例的全局设置。

LOAD DATA 的分隔符、编码、列顺序、换行和转义，都是和输入文件约定好的格式。记录数增加了不代表内容全对，要检查警告、关键字段和坏行的处理；尤其 LOCAL 的某些错误处理行为和普通 INSERT 不一样。

文件位置特别容易弄反。在 Windows 上运行 mysql 客户端、连接 Linux 上的数据库时：

- 带 LOCAL：Windows 客户端读取文件并发送过去
- 不带 LOCAL：服务器去读 Linux 自己文件系统上的路径

把 Windows 的 D 盘路径发给 Linux 服务器，Linux 并不会因此能访问你的电脑。

分隔符决定怎么切列，换行符决定怎么切记录。示例 `11,Alice` 按逗号分成 id 和 name 两列；文件要是多了一行表头 `id,name` 又没声明跳过，第一行就不是本例合法的数字记录了。导入后既要查条数，也要查 id 和姓名，才能发现“列分错了但还是写进去了一些内容”的问题。

## 主键顺序为何影响页面维护

InnoDB 的聚簇索引按键组织记录。一直插入越来越大的自增键，一般集中写到右侧的叶子页；插入随机键则可能落到很多不同的页里。目标页空间不够时，就要分裂、移动部分记录，并维护父页和相邻页的关系。

顺序插入也可能分配或分裂页，只是局部性一般更好。随机插入也不是每次都分裂，实际怎么分裂也不能用一张固定的“一半对一半”的图来保证。

删除一般先打删除标记，旧版本清理掉后空间才可能复用；页的利用率降低时，InnoDB 可以尝试和相邻页合并。MERGE_THRESHOLD 控制合并阈值，默认常见是 50，但它是关于页面占用程度的规则，不是“删掉一半记录就立刻回收文件一半的磁盘空间”。

主键尽量稳定、紧凑，并且和生成方式匹配。BIGINT 自增在单库实验里很方便；随机 UUID 字符串可能更长，插入也缺乏局部性；分布式环境下也有有序标识、二进制 UUID 之类的设计，要按生成需求选，别一句“UUID 一律不好”就下结论。主键还会被二级索引携带，长度一增加，多棵索引都跟着变大。

这里的“按主键顺序”说的是索引记录的逻辑顺序，不要求磁盘上所有行永远紧挨着，页里会有空闲空间、分裂和相邻链接。假设一页快满了，里面的键是 10、20、30、40，这时插入 25，要在 20 和 30 之间安排位置，放不下就得调整页面内容和导航信息。插入 50 则更靠近当前的右边界，两者的局部访问模式不同。

删除也不是马上把那块空间从文件里剪掉。按事务可见性，旧的读事务可能还要看到被删记录的历史版本，之后清理和页面管理才有机会回收可用空间。所以删了大量行以后表文件没按同样比例变小，并不能直接说明 DELETE 没执行。

## UPDATE 的索引决定扫描与加锁范围

```sql
EXPLAIN UPDATE emp SET salary=salary+100 WHERE id=1;
EXPLAIN UPDATE emp SET salary=salary+100 WHERE name='柳岩';
```

主键等值定位一般能把扫描范围限得很小。条件没有可用的索引，UPDATE 就可能扫描并锁住大量索引记录，甚至挡住看起来不相关的更新。范围和锁类型还受隔离级别、是不是唯一定位以及实际计划的影响。

这不是“InnoDB 自动把很多行锁升级成一把表锁”。InnoDB 的记录锁加在索引记录上；全扫描可能形成覆盖很大范围的锁，看起来像整张表被挡住了，但机制不是锁升级。[不同语句的加锁行为](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)。

所以更新前要检查实际用到的索引，事务尽量短、及时提交，并用两个连接核对阻塞的对象。建了索引但因为类型转换等原因没被计划采用，一样达不到缩小扫描范围的目的。
