写入性能既受网络往返和事务提交影响，也受索引页面维护影响。把单条 INSERT 变成批量可以减少往返，但批次无限放大又会延长持锁时间、增加日志和失败重试成本。

## 批量语句与事务边界

```sql
CREATE TABLE batch_demo (id INT PRIMARY KEY,name VARCHAR(30)) ENGINE=InnoDB;
START TRANSACTION;
INSERT INTO batch_demo VALUES (1,'a'),(2,'b'),(3,'c');
INSERT INTO batch_demo VALUES (4,'d'),(5,'e');
COMMIT;
```

相较于五次单行自动提交，这里减少了语句往返和提交次数。复用连接时，单条 INSERT 并不意味着每条都重新建立网络连接；省掉的通常是请求往返和反复提交等成本。

批次大小应按行宽、包大小、事务日志、锁占用和超时决定。500～1000 行可以作为某些环境的试验起点，不是数据库的通用最优值。任意一步失败时，应用应回滚本批次并按明确的幂等策略重试。

可以把一次写入耗时拆成几段：客户端发送请求、服务器执行和维护索引、事务提交所需处理、结果返回。把五条记录合成一条多值 INSERT，减少的是部分请求往返与语句处理；把多条语句放进同一个事务，又减少了逐条提交的次数。两种优化发生在不同边界，不能互相替代。

批次变大也意味着失败的单位变大。若一批写入很久，中途遇到错误，回滚和重试要处理更多数据；事务持有的锁也可能更久。因此可以先在一批中记录实际条数、耗时和错误行为，再选择适合的大小，不是一直增加 VALUES 数量就一定更快。

## LOAD DATA 读取的是数据文件

准备 UTF-8 文件 `D:/mysql-lab/batch.csv`，内容为三行，不带表头：

```csv
11,Alice
12,Bob
13,Carol
```

文件位于运行 mysql 客户端的机器。客户端和服务器都允许 LOCAL 加载时，执行：

```sql
LOAD DATA LOCAL INFILE 'D:/mysql-lab/batch.csv'
INTO TABLE batch_demo
CHARACTER SET utf8mb4
FIELDS TERMINATED BY ','
OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\r\n'
(id,name);
SHOW WARNINGS;
SELECT * FROM batch_demo WHERE id>=11 ORDER BY id;
```

这里假设 Windows CRLF 行结束；若实际文件是 LF，应改为 `\n`。预期新增 id 11、12、13。LOCAL 读取客户端文件；不带 LOCAL 则读取服务器允许位置的文件，权限与 secure_file_priv 规则也不同。

客户端可以用 `mysql --local-infile=1 -u 用户 -p` 启用对应能力，服务器是否允许由 local_infile 等配置决定。只对可信连接和自己控制的输入开启，不应为一条示例无条件修改共享实例的全局设置。

LOAD DATA 的分隔符、编码、列顺序、换行和转义都属于输入契约。记录数增加不代表内容完全正确，要检查警告、关键字段和坏行处理；尤其 LOCAL 的某些错误处理行为与普通 INSERT 不同。

文件位置尤其容易弄反。你在 Windows 上运行 mysql 客户端，连接 Linux 上的数据库：带 LOCAL 时，文件由 Windows 客户端读取并发送；不带 LOCAL 时，服务器尝试读取 Linux 自己文件系统上的路径。把 Windows 的 D 盘路径发给 Linux 服务器，不会自动让 Linux 访问你的电脑。

分隔符决定怎样切列，换行符决定怎样切记录。示例 `11,Alice` 按逗号分成 id 与 name 两列；若文件多出一个表头 `id,name` 却没声明跳过，第一行就不再是本例的合法数字记录。导入后既检查条数，也检查 id 和姓名，才能发现“分错列但仍写进一些内容”的问题。

## 主键顺序为何影响页面维护

InnoDB 的聚簇索引按键组织记录。持续插入较大的自增键，通常集中到右侧叶子页；插入随机键则可能落在许多不同页面中。目标页空间不足时，需要分裂、移动部分记录并维护父页和相邻页关系。

顺序插入也可能分配或分裂页面，只是一般有更好的局部性。随机插入并非每次都发生分裂，也不能用一幅固定“一半对一半”的图保证每次实际分裂方式。

删除通常先做删除标记，旧版本清理后空间才可能复用；页面利用率降低时，InnoDB 可以尝试与相邻页合并。MERGE_THRESHOLD 控制合并阈值，默认常见为 50，但它是页面占用程度的规则，不是“删除一半记录立即回收文件一半磁盘空间”。

主键应尽量稳定、紧凑并符合生成方式。BIGINT 自增对单库实验很方便，随机 UUID 字符串可能更长且缺乏插入局部性；分布式环境也存在有序标识和二进制 UUID 等设计，应按生成需求选择，不能只靠“UUID 一律不好”下结论。主键还被二级索引携带，长度增加会传播到多棵索引。

这里的“按主键顺序”说的是索引记录的逻辑顺序，不要求磁盘上所有行永远紧挨着。页面会有空闲空间、分裂和相邻链接。假设一页已经接近容量，里面的键是 10、20、30、40，此时插入 25 需要在 20 与 30 之间安排位置；不足以容纳时，就要调整页面内容和导航信息。插入 50 则更接近当前右边界，两者的局部访问模式不同。

删除也不是立即把一个字节洞从文件中剪掉。事务可见性可能要求旧读者仍能看到被删记录的历史版本，随后清理和页面管理才有机会回收可用空间。因此删除大量行以后，表文件未按相同比例变小，并不能直接证明 DELETE 没有执行。

## UPDATE 的索引决定扫描与加锁范围

```sql
EXPLAIN UPDATE emp SET salary=salary+100 WHERE id=1;
EXPLAIN UPDATE emp SET salary=salary+100 WHERE name='柳岩';
```

主键等值定位通常把扫描范围限制得很小。没有可用索引的条件可能让 UPDATE 扫描、锁住大量索引记录，甚至阻塞看似无关的更新。范围和锁类型还受隔离级别、是否唯一定位以及实际计划影响。

这不应解释成“InnoDB 自动把很多行锁升级为一把表锁”。InnoDB 的记录锁依附索引记录；全扫描可能形成覆盖很大范围的锁，现象像整表被挡住，但机制不是锁升级。[不同语句的加锁行为](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)。

因此，更新前检查实际使用的索引、把事务缩短、及时提交，并用两个连接核对阻塞对象。只创建索引却因类型转换等原因没有被计划采用，也不能达到缩小扫描范围的目的。
