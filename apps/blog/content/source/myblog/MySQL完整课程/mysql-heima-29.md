分库分表要解决的是单个数据库承受不了的数据量或访问压力。先查清瓶颈在哪里：如果慢查询只是缺少索引，把同一条低效查询分发到三台机器，仍然可能得到三个慢查询，还增加了网络和结果合并的成本。

课程从磁盘容量、热点数据、I/O 和 CPU 压力引入拆分。这些是调查方向，不能换算成“超过多少万行就必须分库”的固定门槛。行宽、索引数量、查询方式和活跃数据比例都会改变单库的承载能力。

## 垂直拆分改变放在一起的数据

商品、订单和用户属于不同业务。把商品表放进商品库、订单表放进订单库、用户表放进用户库，就是垂直分库。每个库保存的表不同，可以分别安排容量和访问权限。代价是原本能在一个数据库中完成的关联查询和事务，可能跨越多个数据库。

垂直分表拆的是同一行的字段。例如，把常用的商品编号、名称、价格与很少读取的大段详情分开，用同一个商品 ID 关联。查询列表时不必读取详情，有机会减少读取的数据量；需要完整商品信息时，则要多一次查询或关联。是否值得拆，取决于两组字段是否确实有不同的访问模式。

垂直拆分没有减少某张热点订单表的订单数量。即使它已经有独立的订单库，单表增长的问题仍然存在，这才引出水平拆分。

## 水平拆分决定每一行去哪里

水平拆分保留相同的表结构，把不同行分开存放。按照订单 ID 范围分三片，三个节点都可以有 `tb_order` 表，但各自只保存一部分订单。把它们合起来，才是完整的逻辑表。

| 拆分方式 | 改变什么 | 能直接分散什么 | 需要补上的能力 |
| --- | --- | --- | --- |
| 垂直分库 | 不同业务表的位置 | 不同业务的数据库负载 | 跨库查询、跨业务事务 |
| 垂直分表 | 一行字段的组织 | 不常用大字段带来的读取成本 | 按主键重组完整记录 |
| 水平分库 | 同结构记录所在的实例 | 容量、连接和计算压力 | 路由、跨片查询、迁移 |
| 水平分表 | 同结构记录所在的表 | 单表规模 | 表名路由、跨表查询 |

在同一实例里创建更多表，并没有增加这台机器的 CPU、内存或磁盘带宽。水平分表与水平分库因此不能混为一谈。

分片字段也不能只看“分得均不均”。假设按订单 ID 分片，而主要接口总是按用户 ID 查询订单，这个接口很可能需要查询全部分片。反过来，按用户 ID 分片可以让同一个用户的订单聚在一起，但大客户可能形成热点。选择时应把最常用的过滤条件、关联关系和事务范围一起放进判断。

可以把几个业务动作放进拆分方案里检查。商品价格修改只访问商品库，通常容易局部完成；查询某个用户的全部订单，如果订单按用户 ID 分片，就可能一次定位；统计所有订单总额，则可能要访问全部订单片；同时修改订单和库存，如果二者已分开，就需要明确跨库操作怎样协调。拆分方案是否合适，要沿这些真实访问模式判断。

“每个节点结构相同”也不等于“每个节点数据相同”。水平分片的完整数据是各片记录的并集，同一个业务主键通常应归属确定的一片；主从复制则让多个节点保存相应数据副本。把分片当副本使用，主节点一停就读另一片，会漏掉原本属于故障片的数据；把副本当分片相加统计，又可能重复计数。

垂直拆分还会影响关联位置。用户表与省市区字典同节点时，地址展示可以在本地关联；订单表在别的节点，需要地区名称时就涉及跨节点访问。后面引入小型全局表，正是为了让一些常用字典能在多个业务节点本地使用，不是因为所有表都适合复制到所有节点。

## Mycat 放在应用与数据库之间

课程使用 Mycat 1.x 演示代理式分片。应用连接 Mycat，Mycat 解析 SQL，根据配置选出后端节点，再收集执行结果。另一类方案把路由逻辑放在应用进程中的数据库访问层；两者都需要处理分片规则，只是部署位置不同。

![应用经 Mycat 访问分片](assets/sharding-topology.svg)

Mycat 本身不保存这些业务表的数据。它保存配置、维护连接并处理请求。应用虽然仍通过 MySQL 协议发送 SQL，但这不代表所有单机 SQL、事务和数据库工具都能无条件照搬。

例如，三片分别返回局部排序结果，还需要在代理层合成全局顺序。跨片求平均值也不能直接平均三个平均值：一片有 1 条记录，另一片有 100 条记录，权重显然不同，必须结合总和与数量。分片减少了单个后端的工作量，也让代理承担了协调工作。

代理把数据库地址隐藏在一个入口后面，但仍需根据 SQL 判断路由。它要知道逻辑表对应哪些节点、分片字段是哪一列，以及本次条件是否提供足够信息。查询 id=5000001 与查询“姓名包含张”，虽然都能发到同一个 Mycat 地址，后端访问范围可能完全不同。

所以对应用“看起来还是连一个数据库”，主要描述连接入口，而不是取消了分布式数据的限制。生成全局唯一 ID、维护跨节点一致性、处理分片迁移，仍需要与实际布局相匹配的设计。单点入口还可能成为新的性能或可用性关注点，必须和后端分片一起测量。

## 扩容会改变数据的归属

用 `id % 3` 决定分片后，把配置直接改成 `id % 4`，不少 ID 的计算结果会变化。旧数据仍在旧节点，新查询却可能被送到新节点，于是出现“数据还在，但查不到”。配置变更不能代替数据迁移。

实施拆分前，至少要能回答：一条记录的唯一标识由谁生成，跨片事务如何处理，旧数据如何迁移，如何验证没有丢失和重复，以及失败后怎样回到原路由。这些问题来自拆分本身，不会因引入一个中间件而消失。

用 ID 4 看扩容的具体影响：三片时 `4%3=1`，记录写到下标 1；改为四片后 `4%4=0`，同一条件会被计算到下标 0。如果只改配置而没搬数据，按主键查询就可能返回空，尽管原节点仍保存着它。若新写入再按新规则落到另一片，还可能产生同一业务主键的多份记录。

迁移因此至少包含旧规则到新规则的对应、记录搬运、迁移期间写入如何处理、切换前一致性核对和失败后的路由恢复。这里讲这些步骤，是为了说明为什么“新增一台服务器”还没有完成扩容；具体在线迁移实现超出本课程实验，不能用修改 count 参数冒充。
