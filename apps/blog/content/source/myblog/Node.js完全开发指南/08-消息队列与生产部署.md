# 消息队列、服务治理与生产部署

下面这段代码看起来没有问题，实际上藏着一个无法靠重试彻底修复的窗口：

```ts
const order = await database.createOrder(input);
await messageBroker.publish('order.created', { orderId: order.id });
```

数据库提交后、消息发送前，如果进程崩溃，订单已经存在，消费者却永远不知道。反过来先发消息再写数据库，则可能让消费者看到一笔最终回滚的订单。消息系统真正难的不是“能发出去”，而是业务状态、投递确认、重复消费和失败恢复能闭环。

## Outbox 补上发布窗口

Outbox 把业务变更和待发布事件写进同一个本地事务：

```ts
import { randomUUID } from 'node:crypto';

await database.transaction(async (tx) => {
  const order = await tx.orders.create(input);

  await tx.outbox.create({
    id: randomUUID(),
    topic: 'order.created',
    aggregateId: order.id,
    payload: JSON.stringify({
      orderId: order.id,
      userId: order.userId,
    }),
    createdAt: new Date(),
  });
});
```

独立 Relay 持续读取未发布记录，发送成功后再标记：

```ts
async function relay(batchSize = 100) {
  const events = await outbox.claimUnpublished(batchSize);

  for (const event of events) {
    try {
      await broker.publish(event.topic, event.payload, {
        eventId: event.id,
      });
      await outbox.markPublished(event.id);
    } catch (error) {
      await outbox.release(event.id, error);
    }
  }
}
```

Relay 可能在 Broker 已确认、但 `markPublished` 尚未执行时崩溃，因此同一事件仍可能发送两次。Outbox 解决的是“事件不会悄悄丢失”，不是“天然只消费一次”；消费者仍要按 `eventId` 幂等。

事件信封至少应该有稳定 ID、类型、版本和发生时间：

```ts
interface EventEnvelope<T> {
  id: string;
  type: string;
  schemaVersion: number;
  occurredAt: string;
  payload: T;
}
```

## RabbitMQ 的确认链路

RabbitMQ 的可靠投递需要同时覆盖 Broker 和消费者两端：

```text
durable exchange
  + durable queue
  + persistent message
  + publisher confirm
  + consumer ack
  + idempotent handler
```

只写 `persistent: true` 不够。如果 Exchange 或 Queue 重启后不存在，消息仍然无处可去；如果生产端没等 Publisher Confirm，也无法判断 Broker 是否真正接收。

```ts
import amqp from 'amqplib';
import { once } from 'node:events';

const connection = await amqp.connect(process.env.AMQP_URL!);
const channel = await connection.createConfirmChannel();

await channel.assertExchange('domain.events', 'topic', {
  durable: true,
});

await channel.assertExchange('domain.events.dlx', 'topic', {
  durable: true,
});

await channel.assertQueue('email.order-created.dead', {
  durable: true,
});

await channel.bindQueue(
  'email.order-created.dead',
  'domain.events.dlx',
  'email.order-created',
);

await channel.assertQueue('email.order-created', {
  durable: true,
  deadLetterExchange: 'domain.events.dlx',
  deadLetterRoutingKey: 'email.order-created',
});

await channel.bindQueue(
  'email.order-created',
  'domain.events',
  'order.created',
);

async function publishOrderCreated(event: EventEnvelope<unknown>) {
  const accepted = channel.publish(
    'domain.events',
    'order.created',
    Buffer.from(JSON.stringify(event)),
    {
      persistent: true,
      contentType: 'application/json',
      messageId: event.id,
      type: event.type,
    },
  );

  if (!accepted) {
    await once(channel, 'drain');
  }

  await channel.waitForConfirms();
}
```

`publish()` 返回 `false` 表示客户端写缓冲区已满，不表示消息发送失败。忽略背压会让高峰期内存持续增长。连接的 `error` 与 `close` 事件也要进入重连和告警逻辑，重连后必须重新声明 Channel、Exchange、Queue 和消费者。

### Ack 要放在业务提交后

```ts
channel.prefetch(10);

await channel.consume('email.order-created', async (message) => {
  if (!message) return;

  try {
    const event = parseAndValidateEvent(message.content);

    await database.transaction(async (tx) => {
      const inserted = await tx.processedEvents.tryInsert(event.id);
      if (!inserted) return;

      await tx.emailJobs.create({
        eventId: event.id,
        userId: event.payload.userId,
      });
    });

    channel.ack(message);
  } catch (error) {
    if (isPermanentMessageError(error)) {
      channel.nack(message, false, false);
      return;
    }

    await retryPublisher.schedule(message, error);
    channel.ack(message);
  }
});
```

业务提交前就 `ack`，进程崩溃会丢任务。对临时故障直接 `nack(..., true)` 又可能形成毫秒级热循环，把数据库故障放大。更稳妥的做法是把重试次数和下一次执行时间写入重试队列，超过上限再进入死信队列。

无法解析、缺字段或 schema 不支持属于永久错误，不应该无限重试。死信中要保留原消息 ID、错误类型、首次失败时间和重试次数，便于修复后重放。

## Exchange 怎么选

| Exchange | 路由方式 | 适合的消息 |
| --- | --- | --- |
| `direct` | Routing Key 精确匹配 | 明确的一类任务 |
| `topic` | `*` 匹配一段，`#` 匹配多段 | `order.created`、`order.paid` 这类分层事件 |
| `headers` | 按消息头组合匹配 | 确实存在多维路由条件的消息 |
| `fanout` | 忽略 Routing Key，广播到所有绑定队列 | 缓存失效、系统通知 |

Fanout 的每个订阅方都需要自己的 Queue。邮件服务和审计服务如果共用一条 Queue，它们会竞争消费，每条消息只会落到其中一个消费者，而不是双方各拿一份。

Topic 命名要表达已经发生的事实，例如 `order.created`，不要把命令和事件混成 `do.create.order`。版本兼容优先放在消息信封的 `schemaVersion` 中，避免每次字段变化都创建一套无法管理的新 Topic。

## 延迟消息会积压

延迟消息适合订单超时关闭、预约提醒和退避重试。RabbitMQ 的延迟 Exchange 插件可以直接使用 `x-delay`：

```ts
await channel.assertExchange('jobs.delayed', 'x-delayed-message', {
  durable: true,
  arguments: {
    'x-delayed-type': 'direct',
  },
});

channel.publish(
  'jobs.delayed',
  'order.expire',
  Buffer.from(JSON.stringify({ orderId: 'o_1' })),
  {
    persistent: true,
    headers: {
      'x-delay': 5 * 60 * 1000,
    },
  },
);
```

插件版本必须和 Broker 版本兼容，并纳入备份、升级和故障演练。TTL 加死信 Exchange 也能构造延迟队列，但不同过期时间共用一条 Queue 时可能出现队头阻塞。

数天或数月后的海量定时任务不应不加评估地堆入 Broker。需要取消、修改、查询和审计的长周期任务，更适合先落数据库或专用调度系统，到期前再投递给执行队列。

## Kafka 的顺序边界

Kafka 的 Topic 由多个 Partition 组成，顺序只在单个 Partition 内成立。需要保持同一订单事件有序时，必须使用稳定的业务 Key：

```ts
import { Kafka } from 'kafkajs';

const kafka = new Kafka({
  clientId: 'order-service',
  brokers: process.env.KAFKA_BROKERS!.split(','),
});

const producer = kafka.producer({
  allowAutoTopicCreation: false,
});

await producer.connect();

await producer.send({
  topic: 'order-events',
  messages: [
    {
      key: 'order:o_1',
      value: JSON.stringify({
        id: 'evt_1',
        type: 'order.created',
        schemaVersion: 1,
        orderId: 'o_1',
      }),
      headers: {
        traceId: 'trace_123',
      },
    },
  ],
});
```

同一个 Key 会稳定映射到同一 Partition。没有 Key 时，相关事件可能落到不同 Partition，消费者就可能先看到 `order.paid`，后看到 `order.created`。

### Consumer Group 分担分区

同一 Consumer Group 内，一个 Partition 同时只交给一个消费者处理；不同 Group 各自维护 Offset，因此计费和审计可以独立读取同一批事件。

```ts
const consumer = kafka.consumer({
  groupId: 'billing-service',
});

await consumer.connect();
await consumer.subscribe({
  topic: 'order-events',
  fromBeginning: false,
});

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    if (!message.value) throw new Error('empty_message');

    const event = parseAndValidateEvent(message.value);

    await database.transaction(async (tx) => {
      const inserted = await tx.processedEvents.tryInsert(event.id);
      if (!inserted) return;

      await applyBillingChange(tx, event);
    });

    logger.info({
      topic,
      partition,
      offset: message.offset,
      eventId: event.id,
    });
  },
});
```

处理函数抛错时不能吞掉异常并假装成功，否则 Offset 继续前进，失败消息不会再来。另一方面，数据库提交后、Offset 提交前崩溃会导致消息再次处理，所以数据库中的唯一事件 ID 仍然是必要边界。

Rebalance 会暂停和重新分配 Partition。单条处理时间过长、消费者失联或实例频繁扩缩容都会触发它；耗时任务应拆分，避免一个消息长期占住消费循环。

## 分区与容量

Kafka 配置要从容量和恢复目标倒推：

```text
日均消息数
  × 平均消息大小
  × 保留天数
  × 副本因子
  ≈ 原始存储需求
```

还要给索引、日志段、峰值增长和故障迁移预留空间。分区越多，并行上限越高，但文件句柄、Leader 选举、Rebalance 和副本同步成本也越高。副本因子不能超过可用 Broker 数，并且需要验证少一台 Broker 时仍有足够容量。

消息的职责应该分开：

- `key`：决定分区和业务有序范围。
- `value`：承载业务数据。
- `headers`：放 trace ID、schema 版本等元数据。

批量和压缩能提高吞吐，但会增加等待成批的延迟。Admin API 适合部署工具创建 Topic、检查分区和副本，不应作为普通业务接口暴露，更不能允许任意用户删除 Topic。

Kafka 事务能原子提交一组 Kafka 写入，或把消费 Offset 与新的 Kafka 消息一起提交；它不会自动把 MySQL、PostgreSQL 等业务数据库加入同一个事务。数据库与 Kafka 的一致性仍然需要 Outbox、CDC 或经过验证的等价设计。

## 两种 MQ 怎么选

| 需求 | 更自然的选择 |
| --- | --- |
| 任务队列、灵活路由、逐条 Ack | RabbitMQ |
| 高吞吐事件流、长时间保留、重放 | Kafka |
| Direct、Topic、Headers、Fanout 路由 | RabbitMQ |
| 按 Key 分区并让多个 Group 独立回放 | Kafka |

选型前先写清楚峰值吞吐、消息大小、允许延迟、保留时间、重放需求、顺序范围和团队运维能力。“吞吐更高”不能替代业务约束；一个没人会排障的集群通常比性能较低但能稳定维护的系统更危险。

## Nacos 发现服务

服务实例启动时向注册中心上报服务名、IP、端口和元数据；调用方按服务名获取健康实例。这里容易写成每次业务请求都同步查询注册中心，结果注册中心一抖动，所有服务调用一起失败。

`nacos` 客户端负责注册、摘除和发现。实例必须在依赖就绪后注册，并在停止接收新请求时先摘除：

```bash
npm install --save-exact nacos@2.6.3 urllib@2.44.0
```

```ts
import { NacosNamingClient } from 'nacos';
import { request as httpRequest, type RequestOptions } from 'urllib';

const INSTANCE_REFRESH_MS = 5000;
const INSTANCE_QUERY_TIMEOUT_MS = 2000;
const INSTANCE_MAX_STALE_MS = 15_000;
const serviceName = 'user-service';
const serviceGroup = 'DEFAULT_GROUP';
const serviceInstance = {
  ip: process.env.SERVICE_IP!,
  port: Number(process.env.PORT ?? 3001),
  weight: 1,
  enabled: true,
  healthy: true,
  metadata: { version: process.env.APP_VERSION ?? 'dev' },
};

const timeoutHttpClient = {
  request(url: string, options: RequestOptions = {}) {
    return httpRequest(url, {
      ...options,
      timeout: [INSTANCE_QUERY_TIMEOUT_MS, INSTANCE_QUERY_TIMEOUT_MS],
    });
  },
};

const namingClientOptions = {
  logger,
  serverList: process.env.NACOS_SERVER_ADDR!,
  namespace: process.env.NACOS_NAMESPACE ?? 'public',
  httpclient: timeoutHttpClient,
};

const namingClient = new NacosNamingClient(namingClientOptions);

await namingClient.ready();
await startDependencies();
await namingClient.registerInstance(
  serviceName,
  serviceInstance,
  serviceGroup,
);

interface DiscoveredInstance {
  ip: string;
  port: number;
  healthy: boolean;
  enabled: boolean;
}

interface InstanceSnapshot {
  instances: readonly DiscoveredInstance[];
  refreshedAt: number;
  errorSince?: number;
}

let userServiceSnapshot: InstanceSnapshot | undefined;
let instanceRefreshFlight: { result: Promise<void> } | undefined;

function isDiscoveredInstance(value: unknown): value is DiscoveredInstance {
  if (!value || typeof value !== 'object') return false;
  const item = value as Record<string, unknown>;

  return typeof item.ip === 'string' &&
    Number.isInteger(item.port) &&
    typeof item.healthy === 'boolean' &&
    typeof item.enabled === 'boolean';
}

function applyInstanceSnapshot(value: unknown, now = Date.now()) {
  if (!Array.isArray(value) || !value.every(isDiscoveredInstance)) {
    throw new Error('malformed_nacos_instance_snapshot');
  }

  userServiceSnapshot = {
    instances: Object.freeze(
      value.filter((item) => item.healthy && item.enabled),
    ),
    refreshedAt: now,
  };
}

function recordDiscoveryError(error: unknown, now = Date.now()) {
  if (!userServiceSnapshot) throw error;

  userServiceSnapshot = {
    ...userServiceSnapshot,
    errorSince: userServiceSnapshot.errorSince ?? now,
  };
  logger.warn({ err: error }, 'retaining short-lived instance snapshot');
}

function refreshInstances() {
  if (instanceRefreshFlight) return instanceRefreshFlight.result;

  let timedOut = false;
  let timeout: ReturnType<typeof setTimeout>;
  const source = namingClient.getAllInstances(
    serviceName,
    serviceGroup,
    '',
    false,
  );

  const observed = source.then(
    (instances) => {
      if (!timedOut) applyInstanceSnapshot(instances);
    },
    (error) => {
      if (!timedOut) recordDiscoveryError(error);
    },
  );

  const deadline = new Promise<void>((resolve, reject) => {
    timeout = setTimeout(() => {
      timedOut = true;
      try {
        recordDiscoveryError(new Error('nacos_instance_query_timeout'));
        resolve();
      } catch (error) {
        reject(error);
      }
    }, INSTANCE_QUERY_TIMEOUT_MS);
  });

  const result = Promise.race([observed, deadline]).finally(() => {
    clearTimeout(timeout);
  });
  const flight = { result };
  instanceRefreshFlight = flight;

  void source.finally(() => {
    if (instanceRefreshFlight === flight) {
      instanceRefreshFlight = undefined;
    }
  }).catch(() => {});

  return result;
}

function getUserServiceInstances(now = Date.now()) {
  const snapshot = userServiceSnapshot;
  if (!snapshot) throw new Error('service_discovery_unavailable');

  if (now - snapshot.refreshedAt > INSTANCE_MAX_STALE_MS) {
    throw new Error('service_discovery_snapshot_stale');
  }

  if (snapshot.instances.length === 0) {
    throw new Error('user_service_unavailable');
  }

  return snapshot.instances;
}

await refreshInstances();

namingClient.subscribe({
  serviceName,
  groupName: serviceGroup,
}, (instances) => {
  try {
    applyInstanceSnapshot(instances);
  } catch (error) {
    recordDiscoveryError(error);
  }
});

const instanceRefreshTimer = setInterval(() => {
  void refreshInstances().catch((error) => {
    logger.error({ err: error }, 'instance refresh failed');
  });
}, INSTANCE_REFRESH_MS);
instanceRefreshTimer.unref();

async function stopService() {
  clearInterval(instanceRefreshTimer);
  await namingClient.deregisterInstance(
    serviceName,
    serviceInstance,
    serviceGroup,
  );
  await stopAcceptingRequests();
  await drainInFlightRequests();
}
```

合法的空数组表示注册中心明确确认当前没有健康实例，`applyInstanceSnapshot()` 会立刻用空列表替换旧值，随后 `getUserServiceInstances()` 返回 unavailable。只有查询抛错或通知格式异常时才保留旧快照；`getUserServiceInstances()` 无条件检查 `refreshedAt`，即使控制面请求一直 pending，也不能无限使用旧地址。

应用层 deadline 控制当前刷新最多等多久，`instanceRefreshFlight` 保证 single-flight。`getAllInstances()` 的第四个参数显式传 `false`，让主动刷新直接请求 Nacos，而不是把 SDK 本地缓存误当成新的服务端响应。Push 订阅仍保留，两条路径使用同一个 group。

注入 SDK 的 `urllib` transport 同时限制连接和响应等待，会主动结束超时的底层 HTTP 请求。因此原 `source` 最终会 settle 并清除 flight，Nacos 恢复后下一轮能重新查询；不会在“永不重试”和“无限叠加悬挂请求”之间二选一。

`httpclient` 是这个已锁定 SDK 版本的 transport 适配边界，升级 `nacos` 时要用断网和慢响应集成测试重新确认它。

负载均衡不能只看随机数。实例权重、连接失败、主动健康检查和熔断状态都应该参与选择。注册成功也不代表业务可用，只有依赖初始化完成后才应把实例标记为可接收流量；关闭时先摘除实例，再等待在途请求结束。

## 动态配置先校验

动态配置适合功能开关、灰度比例、限流阈值和超时时间，不适合把所有启动参数都热更新。

```ts
import { NacosConfigClient } from 'nacos';

interface RuntimeConfig {
  featureEnabled: boolean;
  requestTimeoutMs: number;
  rolloutPercent: number;
}

let currentConfig: Readonly<RuntimeConfig> = Object.freeze({
  featureEnabled: false,
  requestTimeoutMs: 3000,
  rolloutPercent: 0,
});

function applyConfig(raw: string, version: string) {
  const parsed = JSON.parse(raw);
  const next = validateRuntimeConfig(parsed);

  currentConfig = Object.freeze(next);
  logger.info({ version }, 'runtime config applied');
}

const dataId = 'gateway.runtime.json';
const group = 'DEFAULT_GROUP';
const configClient = new NacosConfigClient({
  serverAddr: process.env.NACOS_SERVER_ADDR!,
  namespace: process.env.NACOS_NAMESPACE ?? 'public',
});

await configClient.ready();

applyConfig(
  await configClient.getConfig(dataId, group),
  'startup',
);

configClient.subscribe({ dataId, group }, (content) => {
  try {
    applyConfig(content, new Date().toISOString());
  } catch (error) {
    logger.error({ err: error }, 'invalid nacos config ignored');
  }
});
```

解析或校验失败时必须保留上一版，不能留下半更新对象。一次更新如果同时修改多个相关字段，应先构造完整新对象，再原子替换引用。

### 发布配置归管理面

发布动作放在受审计的管理工具或部署流程中，不跟普通业务实例的读取代码混在一起：

```ts
const adminClient = new NacosConfigClient({
  serverAddr: process.env.NACOS_SERVER_ADDR!,
  namespace: process.env.NACOS_NAMESPACE ?? 'public',
});

await adminClient.ready();

const published = await adminClient.publishSingle(
  dataId,
  group,
  JSON.stringify({
    featureEnabled: true,
    requestTimeoutMs: 2500,
    rolloutPercent: 10,
  }),
);

if (!published) throw new Error('nacos_config_publish_failed');
```

发布凭据与业务读取凭据应分权，并记录版本、操作者和回滚点。

数据库连接地址、线程数或数据结构版本往往需要重建资源，不能仅靠改一个变量安全生效。密钥也应进入专用密钥管理系统，配置中心不是默认的明文密码仓库。

## Elasticsearch 是搜索投影

Elasticsearch 适合全文检索和分析，不适合成为订单、余额等交易数据的唯一真相源。业务数据库先提交，再通过 Outbox 或 CDC 更新索引；索引损坏时应能从真相源重建。

客户端只创建一次，地址和 API Key 从服务端配置读取。Mapping 由部署或迁移任务在首次写入前创建：

```ts
import { Client } from '@elastic/elasticsearch';

const es = new Client({
  node: process.env.ELASTICSEARCH_URL!,
  auth: {
    apiKey: process.env.ELASTICSEARCH_API_KEY!,
  },
});

await es.ping();

await es.indices.create({
  index: 'articles',
  mappings: {
    properties: {
      title: {
        type: 'text',
        fields: {
          keyword: { type: 'keyword' },
        },
      },
      description: { type: 'text' },
      authorId: { type: 'keyword' },
      publishedAt: { type: 'date' },
      viewCount: { type: 'long' },
    },
  },
});
```

文本、精确值、日期和数字的索引方式不同。Mapping 错了以后再改类型通常需要新建 Index、重建数据并切换 Alias，不能指望在线原地修改。下面的最小 CRUD 分别使用 `index`、`get`、`update` 和 `delete`：

```ts
await es.index({
  index: 'articles',
  id: 'a_1',
  document: {
    title: 'Node.js 消息队列',
    description: 'RabbitMQ 与 Kafka 的可靠投递',
    authorId: 'u_123',
    publishedAt: '2026-07-13T00:00:00.000Z',
    viewCount: 0,
  },
  refresh: 'wait_for',
});

const article = await es.get({ index: 'articles', id: 'a_1' });
console.log(article._source);

await es.update({
  index: 'articles',
  id: 'a_1',
  doc: { viewCount: 1 },
});

await es.delete({ index: 'articles', id: 'a_1' });
```

`refresh: 'wait_for'` 适合必须立刻查到写入结果的低频操作，批量导入时滥用会降低吞吐。删除文档也不会删除业务数据库中的事实数据。

### Bulk 要检查局部失败

```ts
const response = await es.bulk({
  operations: articles.flatMap((article) => [
    {
      index: {
        _index: 'articles',
        _id: article.id,
      },
    },
    article,
  ]),
});

if (response.errors) {
  const failures = response.items
    .map((item, index) => ({
      item,
      articleId: articles[index]?.id,
    }))
    .filter(({ item }) => item.index?.error);

  throw new BulkIndexError(failures);
}
```

Bulk 的 HTTP 请求成功，不等于每个文档都成功。局部失败可能来自 Mapping 冲突、数据格式或资源压力；只看顶层状态会静默漏索引。

## 查询字段要对

不带条件地分页浏览可以用 `match_all`，不要用空字符串伪造全文查询：

```ts
const page = await es.search({
  index: 'articles',
  from: 0,
  size: 20,
  query: { match_all: {} },
  sort: [{ publishedAt: 'desc' }],
});
```

`match` 会对查询文本和 `text` 字段做分词，适合全文搜索：

```ts
query: {
  match: {
    title: 'Node.js 消息队列',
  },
}
```

聚合结果位于 `aggregations`，与命中文档列表相互独立。按作者统计文章数量时，把 `size` 设为 `0` 可以只返回桶：

```ts
const result = await es.search({
  index: 'articles',
  size: 0,
  query: {
    range: {
      publishedAt: { gte: '2026-01-01' },
    },
  },
  aggs: {
    articlesByAuthor: {
      terms: {
        field: 'authorId',
        size: 20,
      },
    },
  },
});

console.log(result.aggregations?.articlesByAuthor);
```

`term` 不分词，适合 `keyword`、ID、数字和布尔值：

```ts
query: {
  term: {
    authorId: 'u_123',
  },
}
```

多字段搜索可以用 `multi_match`，并给标题更高权重：

```ts
query: {
  multi_match: {
    query: 'Node.js',
    fields: ['title^2', 'description'],
  },
}
```

范围和精确过滤放入 `bool.filter`，避免参与相关性评分：

```ts
query: {
  bool: {
    must: [
      {
        match: {
          title: 'Node.js',
        },
      },
    ],
    filter: [
      {
        range: {
          publishedAt: {
            gte: '2026-01-01',
          },
        },
      },
      {
        term: {
          authorId: 'u_123',
        },
      },
    ],
  },
}
```

宽泛前缀、通配符和高基数字段聚合可能消耗大量 CPU 与内存。自动补全应使用专门的字段设计，不要直接对任意正文执行前导通配查询。

## cluster 的共享状态

一个 Node.js 进程的 JavaScript 主线程不会同时跑满多个 CPU 核心。`cluster` 可以创建多个 Worker 共同监听服务端口：

```ts
import cluster from 'node:cluster';
import { availableParallelism } from 'node:os';
import process from 'node:process';

if (cluster.isPrimary) {
  const workerCount = availableParallelism();

  for (let index = 0; index < workerCount; index += 1) {
    cluster.fork();
  }

  cluster.on('exit', (worker, code) => {
    console.error({
      pid: worker.process.pid,
      code,
    }, 'worker exited');

    setTimeout(() => cluster.fork(), 1000);
  });
} else {
  await startHttpServer();
}
```

每个 Worker 都有独立堆内存。`Map`、本地 Session 和内存限流计数不会共享，必须移到 Redis、数据库或其他外部存储。数据库连接池也会按 Worker 数倍增：8 个 Worker 各开 20 条连接，就是 160 条，不应只看单进程配置。

`availableParallelism()` 也不是必须启动的实例数。容器 CPU 配额、内存、连接上限以及应用是 CPU 密集还是 I/O 密集都会影响合理值。持续崩溃时无条件立即 `fork` 会形成重启风暴，至少要退避并告警。

## PM2 管理进程生命周期

PM2 可以接管启动、停止、日志、监控、内存阈值和 Cluster 模式。生产参数放进版本化配置，避免依赖某次终端命令：

```js
// ecosystem.config.cjs
module.exports = {
  apps: [
    {
      name: 'api',
      script: './dist/server.js',
      instances: 4,
      exec_mode: 'cluster',
      max_memory_restart: '500M',
      min_uptime: '10s',
      max_restarts: 10,
      kill_timeout: 10000,
      listen_timeout: 10000,
      wait_ready: true,
      env: {
        NODE_ENV: 'production',
        PORT: 3000,
      },
    },
  ],
};
```

`wait_ready: true` 时，应用要在监听端口并完成必要初始化后通知 PM2：

```ts
const server = await startHttpServer();
process.send?.('ready');

let shuttingDown = false;

async function shutdown(signal: string) {
  if (shuttingDown) return;
  shuttingDown = true;

  logger.info({ signal }, 'shutting down');

  const forceExit = setTimeout(() => {
    process.exit(1);
  }, 9000);
  forceExit.unref();

  await server.close();
  await consumer.disconnect();
  await database.close();

  process.exit(0);
}

process.on('SIGINT', () => void shutdown('SIGINT'));
process.on('SIGTERM', () => void shutdown('SIGTERM'));
```

不要同时在应用里调用 `cluster.fork()`，又让 PM2 使用 `exec_mode: 'cluster'`，否则会产生两层进程树，实例数和连接数成倍增加。二者选一个负责多进程。

自动重启只能恢复进程，不能修复持续的代码错误。若实例不断退出，`max_restarts` 应阻止无限循环并触发告警。部署完成的判据也不是 `pm2 list` 显示 `online`，而是新实例通过健康检查、真实 HTTP 请求成功、消息消费者恢复、日志没有重复崩溃，并且旧实例已经完成优雅退出。
