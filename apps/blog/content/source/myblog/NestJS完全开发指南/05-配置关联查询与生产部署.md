# NestJS 配置、关联查询与生产部署

## ConfigModule 与环境隔离

开发、测试和生产用不同的数据库和密钥。E2E 测试会建数据、删数据，不能指向开发库。

`.env.development`：

```dotenv
DB_NAME=db.sqlite
COOKIE_KEY=dev-only-secret
```

`.env.test`：

```dotenv
DB_NAME=test.sqlite
COOKIE_KEY=test-only-secret
```

`.env.*` 要加进 `.gitignore`。生产环境的变量由部署平台注入，仓库里不存 Cookie key、数据库密码或连接串。

`ConfigModule` 加载对应环境的文件，`TypeOrmModule.forRootAsync()` 从 `ConfigService` 读数据库配置：

```ts
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      envFilePath: `.env.${process.env.NODE_ENV}`,
    }),
    TypeOrmModule.forRootAsync({
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        type: "sqlite",
        database: config.getOrThrow<string>("DB_NAME"),
        entities: [User, Report],
        synchronize: true, // 仅限本地原型阶段
      }),
    }),
  ],
})
export class AppModule {}
```

文件名取决于 `NODE_ENV`。用 `cross-env` 让 Windows、macOS 和 Linux 的启动脚本写法一致：

```json
{
  "scripts": {
    "start:dev": "cross-env NODE_ENV=development nest start --watch",
    "test:e2e": "cross-env NODE_ENV=test jest --config ./test/jest-e2e.json --maxWorkers=1"
  }
}
```

多个 Jest worker 同时写一个 SQLite 文件，容易报 `SQLITE_BUSY: database is locked`，所以这里用 `--maxWorkers=1`。换成支持并发测试的数据库就不用照搬。

## SQLite E2E 数据重置

SQLite 文件要在 TypeORM 建立连接之前删掉。应用初始化以后，连接还占着文件句柄，Windows 上还可能报文件被占用。整组 E2E 启动前删库，每个用例前按外键顺序清表：

```ts
import { rm } from "node:fs/promises";
import { join } from "node:path";
import { DataSource } from "typeorm";

const testDb = join(process.cwd(), "test.sqlite");
let app!: INestApplication;

beforeAll(async () => {
  await rm(testDb, { force: true });

  const moduleRef = await Test.createTestingModule({
    imports: [AppModule],
  }).compile();

  app = moduleRef.createNestApplication();
  await app.init();
});

beforeEach(async () => {
  const dataSource = app.get(DataSource);
  await dataSource.getRepository(Report).clear();
  await dataSource.getRepository(User).clear();
});

afterAll(() => app.close());
```

有外键关联的话，先清从表，再清主表。要每个用例都删库，得先关掉应用和 `DataSource`；用了 Migration 的话，重建的空库还要先跑迁移。事务回滚、每个用例重建 schema 也都能做到隔离。

## Report DTO 与持久化

Report 存品牌、型号、年份、里程、经纬度和价格。DTO 用 `class-validator` 检查请求体，Service 再创建实体。TypeScript 类型不会校验运行时的输入。

```ts
export class CreateReportDto {
  @IsString()
  make!: string;

  @IsString()
  model!: string;

  @IsInt()
  @Min(1930)
  @Max(2050)
  year!: number;

  @IsNumber()
  @Min(0)
  mileage!: number;

  @IsLongitude()
  lng!: number;

  @IsLatitude()
  lat!: number;

  @IsNumber()
  @Min(0)
  price!: number;
}
```

Controller 接 HTTP 输入，Service 组装并保存实体。报告要关联到当前登录的用户：

```ts
@Post()
@UseGuards(AuthGuard)
createReport(
  @Body() body: CreateReportDto,
  @CurrentUser() user: User,
) {
  return this.reportsService.create(body, user);
}
```

```ts
async create(dto: CreateReportDto, user: User): Promise<Report> {
  const report = this.repo.create({
    ...dto,
    user,
    userId: user.id,
  });
  return this.repo.save(report);
}
```

## User 与 Report 一对多关系

一个用户可以提交多份报告，每份报告只属于一个用户，所以关系是 `User 1 -> N Report`：

```ts
// user.entity.ts
@OneToMany(() => Report, (report) => report.user)
reports!: Report[];
```

```ts
// report.entity.ts
@Column()
userId!: number;

@ManyToOne(() => User, (user) => user.reports, { nullable: false })
user!: User;
```

Report 的 `ManyToOne` 那一侧持有外键。显式声明了 `userId`，不加载 User 也能读到归属 ID。`() => User` 推迟实体求值，能避开实体互相导入时的循环依赖。

关联默认不自动加载。要用户详情就显式用 `relations` 或 `leftJoinAndSelect`；只要归属 ID 就读 `report.userId`。

别把整个 User 实体放进响应，密码字段可能跟着关联一起泄漏。响应 DTO 只暴露 `userId`：

```ts
export class ReportDto {
  @Expose()
  id!: number;

  @Expose()
  make!: string;

  @Expose()
  model!: string;

  @Expose()
  price!: number;

  @Expose()
  userId!: number;
}
```

这个 DTO 不依赖 `report.user` 有没有加载，序列化时也不会去访问 `undefined.id`。输出字段用白名单，实体新加的字段不会自动进响应。

## 管理员审批与请求执行顺序

新报告默认 `approved = false`，管理员审核过才能进估价样本。这样普通用户批量提交假价格，也污染不了查询结果。

```ts
@Column({ default: false })
approved!: boolean;
```

`AuthGuard` 只查登录状态，审批接口还要用 `AdminGuard` 查管理员权限：

```ts
@Injectable()
export class AdminGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest<Request>();
    return Boolean(request.currentUser?.admin);
  }
}
```

NestJS 的请求顺序：

```text
middleware -> guard -> interceptor -> pipe/controller -> response interceptor
```

Guard 在 Interceptor 之前执行。要是 Interceptor 才写入 `currentUser`，`AdminGuard` 就读不到用户。所以把 session 查询提前到 Middleware：

```ts
@Injectable()
export class CurrentUserMiddleware implements NestMiddleware {
  constructor(private readonly usersService: UsersService) {}

  async use(req: Request, _res: Response, next: NextFunction) {
    const userId = req.session?.userId;
    if (userId) {
      req.currentUser = await this.usersService.findOne(userId);
    }
    next();
  }
}
```

Express 的 `Request` 上没有 `currentUser` 字段，用声明合并把类型补上，别用 `@ts-ignore`：

```ts
declare global {
  namespace Express {
    interface Request {
      currentUser?: User;
    }
  }
}
```

分工：Middleware 准备请求上下文，Guard 判断放不放行，Interceptor 处理日志、响应格式和调用前后的增强。新用户的 `admin` 默认值一定要是 `false`，不然一注册就有审批权限了。

## QueryBuilder 估价查询

查询字符串里的值都是字符串。年份、里程和经纬度要先转换，再验证：

```ts
export class GetEstimateDto {
  @IsString()
  make!: string;

  @IsString()
  model!: string;

  @Transform(({ value }) => Number(value))
  @IsInt()
  year!: number;

  @Transform(({ value }) => Number(value))
  @IsNumber()
  mileage!: number;

  @Transform(({ value }) => Number(value))
  @IsLongitude()
  lng!: number;

  @Transform(({ value }) => Number(value))
  @IsLatitude()
  lat!: number;
}
```

估价要做范围过滤、排序和数量限制，所以用 QueryBuilder。先取里程最接近的三份已审批报告，再在应用层算均价：

```ts
async createEstimate(dto: GetEstimateDto) {
  const { make, model, year, mileage, lng, lat } = dto;

  const reports = await this.repo
    .createQueryBuilder("report")
    .where("report.make = :make", { make })
    .andWhere("report.model = :model", { model })
    .andWhere("ABS(report.lng - :lng) <= 5", { lng })
    .andWhere("ABS(report.lat - :lat) <= 5", { lat })
    .andWhere("ABS(report.year - :year) <= 3", { year })
    .andWhere("report.approved = :approved", { approved: true })
    .orderBy("ABS(report.mileage - :mileage)", "ASC")
    .setParameter("mileage", mileage)
    .take(3)
    .getMany();

  if (reports.length === 0) return { price: null };

  const total = reports.reduce((sum, report) => sum + report.price, 0);
  return { price: total / reports.length };
}
```

参数用 `:make`、`:year` 这种占位符绑定，不能把用户输入拼进 SQL。第一次用 `where()`，后面都用 `andWhere()`；再调一次 `where()` 会把之前的条件覆盖掉。正负 5 度、正负 3 年、取三条样本只是示例条件，不是能上生产的车辆估值模型。

## TypeORM 0.3 Migration

`synchronize: true` 会在应用启动时比较 Entity 和数据库结构，然后自动改表。开发早期很省事，但在生产环境，一次误删实体字段，TypeORM 就可能把整列连同数据一起删掉。

数据库开始存真实数据以后，就把它固定成 `false`，结构变更交给 Migration：

```text
修改 Entity
  -> 生成并检查 migration
  -> 在测试库执行
  -> 备份生产库
  -> 在生产库执行
  -> 启动新版本应用
```

Migration 的 `up()` 执行变更，`down()` 负责回滚。生成的文件要人工检查列类型、默认值、非空约束、索引和回滚逻辑。

TypeORM 0.3 用 `DataSource` 文件做 CLI 入口，旧版 `ormconfig.js` 的命令不能直接照搬。应用和 CLI 最好共用数据库配置，免得 `AppModule` 和迁移配置越差越远；具体命令以项目锁定的 TypeORM 版本为准。

测试库重建后要先跑 Migration。生产迁移放在单独的发布步骤里；`migrationsRun: true` 只适合能保证单实例执行的场景，多个实例同时迁移可能冲突。

## 生产配置与部署

生产环境一般用 PostgreSQL，由平台注入 `DATABASE_URL` 和 Cookie 密钥：

```ts
const productionOptions = {
  type: "postgres" as const,
  url: process.env.DATABASE_URL,
  synchronize: false,
  ssl: { rejectUnauthorized: false }, // 是否需要取决于数据库服务商
};
```

端口也从环境变量读：

```ts
await app.listen(Number(process.env.PORT ?? 3000));
```

部署步骤：

1. 装依赖，编译 TypeScript。
2. 校验必需的环境变量，缺了就直接启动失败。
3. 对目标数据库执行审查过的 Migration。
4. 用 `start:prod` 启动编译后的 JavaScript。
5. 检查健康接口、日志和数据库连接。

Heroku、`Procfile`、Heroku Postgres 和 Git push 是旧的部署流程，套餐名和命令别直接照抄。Render、Railway、云服务器和容器平台一样要注入端口、数据库 URL 和密钥。`ssl.rejectUnauthorized: false` 能不能用，要按数据库服务商的文档来配；关掉证书校验会降低连接安全性。

## 上线检查

- [ ] `NODE_ENV` 已设置，开发、测试、生产用不同的数据库和 Cookie 密钥。
- [ ] `.env.*` 已忽略，仓库里没有密钥、密码或连接串。
- [ ] SQLite E2E 串行运行；重建数据库后已执行 Migration。
- [ ] 全局 `ValidationPipe` 已开启，查询参数先转换再验证。
- [ ] 创建 Report 要登录，审批 Report 要管理员权限，新用户默认不是管理员。
- [ ] 响应 DTO 不暴露密码；估价只读 `approved = true` 的数据，并处理空样本。
- [ ] SQL 参数全部绑定，QueryBuilder 的条件没被后面的 `where()` 覆盖。
- [ ] 所有生产配置的 `synchronize` 都是 `false`，Migration 验证过升级、回滚和已有数据的场景。
- [ ] 多实例部署只有一个迁移执行者，应用和 CLI 共用 TypeORM 0.3 的 `DataSource` 配置。
- [ ] `PORT`、`DATABASE_URL`、Cookie 密钥和 SSL 配置都来自部署环境。
- [ ] 部署后检查过健康接口、日志、数据库连接和完整的业务请求。
