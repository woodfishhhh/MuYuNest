# NestJS 完全开发指南（4）：认证、授权与自动化测试

```text
注册：检查邮箱 -> 哈希密码 -> 创建用户 -> Session 记住 userId
登录：查找用户 -> 校验密码 -> Session 记住 userId
后续请求：读取 Session -> 查当前用户 -> Guard 放行或拒绝
```

- 认证：确认用户身份。
- 授权：判断当前用户能否执行操作。
- Session：保存身份标识，不保存权限规则。
- AuthService：校验凭据；Controller：写 Session；Guard：控制访问。

## 密码哈希

密码不能明文存储，也不使用可逆加密。注册时保存 `salt.hash`，登录时重新计算并比较哈希。

```ts
import {
  randomBytes,
  scrypt as scryptCallback,
  timingSafeEqual,
} from 'node:crypto';
import { promisify } from 'node:util';

const scrypt = promisify(scryptCallback);

async function hashPassword(password: string) {
  const salt = randomBytes(16).toString('hex');
  const hash = (await scrypt(password, salt, 32)) as Buffer;
  return `${salt}.${hash.toString('hex')}`;
}

async function verifyPassword(password: string, stored: string) {
  const [salt, storedHex] = stored.split('.');
  if (!salt || !storedHex) return false;

  const actual = (await scrypt(password, salt, 32)) as Buffer;
  const expected = Buffer.from(storedHex, 'hex');

  return (
    actual.length === expected.length &&
    timingSafeEqual(actual, expected)
  );
}
```

- salt 无需保密，用于让相同密码产生不同哈希。
- 使用 `scrypt`、Argon2 或 bcrypt，并按服务器负载测试时间和内存成本。
- 使用 `timingSafeEqual` 比较哈希。
- 日志、异常监控、access log 和测试快照都不能记录明文密码。

AuthService 只校验凭据，不读写 Session：

```ts
@Injectable()
export class AuthService {
  constructor(private readonly usersService: UsersService) {}

  async signup(email: string, password: string) {
    const existing = await this.usersService.findOneByEmail(email);
    if (existing) {
      throw new BadRequestException('邮箱已被使用');
    }

    const passwordHash = await hashPassword(password);
    return this.usersService.create(email, passwordHash);
  }

  async signin(email: string, password: string) {
    const user = await this.usersService.findOneByEmail(email);
    const matched = user
      ? await verifyPassword(password, user.password)
      : false;

    if (!user || !matched) {
      throw new UnauthorizedException('邮箱或密码错误');
    }

    return user;
  }
}
```

- 登录失败统一返回“邮箱或密码错误”，避免枚举已注册邮箱。
- 邮箱必须有数据库唯一约束；“先查再写”不能防止并发重复注册。
- Session 留在 Controller，AuthService 可被 CLI、消息消费者和 GraphQL resolver 复用。

## Session

`cookie-session` 把 Session 放在客户端 Cookie 中。签名只能防篡改，不会加密内容，因此只保存 `userId` 等最小身份信息。

```ts
type AuthSession = {
  userId?: number | null;
};

@Serialize(UserDto)
@Post('signup')
async signup(
  @Body() body: CreateUserDto,
  @Session() session: AuthSession,
) {
  const user = await this.authService.signup(body.email, body.password);
  session.userId = user.id;
  return user;
}

@Serialize(UserDto)
@Post('signin')
async signin(
  @Body() body: SigninDto,
  @Session() session: AuthSession,
) {
  const user = await this.authService.signin(body.email, body.password);
  session.userId = user.id;
  return user;
}

@Post('signout')
signout(@Session() session: AuthSession) {
  session.userId = null;
}
```

- Cookie 密钥从环境变量读取。
- 生产环境设置 `httpOnly`、`sameSite`，HTTPS 开启 `secure`，并配置 CSRF 防护。
- 需要服务端撤销、多端管理或更大 Session 时，使用 `express-session` + Redis。
- Cookie 只证明 Session 未被篡改；账号是否有效仍以数据库为准。

## `CurrentUser` 与 Interceptor

参数装饰器不能直接从 DI 容器取得 `UsersService`。Interceptor 负责查询用户并写入 request，装饰器只读取结果。

```ts
interface RequestWithUser extends Request {
  session?: AuthSession;
  currentUser?: User | null;
}

@Injectable()
export class CurrentUserInterceptor implements NestInterceptor {
  constructor(private readonly usersService: UsersService) {}

  async intercept(context: ExecutionContext, next: CallHandler) {
    const request = context
      .switchToHttp()
      .getRequest<RequestWithUser>();

    const userId = request.session?.userId;
    request.currentUser = userId
      ? await this.usersService.findOne(userId)
      : null;

    return next.handle();
  }
}

export const CurrentUser = createParamDecorator(
  (_: unknown, context: ExecutionContext) =>
    context.switchToHttp().getRequest<RequestWithUser>().currentUser,
);
```

全局注册后，Controller 可以直接读取当前用户：

```ts
@Serialize(UserDto)
@Get('whoami')
whoAmI(@CurrentUser() user: User | null) {
  return user;
}
```

```ts
{
  provide: APP_INTERCEPTOR,
  useClass: CurrentUserInterceptor,
}
```

- 全局 Interceptor 会让不需要用户的路由也查询数据库；可缩小到 Controller，或合并进认证 Guard。
- 公开路由使用 `User | null`；受保护路由由 Guard 保证用户非空。

## Guard

Guard 决定请求是否继续。缺少登录身份时抛出 `UnauthorizedException`，返回 401：

```ts
@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext) {
    const request = context
      .switchToHttp()
      .getRequest<RequestWithUser>();

    if (!request.session?.userId) {
      throw new UnauthorizedException('请先登录');
    }

    return true;
  }
}
```

```ts
@UseGuards(AuthGuard)
@Serialize(UserDto)
@Get('profile')
getProfile(@CurrentUser() user: User) {
  return user;
}
```

- Session 中有 ID 不代表用户仍然存在；敏感接口需要重新查询用户状态。
- Guard 在路由 Interceptor 之前执行，不能依赖 `CurrentUserInterceptor` 的结果。

## 单元测试与 Mock

测试 AuthService 时 Mock `UsersService`，保留真实密码哈希逻辑。

```ts
type UsersPort = Pick<
  UsersService,
  'findOneByEmail' | 'create'
>;

describe('AuthService', () => {
  let service: AuthService;
  let users: jest.Mocked<UsersPort>;

  beforeEach(async () => {
    users = {
      findOneByEmail: jest.fn(),
      create: jest.fn(),
    };

    const module = await Test.createTestingModule({
      providers: [
        AuthService,
        { provide: UsersService, useValue: users },
      ],
    }).compile();

    service = module.get(AuthService);
  });

  it('注册时不会把明文密码交给持久化层', async () => {
    users.findOneByEmail.mockResolvedValue(null);
    users.create.mockImplementation(async (email, password) =>
      ({ id: 1, email, password }) as User,
    );

    const user = await service.signup('a@example.com', 'secret123');

    expect(user.password).not.toBe('secret123');
    expect(user.password.split('.')).toHaveLength(2);
  });

  it('邮箱已存在时拒绝注册', async () => {
    users.findOneByEmail.mockResolvedValue({ id: 1 } as User);

    await expect(
      service.signup('a@example.com', 'secret123'),
    ).rejects.toThrow(BadRequestException);
  });
});
```

异步异常使用 `await expect(promise).rejects`，不要使用 `try/catch + done`。

Mock 边界：

- 测 AuthService：Mock UsersService，保留真实哈希逻辑。
- 测 Controller：Mock AuthService，只断言参数转交、返回值和 Session 是否被修改。
- 测装饰器、Pipe、Guard、Cookie：别硬塞进 Controller 单元测试，交给 E2E。
- 被测流程需要“先注册再登录”时，可以写一个小型内存 Fake；只验证单个分支时，用 `mockResolvedValue` 更直接。
- Mock 只实现被测对象实际调用的方法，并保持异步返回、参数和错误行为与真实依赖一致。

- 断言可观察行为，不断言 `randomBytes` 调用次数等实现细节。
- 单分支使用静态 Mock；需要“先写后读”时使用内存 Fake。Fake 不复制数据库约束和事务。
- Controller 单测不运行装饰器、Pipe、Guard 和 Cookie 中间件，这些行为交给 E2E。

### 测试边界

| 行为 | 单元测试 | E2E |
| --- | --- | --- |
| 密码不以明文保存 | AuthService | 可补一条响应不泄露密码 |
| Session 写入 `userId` | Controller | 用 Cookie 跨请求验证 |
| DTO 拒绝非法邮箱 | 不测装饰器 | 发送非法 HTTP 请求断言 400 |
| Guard 拒绝游客 | 可单测 `canActivate` | 请求受保护路由断言 401 |
| Repository 真能写库 | 不用 Mock 猜 | 使用隔离测试库验证 |

## E2E

E2E 从 `AppModule` 创建应用并通过 Supertest 发请求。跨请求保留 Cookie 使用 `request.agent`：

```ts
describe('Auth e2e', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const module = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = module.createNestApplication();
    await app.init();
  });

  afterAll(() => app.close());

  it('注册、退出并重新登录', async () => {
    const agent = request.agent(app.getHttpServer());
    const email = 'e2e@example.com';

    await agent
      .post('/auth/signup')
      .send({ email, password: 'secret123' })
      .expect(201)
      .expect(({ body }) => {
        expect(body.id).toBeDefined();
        expect(body.email).toBe(email);
        expect(body.password).toBeUndefined();
      });

    await agent.post('/auth/signout').expect(201);
    await agent
      .post('/auth/signin')
      .send({ email, password: 'secret123' })
      .expect(201)
      .expect(({ body }) => {
        expect(body.email).toBe(email);
        expect(body.password).toBeUndefined();
      });

    await agent
      .get('/auth/whoami')
      .expect(200)
      .expect(({ body }) => {
        expect(body.email).toBe(email);
        expect(body.password).toBeUndefined();
      });
  });
});
```

E2E 直接从 `AppModule` 创建应用，不会执行 `main.ts`。只在 `main.ts` 注册的全局前缀、Filter、Pipe、CORS 和 Session 中间件都会缺失。

出现 500 时先读取服务端异常，再比较开发与测试的启动配置。

一种处理方式是把全局能力接回模块：

```ts
@Module({
  providers: [
    {
      provide: APP_PIPE,
      useValue: new ValidationPipe({
        whitelist: true,
        transform: true,
      }),
    },
  ],
})
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(
        cookieSession({
          keys: [process.env.COOKIE_KEY!],
          httpOnly: true,
          sameSite: 'lax',
        }),
      )
      .forRoutes('{*splat}');
  }
}
```

NestJS 11 使用 path-to-regexp v8，全路由通配写成 `'{*splat}'`。也可以抽出 `configureApp(app)`，让 `main.ts` 和 E2E 复用同一套配置。

## 测试数据库隔离

E2E 不能连接开发数据库：

1. 测试使用独立数据库，例如 `test.sqlite` 或 SQLite `:memory:`。
2. 每个测试前清空表、重建 schema，或用事务回滚，保证用例互不依赖。

```ts
TypeOrmModule.forRootAsync({
  useFactory: () => {
    const testing = process.env.NODE_ENV === 'test';

    return {
      type: 'sqlite' as const,
      database: testing ? 'test.sqlite' : 'db.sqlite',
      entities: [User],
      synchronize: true,
      dropSchema: testing,
    };
  },
});
```

- `dropSchema` 仅用于测试库，禁止用于生产。
- 并行 Jest worker 不能共享同一个 SQLite 文件；使用独立数据库、容器或事务回滚。
- 每个用例自行准备和清理数据，不能依赖执行顺序。

## 排错

### 1. E2E 中 `session` 是 `undefined`

检查测试是否跳过了 `main.ts` 中的配置。确认 Cookie 中间件在 `app.init()` 前注册，并查看请求是否收到 `Set-Cookie`。

### 2. 登录成功，下一次请求仍像未登录

Supertest 的普通 `request(app)` 不会自动替不同请求保存 Cookie。改用 `request.agent(app)`，或手动把 `set-cookie` 回传。

### 3. Guard 总是返回 401

检查 Cookie 是否到达服务端、Session 字段名是否一致，以及 Guard 是否错误依赖了尚未执行的 Interceptor。Guard 返回 `false` 通常得到 403；缺少身份应主动抛出 401。

### 4. 注销后却查到了第一个用户

不要把 `null` 或 `undefined` 继续传给查询。`findOne` 在收到空 ID 时应直接返回 `null`，Controller 和 CurrentUser Interceptor 也要先判断 Session。

### 5. 单元测试通过，接口校验却坏了

直接调用 Controller 方法不会运行装饰器、Pipe 和 Guard。给关键路由补一条 E2E，发送非法请求体并断言 400。

### 6. Mock 越写越像第二套业务代码

先缩小 Mock 边界。静态返回值能表达场景时不要造内存数据库；只有“先写后读”的连续流程确实需要状态时，再使用内存 Fake。

### 7. E2E 只能成功运行一次

检查测试库是否独立、用例前是否清理，以及并行 worker 是否共享 SQLite 文件。
