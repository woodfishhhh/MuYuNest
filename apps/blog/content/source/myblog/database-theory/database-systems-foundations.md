应用程序如果不直接读写磁盘文件，中间就必须有一层专门负责结构定义、并发控制和故障恢复的数据管理软件。理解数据库系统，核心就是搞清数据如何从现实世界抽象成表结构，以及数据库管理系统（DBMS）如何通过分层架构把业务代码和物理存储隔离开。

## 数据库系统的核心组成与分层位置

日常讨论数据库时，经常把数据、数据库、DBMS 和整个数据库系统混为一谈，其实它们各自承担不同职责：

| 概念 | 英文全称 | 核心定位 | 主要职责或特征 |
| :--- | :--- | :--- | :--- |
| 数据 | Data | 描述事物的符号记录 | 覆盖数字、文本、图像、音频、视频等，数据库重点管理记录及其关联 |
| 数据库 | DB (Database) | 长期存储的数据集合 | 长期储存、有组织、可共享、低冗余、高独立性与可扩展性 |
| 数据库管理系统 | DBMS | 位于用户与操作系统之间的软件 | 提供 DDL、DML、存储组织、事务并发控制、安全与恢复能力 |
| 数据库系统 | DBS | 完整运行的软硬件与人员体系 | 由 $\boldsymbol{DBS=DB+DBMS+}$应用程序$\boldsymbol{+DBA}$ 组成 |

**应用程序永远通过 DBMS 访问数据，绝不直接跨过 DBMS 去操作底层存储文件。**

从调用链路来看，完整的访问层级依次为：用户 → 应用系统与开发工具 → DBMS（由数据库管理员 DBA 参与配置与运维） → 操作系统（OS） → 物理存储上的数据库（DB）。DBMS 在中间承担了五项核心职能：

1. **数据定义**：提供 DDL（Data Definition Language），定义模式、基本表、视图和索引等对象结构。
2. **数据组织、存储与管理**：维护数据字典、用户数据与存取路径，决定文件结构和物理存储方式。
3. **数据操纵**：提供 DML（Data Manipulation Language），执行数据的查询、插入、更新和删除。
4. **事务与运行管理**：统一调度并发事务，保障数据安全性、完整性与故障后的可恢复性。
5. **数据库建立与维护**：承担初始数据装入、转储恢复、性能监控与结构重构。

## 数据管理演进与数据库解决的工程问题

数据管理技术从人工管理、文件系统一路演进到数据库系统，根本驱动力是降低数据冗余、提升共享能力并解耦程序与存储。

| 演进阶段 | 硬件与系统基础 | 处理方式 | 数据共享与结构化特征 |
| :--- | :--- | :--- | :--- |
| 人工管理阶段 | 无专用磁盘与操作系统（卡片/纸带） | 批处理 | 数据与程序绑定，不共享、冗余极大、无独立性、无结构 |
| 文件系统阶段 | 磁盘/磁鼓与 OS 文件系统 | 批处理 + 联机处理 | 共享性弱、冗余度高、独立性低，仅记录内部有结构、整体无关联 |
| 数据库系统阶段 | DBMS 统一管理 | 高并发联机与批处理 | 共享性强、低冗余、易扩展、数据整体结构化、独立性高 |

文件系统最大的瓶颈在于“数据面向单个应用”。每新增一个业务模块，往往要重写文件格式或复制一份数据，导致同一份信息在多个文件里口径不一致。数据库系统面向整个业务组织统一建模，数据存取粒度可以从整条记录细化到单个数据项，一处更新即可全局同步，消除了数据不相容问题。

**真正让业务代码摆脱存储细节束缚的，是 DBMS 提供的物理独立性与逻辑独立性，以及统一的安全与并发控制。**

- **物理独立性**：当数据的物理存储方式（例如从顺序存储改成 B+ 树索引存储）改变时，应用程序无需修改。
- **逻辑独立性**：当数据库的整体逻辑结构（例如拆分字段或新增表）发生变化时，只要局部视图保持稳定，应用程序依然无需改动。
- **统一运行控制**：哪怕数据集中存放在一起，若缺乏 DBMS 层的锁机制、日志恢复和权限检查，多用户并发读写依然会破坏数据一致性。

## 数据模型：从现实对象到逻辑表结构

数据模型是对现实世界数据特征的抽象工具，包含数据结构、数据操作和完整性约束三个要素。工程上通常先用概念模型厘清业务实体与关联，再转换为 DBMS 可执行的逻辑模型和物理模型。

| 模型分类 | 建模视角 | 核心用途 | 典型代表 |
| :--- | :--- | :--- | :--- |
| 概念模型（信息模型） | 业务与用户视角 | 数据库概念设计 | E-R 模型（实体-联系模型） |
| 逻辑模型与物理模型 | 计算机系统视角 | DBMS 具体实现 | 层次模型、网状模型、关系模型 |

### 概念模型的核心抽象

概念模型用来回答系统里有哪些业务对象、各自包含什么特征，以及对象之间如何发生关联（具体建模规范与映射规则见[数据库概念设计](/posts/er-modeling-and-schema-design)）：

- **实体与实体集**：客观存在且相互区别的事物称为实体（如某位学生、某个学院）；同一类实体的集合称为实体集。
- **属性与码**：描述实体某一特征的字段称为属性（如学号、姓名、专业）；能唯一标识实体的属性或属性组称为码（学号是码，姓名因可能重名而不能作码）。
- **实体型**：用实体名和属性名集合抽象刻画同类实体，记作 $\boldsymbol{实体名(属性_1,属性_2,...,属性_n)}$，例如 `学生(学号, 姓名, 专业, 性别)`。
- **实体间的联系**：分为一对一（1:1，如一夫一妻婚姻关系）、一对多（1:$n$，如一名教师指导多名学生）和多对多（$m$:$n$，如学生与课程的双向选修）。

### 三种逻辑模型的结构对比

1. **层次模型**：采用树形结构，要求有且仅有一个根节点，且除根节点外每个节点有且仅有一个双亲节点。它擅长沿着父子路径快速检索，但难以直接表达一个节点拥有多个双亲的复杂关系。
2. **网状模型**：允许一个及以上节点无双亲，也允许一个节点拥有多个双亲。它能直接刻画复杂网状关联，代价是指针结构复杂、维护难度大。
3. **关系模型**：建立在严格的集合论与关系代数基础上，用规范化二维表组织数据，彻底摆脱了物理指针导航。

关系模型的常用术语与表结构对应关系如下：

- **关系**：对应一张二维表；**元组**对应表中的一行；**属性**对应表中的一列。
- **域**：一组具有相同数据类型的值的集合，限定属性的有效取值范围；**分量**是元组中某个属性的具体值。
- **码**：唯一确定一个元组的属性或属性集；**关系模式**是对关系结构的静态描述，记作 $\boldsymbol{关系名(属性_1,属性_2,...,属性_n)}$。

## 三级模式与两级映像：隔离变化的架构防线

在讨论分层架构前，先区分“型与值”“模式与实例”两组基础概念：

- **型与值**：型是对数据结构与属性的静态说明，如 `学生(学号, 姓名, 专业)`；值是对型的具体赋值，如 `学生(20250001, 张三, 计算机)`。
- **模式与实例**：模式描述数据库中全体数据的逻辑结构和特征，对应“型”的层面，相对稳定；实例是模式在某一时刻存储的实际数据集合，会随增删改动态变化，同一个模式可以对应多个不同时刻的实例。

**三级模式把用户视图、全局逻辑结构和物理存储彻底拆开，两级映像则在层间承担翻译职责，这是数据独立性落地的直接机制。**

```text
[ 应用 A / 外模式 1 ]   [ 应用 B / 外模式 2 ]
          \                     /
           +---- 外模式-模式映像 ----+   --> 保障逻辑独立性
                      |
               [ 模式 (全局逻辑) ]
                      |
               模式-内模式映像           --> 保障物理独立性
                      |
               [ 内模式 (物理存储) ]
```

### 三级模式的职责边界

1. **外模式（子模式 / 用户模式）**：描述单个用户或应用系统可见的局部数据逻辑视图，通过 DDL 定义。一个数据库可以有多个外模式，例如教务人员和学生看到的字段权限各不相同，外模式直接隔离了敏感字段，提升了数据安全性。
2. **模式（概念模式）**：描述数据库中全体数据的全局逻辑结构与约束，是所有用户的公共数据视图。一个数据库只有一个模式，位于外模式与内模式之间。
3. **内模式（存储模式）**：描述数据在底层磁盘上的物理结构与存储方式，包括记录定长或变长格式、顺序或索引组织、数据压缩与加密、是否跨物理块存储等。一个数据库同样只有一个内模式，这类底层布局细节绝不直接暴露给应用层。

### 两级映像如何保障独立性

- **外模式-模式映像（保障逻辑独立性）**：一个模式可以对应多个外模式，每个外模式都配有一条外模式-模式映像。当全局模式发生修改（如拆分表、增加新字段）时，DBA 只需调整对应的外模式-模式映像，使外模式保持不变；由于应用程序基于外模式编写，业务代码无需改动。
- **模式-内模式映像（保障物理独立性）**：一个数据库只有一个模式和一个内模式，因此只有一条模式-内模式映像。当物理存储结构调整（如更换存储引擎、重建索引或改变压缩策略）时，DBA 或 DBMS 修改模式-内模式映像，使全局模式保持不变，进而保证了外模式和应用程序的稳定。
