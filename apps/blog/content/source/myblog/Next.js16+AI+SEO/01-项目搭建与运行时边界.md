# Next.js 16 项目搭建与运行时边界

Next.js 项目第一步就容易埋雷：Node 版本不够，脚手架选项和团队习惯对不上，或者服务器代码、浏览器代码和静态资源混在一起。先把这些边界定下来，后面写路由、AI 和认证时才不用边写边返工。

## 1. 版本和脚手架

课程以 Next.js 16.0.2 为准，Node.js 至少 `20.9`。初始化时可以把选项直接写进命令，省得多人协作时每个人交互选的不一样：

```bash
pnpm create next-app@latest next-ai-seo \
  --ts \
  --eslint \
  --tailwind \
  --src-dir \
  --app \
  --turbopack \
  --import-alias "@/*"

cd next-ai-seo
pnpm dev
```

用交互式脚手架的话，关键的几项：

- TypeScript：开。
- `src/` 目录：开，业务代码和配置更好分层。
- App Router：开。
- Tailwind：看项目需要。
- Turbopack：开发环境可以开；它是打包器，跟 React Compiler 是两回事。
- import alias：保留 `@/*`，免得目录一深相对路径就失控。

React Compiler 管组件的编译和优化，Turbopack 管模块构建和开发服务器。开了其中一个，另一个并不会自动被替代。

## 2. 目录各自负责什么

```text
next-ai-seo/
├─ .next/                 # 构建缓存和产物，不能提交
├─ node_modules/          # 依赖安装目录
├─ public/                # 不经编译、以根路径访问的静态资源
├─ src/
│  └─ app/                # App Router 路由和页面
│     ├─ layout.tsx       # 根布局，必须保留 html/body
│     ├─ page.tsx         # 根路径 /
│     └─ globals.css      # 全局样式入口
├─ next.config.ts         # Next.js 配置
├─ package.json           # scripts 和依赖
├─ postcss.config.mjs     # Tailwind/PostCSS 配置
└─ tsconfig.json          # TypeScript 配置
```

`public` 下的文件不会被当成模块编译，比如 `public/logo.svg` 直接用 `/logo.svg` 访问。`src` 下的代码会进构建图，图片、字体和业务模块按需导入，别什么都往 `public` 里扔。

根布局是整个 App Router 的 HTML 外壳：

```tsx
// src/app/layout.tsx
import type { Metadata } from 'next';
import './globals.css';

export const metadata: Metadata = {
  title: 'Next AI SEO',
  description: 'A full-stack Next.js application',
};

export default function RootLayout({
  children,
}: Readonly<{ children: React.ReactNode }>) {
  return (
    <html lang="zh-CN">
      <body>{children}</body>
    </html>
  );
}
```

`layout.tsx` 必须提供 `<html>` 和 `<body>`，`children` 是当前路由的页面内容。具体的页面是 `page.tsx`：

```tsx
// src/app/page.tsx
export default function HomePage() {
  return <main>首页</main>;
}
```

## 3. 三个运行命令

```json
{
  "scripts": {
    "dev": "next dev --turbopack",
    "build": "next build",
    "start": "next start"
  }
}
```

```bash
pnpm dev          # 开发服务器，默认 http://localhost:3000
pnpm build        # 生产构建，尽早发现类型和路由问题
pnpm start        # 启动已经构建好的生产版本
```

`pnpm start` 代替不了 `pnpm build`。没有新的构建产物时，它启动的是上一次的构建结果；部署脚本要先构建，再启动或者交给平台接管。

## 4. 先理解服务器边界

App Router 里的组件默认是 Server Component。服务器组件能直接读服务端数据、访问私有环境变量，但用不了浏览器状态和事件：

```tsx
// Server Component
export default async function DashboardPage() {
  const data = await loadPrivateData();
  return <pre>{JSON.stringify(data)}</pre>;
}
```

要用 `useState`、`useEffect`、事件处理器、浏览器 API 或自定义的客户端 Hook 时，才在文件顶部声明：

```tsx
'use client';

import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount((value) => value + 1)}>{count}</button>;
}
```

别为了一个按钮就把根布局和整棵页面树变成 Client Component。更好的边界是：服务器页面包着一个很小的交互叶子组件。

## 5. 这一层的验收标准

- Node.js 版本满足项目要求，团队用同一个包管理器。
- `pnpm dev`、`pnpm build`、`pnpm start` 都能单独跑起来。
- `public` 只放真正公开的静态资源，私有文件不从这里暴露。
- 根布局保留 `html`、`body` 和 `children`。
- 页面默认是 Server Component，只有真有交互才声明 `'use client'`。
