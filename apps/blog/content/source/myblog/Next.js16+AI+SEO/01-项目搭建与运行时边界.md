# Next.js 16 项目搭建与运行时边界

Next.js 项目最容易在第一步就留下隐患：Node 版本不满足要求，脚手架选项和团队习惯不一致，或者把服务器代码、浏览器代码和静态资源混在一起。先把这些边界固定，后面的路由、AI 和认证才不会一边写一边返工。

## 1. 版本和脚手架

这套课程以 Next.js 16.0.2 为基准，Node.js 至少使用 `20.9`。项目初始化可以把选择显式写进命令，减少多人协作时的交互差异：

```bash
pnpm create next-app@latest next-ai-seo \
  --ts \
  --eslint \
  --tailwind \
  --src-dir \
  --app \
  --turbopack \
  --import-alias "@/*"

cd next-ai-seo
pnpm dev
```

如果使用交互式脚手架，关键选择通常是：

- TypeScript：开启。
- `src/` 目录：开启，业务代码和配置更容易分层。
- App Router：开启。
- Tailwind：按项目需要开启。
- Turbopack：开发环境可以开启；它是打包器，不等于 React Compiler。
- import alias：保留 `@/*`，避免相对路径在深层目录中失控。

React Compiler 解决的是组件编译和优化问题，Turbopack 解决的是模块构建和开发服务器问题。二者职责不同，开启其中一个不会自动替代另一个。

## 2. 目录各自负责什么

```text
next-ai-seo/
├─ .next/                 # 构建缓存和产物，不能提交
├─ node_modules/          # 依赖安装目录
├─ public/                # 不经编译、以根路径访问的静态资源
├─ src/
│  └─ app/                # App Router 路由和页面
│     ├─ layout.tsx       # 根布局，必须保留 html/body
│     ├─ page.tsx         # 根路径 /
│     └─ globals.css      # 全局样式入口
├─ next.config.ts         # Next.js 配置
├─ package.json           # scripts 和依赖
├─ postcss.config.mjs     # Tailwind/PostCSS 配置
└─ tsconfig.json          # TypeScript 配置
```

`public` 下的文件不会被当作模块编译。例如 `public/logo.svg` 通过 `/logo.svg` 访问。`src` 下的代码会进入构建图，图片、字体和业务模块应按需要导入，而不是把所有东西都丢进 `public`。

根布局是整个 App Router 的 HTML 外壳：

```tsx
// src/app/layout.tsx
import type { Metadata } from 'next';
import './globals.css';

export const metadata: Metadata = {
  title: 'Next AI SEO',
  description: 'A full-stack Next.js application',
};

export default function RootLayout({
  children,
}: Readonly<{ children: React.ReactNode }>) {
  return (
    <html lang="zh-CN">
      <body>{children}</body>
    </html>
  );
}
```

`layout.tsx` 必须提供 `<html>` 和 `<body>`，`children` 是当前路由的页面内容。`page.tsx` 才是具体的页面：

```tsx
// src/app/page.tsx
export default function HomePage() {
  return <main>首页</main>;
}
```

## 3. 三个运行命令

```json
{
  "scripts": {
    "dev": "next dev --turbopack",
    "build": "next build",
    "start": "next start"
  }
}
```

```bash
pnpm dev          # 开发服务器，默认 http://localhost:3000
pnpm build        # 生产构建，尽早发现类型和路由问题
pnpm start        # 启动已经构建好的生产版本
```

`pnpm start` 不能代替 `pnpm build`。没有新的构建产物时，它启动的是上一次构建结果；部署脚本应先构建，再启动或交给平台接管。

## 4. 先理解服务器边界

App Router 中的组件默认是 Server Component。服务器组件可以直接读取服务端数据、访问私有环境变量，但不能使用浏览器状态和事件：

```tsx
// Server Component
export default async function DashboardPage() {
  const data = await loadPrivateData();
  return <pre>{JSON.stringify(data)}</pre>;
}
```

需要 `useState`、`useEffect`、事件处理器、浏览器 API 或自定义客户端 Hook 时，才在文件顶部声明：

```tsx
'use client';

import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount((value) => value + 1)}>{count}</button>;
}
```

不要因为一个按钮就把根布局和整个页面树变成 Client Component。更好的边界是服务器页面包住一个很小的交互叶子组件。

## 5. 这一层的验收标准

- Node.js 版本满足项目要求，并且团队使用同一个包管理器。
- `pnpm dev`、`pnpm build`、`pnpm start` 都能独立运行。
- `public` 只放真正的公开静态资源，私有文件不通过它暴露。
- 根布局保留 `html`、`body` 和 `children`。
- 页面默认保持 Server Component，只有真实交互才声明 `'use client'`。
