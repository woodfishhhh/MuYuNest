# Gin 基础（04）：路径、查询参数、表单与请求体

同一个请求可以同时带路径参数、查询参数、请求头和请求体。取参数之前，先确定值应该来自哪里。否则，前端传了 JSON，后端却调用 `PostForm`，得到的空字符串很容易被误判成“前端没有传”。

## 四个位置，对应四种读取方式

| 请求中的位置 | 示例 | Gin 中的入口 |
| --- | --- | --- |
| 路径 | `/users/3` | `c.Param("id")` |
| 查询字符串 | `?page=2&tag=go&tag=web` | `Query`、`DefaultQuery`、`QueryArray` |
| 请求头 | `X-Request-ID: request-1` | `c.GetHeader("X-Request-ID")` |
| 请求体 | 表单、JSON、二进制 | `PostForm`、绑定方法，或 `c.Request.Body` |

查询字符串也可以出现在 POST URL 上，它不专属于 GET。`Param` 和 `Query` 取出来的值仍是字符串，不能因为路由变量叫 `id` 就假定它已经变成整数。

`Query("name")` 在缺失和空字符串两种情况下都可能得到 `""`。要区分它们，用 `GetQuery` 的第二个返回值。`DefaultQuery("page", "1")` 在键不存在时提供默认值；如果请求明确写了 `page=`，得到的仍是空字符串。

## 先理解请求体格式

`application/x-www-form-urlencoded` 把字段编码成 `name=Lin&age=20`。`multipart/form-data` 用 boundary 分隔多个部分，因此可以混合文本字段和文件。JSON 则是一份结构化文档，不会自动进入 `PostForm`。

用 `curl.exe -F` 或浏览器的 `FormData` 上传时，让客户端生成包含 boundary 的 `Content-Type`。只手动写 `multipart/form-data` 而漏掉 boundary，服务端无法知道各部分在哪里结束。

## 一个能区分来源和读取错误的服务

使用 Go 1.25 或更高版本，新建独立目录。以下命令按 PowerShell 7 编写；Linux/macOS 请求示例中的 `curl.exe` 可换成 `curl`。

```powershell
mkdir gin-04-request
Set-Location gin-04-request
go mod init example.com/gin-04-request
go get github.com/gin-gonic/gin@v1.12.0
```

每个示例单独运行，避免多个 `main` 函数放进同一个包。

保存为 `main.go`：

```go
package main

import (
	"bytes"
	"errors"
	"io"
	"log"
	"net/http"
	"strconv"

	"github.com/gin-gonic/gin"
)

func readError(c *gin.Context, err error) {
	status := http.StatusBadRequest
	var tooLarge *http.MaxBytesError
	if errors.As(err, &tooLarge) {
		status = http.StatusRequestEntityTooLarge
	}
	c.JSON(status, gin.H{"error": "请求体无效或超过 4 KiB"})
}

func NewRouter() *gin.Engine {
	r := gin.New()
	r.Use(gin.Recovery())
	if err := r.SetTrustedProxies(nil); err != nil {
		panic(err)
	}
	r.GET("/users/:id", func(c *gin.Context) {
		id, err := strconv.Atoi(c.Param("id"))
		if err != nil || id < 1 {
			c.JSON(http.StatusBadRequest, gin.H{"error": "id 必须是正整数"})
			return
		}
		name, exists := c.GetQuery("name")
		c.JSON(http.StatusOK, gin.H{
			"id": id, "name": name, "name_exists": exists,
			"page": c.DefaultQuery("page", "1"), "tags": c.QueryArray("tag"),
		})
	})
	r.POST("/form", func(c *gin.Context) {
		if c.ContentType() != gin.MIMEPOSTForm && c.ContentType() != gin.MIMEMultipartPOSTForm {
			c.JSON(http.StatusUnsupportedMediaType, gin.H{"error": "请提交表单"})
			return
		}
		c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, 4096)
		// 显式检查解析错误，不能把超限或损坏的表单当成空字段。
		var err error
		if c.ContentType() == gin.MIMEMultipartPOSTForm {
			err = c.Request.ParseMultipartForm(4096)
			if c.Request.MultipartForm != nil {
				defer c.Request.MultipartForm.RemoveAll()
			}
		} else {
			err = c.Request.ParseForm()
		}
		if err != nil {
			readError(c, err)
			return
		}
		age, exists := c.GetPostForm("age")
		c.JSON(http.StatusOK, gin.H{"name": c.PostForm("name"), "age": age, "age_exists": exists})
	})
	r.POST("/raw", func(c *gin.Context) {
		c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, 4096)
		data, err := io.ReadAll(c.Request.Body)
		if err != nil {
			readError(c, err)
			return
		}
		c.Request.Body = io.NopCloser(bytes.NewReader(data))
		again, err := io.ReadAll(c.Request.Body)
		if err != nil {
			c.JSON(http.StatusInternalServerError, gin.H{"error": "重新读取失败"})
			return
		}
		c.JSON(http.StatusOK, gin.H{"first": string(data), "second": string(again)})
	})
	return r
}

func main() {
	if err := NewRouter().Run("127.0.0.1:8080"); err != nil {
		log.Fatal(err)
	}
}
```

表单接口先显式解析并检查错误，再读取字段。这样请求超过上限时会返回 `413`，而不会悄悄把损坏的表单当成空数据。

`/raw` 演示请求体的读取位置：第一次 `io.ReadAll` 读到了 EOF，接下来从同一个流读通常就没有内容。把字节放进新的 `bytes.Reader`，再用 `io.NopCloser` 适配成 `io.ReadCloser`，才得到一个可从头读取的请求体。原来的字节没有被“删除”，变化的是读取位置。

## 用请求检查几个容易混淆的结果

```powershell
go run .
```

在另一个终端：

```powershell
curl.exe "http://127.0.0.1:8080/users/3?name=&page=&tag=go&tag=web"
curl.exe "http://127.0.0.1:8080/users/3"
curl.exe "http://127.0.0.1:8080/form" --data-urlencode "name=Lin" --data "age=0"
curl.exe "http://127.0.0.1:8080/raw" -H "Content-Type: text/plain" --data-binary "hello"
```

第一条响应中的 `name_exists` 是 `true`，`page` 是 `""`，`tags` 含两个值。第二条的 `name_exists` 是 `false`，`page` 是 `"1"`。表单中的 `age` 仍是字符串 `"0"`；原始请求体示例则返回：

```json
{"first":"hello","second":"hello"}
```

## 为什么接口工具能成功，浏览器却失败

浏览器还受到 Fetch API 和同源策略的约束。浏览器 `fetch` 不允许给 GET 或 HEAD 设置请求体，而某些命令行或接口调试工具允许构造这种请求。浏览器跨域请求也可能先发送 OPTIONS 预检，工具中的一次成功 POST 不代表预检已经配置好。[Fetch 请求体与跨域行为](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)

浏览器原生 WebSocket 构造器同样没有一个通用的“任意请求头”选项。设计认证方式时，不能把调试工具的自定义头能力直接当成浏览器能力。

如果只是想把 JSON 解析为结构体，可以直接使用绑定方法，不必先 `ReadAll` 再恢复请求体。确实要读取原始字节时，先设置上限，并避免把令牌、密码或完整业务正文写进日志。
