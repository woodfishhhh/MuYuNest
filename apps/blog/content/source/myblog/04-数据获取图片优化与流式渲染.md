# 数据获取、图片优化与流式渲染

博客列表通常同时需要三种能力：首屏尽快显示、数据保持新鲜、图片不会拖垮页面。Next.js App Router 与 Convex 可以把这三件事拆开处理：服务器负责首屏数据，客户端负责订阅和交互，`Suspense` 负责把慢区块单独流式传输。

## 1. `useQuery`、`fetchQuery` 与 `preloadQuery`

最直接的客户端写法是：

```tsx
'use client';

const posts = useQuery(api.posts.list);

if (posts === undefined) return <PostListSkeleton />;
return <PostList posts={posts} />;
```

这个方式简单，并且能通过 Convex WebSocket 自动保持实时更新，但首屏需要等待客户端 JavaScript 加载和查询返回。

服务器组件可以直接等待查询：

```tsx
// app/blog/page.tsx
import { fetchQuery } from 'convex/nextjs';

export default async function BlogPage() {
  const posts = await fetchQuery(api.posts.list);
  return <PostList posts={posts} />;
}
```

`fetchQuery` 适合服务器渲染首屏，但它是一次性的服务端读取，不会自动把这个查询订阅到浏览器。需要“服务器先给初始数据，客户端接着实时更新”时，可以使用预加载：

```tsx
// server component
const preloadedPosts = await preloadQuery(api.posts.list);
return <PostList preloadedPosts={preloadedPosts} />;

// client component
const posts = usePreloadedQuery(preloadedPosts);
```

这三者的选型可以记成：

| API | 首屏 | 后续实时更新 | 适合场景 |
| --- | --- | --- | --- |
| `useQuery` | 客户端加载后 | 是 | 纯交互型客户端区域 |
| `fetchQuery` | 服务器直接渲染 | 否 | 静态或一次性数据 |
| `preloadQuery` + `usePreloadedQuery` | 服务器预取 | 是 | 需要 SSR 加速的实时列表 |

Client Component 并不等于“完全不经过服务器”：它仍可以参与初始 HTML 的生成，浏览器拿到 HTML 后再通过 hydration 恢复事件和状态。因此要把客户端组件控制在需要交互的边界，而不是为了方便把整棵页面树都标成 `'use client'`。

## 2. 使用 `next/image` 管理图片

文章卡片中使用远程图片时，优先使用 `Image`：

```tsx
import Image from 'next/image';

<div className="relative h-48 w-full overflow-hidden">
  <Image
    src={post.imageUrl ?? '/placeholder.png'}
    alt={post.title}
    fill
    sizes="(max-width: 768px) 100vw, 33vw"
    className="object-cover"
  />
</div>;
```

`fill` 要求父容器是定位上下文，并且要稳定地给出高度或宽高比。若不使用 `fill`，就为图片提供明确的 `width` 和 `height`。`alt` 应该描述内容，装饰性图片才使用空字符串。

远程域名必须在 `next.config.ts` 中显式允许：

```ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  images: {
    remotePatterns: [
      { protocol: 'https', hostname: '**.convex.cloud' },
      { protocol: 'https', hostname: 'images.unsplash.com' },
    ],
  },
};

export default nextConfig;
```

生产环境使用的 Convex storage host 也必须加入配置。开发环境能显示图片，不代表部署后也能显示；域名、协议或路径限制不匹配时，`next/image` 会直接拒绝加载。

## 3. 用 Suspense 做局部流式渲染

把整个页面都变成一个慢查询，会让导航、标题和骨架一起等待。更好的做法是让页面先渲染稳定外壳，再把数据区放进 `Suspense`：

```tsx
import { Suspense } from 'react';

export default function BlogPage() {
  return (
    <main>
      <BlogHeader />
      <Suspense fallback={<PostListSkeleton />}>
        <AsyncPostList />
      </Suspense>
    </main>
  );
}

async function AsyncPostList() {
  const posts = await fetchQuery(api.posts.list);
  return <PostList posts={posts} />;
}
```

`app/blog/loading.tsx` 适合路由级加载状态；页面内的 `Suspense` 适合更细的边界。边界越小，越容易让用户先看到可用内容，但也要避免把互相依赖的区块拆得过碎。

## 4. 文件上传的完整链路

不要把图片文件直接穿过多个业务函数，也不要把实际文件内容放进文章表。推荐的链路是：

```text
浏览器选择 File
  -> 服务端校验表单和用户身份
  -> Convex 生成一次性 upload URL
  -> 浏览器把文件 POST 到 storage
  -> 取得 storageId
  -> Mutation 写入文章和 storageId
  -> 查询时把 storageId 解析为可访问 URL
```

服务端 Action 的核心步骤如下：

```ts
const file = formData.get('image');
const parsed = imageSchema.safeParse({ image: file });
if (!parsed.success || !(parsed.data.image instanceof File)) {
  return { error: '请选择有效图片' };
}

const uploadUrl = await fetchMutation(api.files.generateImageUploadUrl, {});
const uploadResponse = await fetch(uploadUrl, {
  method: 'POST',
  headers: { 'Content-Type': parsed.data.image.type },
  body: parsed.data.image,
});

if (!uploadResponse.ok) throw new Error('图片上传失败');
const { storageId } = (await uploadResponse.json()) as { storageId: Id<'_storage'> };
await fetchMutation(api.posts.create, { title, body, imageStorageId: storageId });
```

查询文章时再生成 URL：

```ts
const imageUrl = post.imageStorageId
  ? await ctx.storage.getUrl(post.imageStorageId)
  : null;

return { ...post, imageUrl };
```

storage ID 是稳定的业务引用；访问 URL 可能受存储配置、域名和签名策略影响，因此不要把它当作数据库中的永久事实。还应限制 MIME 类型、文件大小，并检查上传响应，不能盲信客户端的文件名或 `Content-Type`。

## 5. 本章检查清单

- 需要实时性的列表使用 `useQuery` 或预加载查询。
- 服务器只需一次读取时使用 `fetchQuery`，避免无意义的客户端订阅。
- `Image` 的父容器有稳定尺寸，远程 host 同时覆盖开发和生产。
- 慢查询被放在合适的 `Suspense` 边界内。
- 数据库只保存 `storageId`，不保存临时或环境相关的图片 URL。
- 上传前后都校验用户、类型、大小和 HTTP 响应。
