# NestJS 配置、关联查询与生产部署

这部分课程把一个“本机能跑”的 NestJS 项目继续推到可以部署的状态。前半段补齐开发、测试环境隔离和 Report 业务，后半段处理授权、复杂查询、Migration 与生产配置。几块内容看似分散，实际都围绕同一个问题：请求进入应用后，配置、身份、数据和数据库结构分别由谁负责。

文中的代码是按课程思路重写的教学版，不是视频代码的逐字抄录。课程使用的 TypeORM CLI 与 Heroku 流程带有明显的版本背景，实际项目应以当前依赖和托管平台文档为准。

## 1. 用 ConfigModule 隔离开发与测试环境

开发库和测试库不能共用。端到端测试会创建、删除数据，如果它连接到开发库，测试结果会受旧数据影响，也可能把手工调试的数据清掉。

课程为两个环境分别准备文件：

```dotenv
DB_NAME=db.sqlite
COOKIE_KEY=dev-only-secret
```

```dotenv
DB_NAME=test.sqlite
COOKIE_KEY=test-only-secret
```

这两个文件应加入 `.gitignore`。生产环境不依赖仓库里的 `.env.production`，而是由部署平台注入真正的环境变量。

`ConfigModule` 负责加载文件并把配置放进 Nest 的依赖注入系统，`TypeOrmModule.forRootAsync()` 再从 `ConfigService` 读取数据库名：

```ts
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      envFilePath: `.env.${process.env.NODE_ENV}`,
    }),
    TypeOrmModule.forRootAsync({
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        type: "sqlite",
        database: config.getOrThrow<string>("DB_NAME"),
        entities: [User, Report],
        synchronize: true, // 只用于课程早期的本地开发阶段
      }),
    }),
  ],
})
export class AppModule {}
```

文件名依赖 `NODE_ENV`，所以启动命令必须明确环境。`cross-env` 可以让同一条脚本兼容 Windows、macOS 和 Linux：

```json
{
  "scripts": {
    "start:dev": "cross-env NODE_ENV=development nest start --watch",
    "test:e2e": "cross-env NODE_ENV=test jest --config ./test/jest-e2e.json --maxWorkers=1"
  }
}
```

`--maxWorkers=1` 是 SQLite 场景下的现实选择。多个 Jest worker 同时打开同一个文件数据库，很容易遇到 `SQLITE_BUSY: database is locked`。这不是所有数据库都必须串行，而是测试基础设施与 SQLite 并发能力之间的取舍。

文件数据库只能在 TypeORM 建立连接前删除。应用已经初始化后继续删文件，连接仍握着旧文件句柄，Windows 上还可能直接报占用错误。可以在整组 E2E 启动前重置一次文件，再在每个用例前清表：

```ts
import { rm } from "node:fs/promises";
import { join } from "node:path";
import { DataSource } from "typeorm";

const testDb = join(process.cwd(), "test.sqlite");
let app!: INestApplication;

beforeAll(async () => {
  await rm(testDb, { force: true });

  const moduleRef = await Test.createTestingModule({
    imports: [AppModule],
  }).compile();

  app = moduleRef.createNestApplication();
  await app.init();
});

beforeEach(async () => {
  const dataSource = app.get(DataSource);
  await dataSource.getRepository(Report).clear();
  await dataSource.getRepository(User).clear();
});

afterAll(() => app.close());
```

有关联外键时先清从表，再清主表。也可以为每个用例重建 schema，或让用例运行在事务里并在结束后回滚。如果确实要逐用例删除 SQLite 文件，必须先关闭应用和 DataSource，再删文件、重建连接；项目改用 Migration 后，新库还要先执行迁移。

## 2. Report 从 DTO 进入数据库

Report 记录车辆成交信息，包括品牌、型号、年份、里程、经纬度和价格。请求体先由 DTO 做运行时校验，再交给 Service 创建实体。TypeScript 类型只约束源码，真正来自客户端的数据仍需要 `class-validator`。

```ts
export class CreateReportDto {
  @IsString()
  make!: string;

  @IsString()
  model!: string;

  @IsInt()
  @Min(1930)
  @Max(2050)
  year!: number;

  @IsNumber()
  @Min(0)
  mileage!: number;

  @IsLongitude()
  lng!: number;

  @IsLatitude()
  lat!: number;

  @IsNumber()
  @Min(0)
  price!: number;
}
```

Controller 只处理 HTTP 边界，Service 负责组装和保存实体。创建报告需要登录，因此当前用户也是业务输入的一部分：

```ts
@Post()
@UseGuards(AuthGuard)
createReport(
  @Body() body: CreateReportDto,
  @CurrentUser() user: User,
) {
  return this.reportsService.create(body, user);
}
```

```ts
async create(dto: CreateReportDto, user: User): Promise<Report> {
  const report = this.repo.create({
    ...dto,
    user,
    userId: user.id,
  });
  return this.repo.save(report);
}
```

## 3. Report 与 User 的关联

一个用户可以提交多份报告，每份报告只属于一个用户，因此关系是 `User 1 -> N Report`：

```ts
// user.entity.ts
@OneToMany(() => Report, (report) => report.user)
reports!: Report[];
```

```ts
// report.entity.ts
@Column()
userId!: number;

@ManyToOne(() => User, (user) => user.reports, { nullable: false })
user!: User;
```

`ManyToOne` 所在的 Report 是持有外键的一侧。这里把与默认关联列同名的 `userId` 显式映射为普通字段，查询报告时无需加载整个 User 也能取得外键。装饰器参数写成 `() => User`，可以推迟实体求值，避开两个实体文件互相导入时的循环依赖问题。

关联不会保证每次查询都自动加载。需要用户详情时仍要显式使用 `relations` 或 `leftJoinAndSelect`；只返回归属 ID 时直接读取 `report.userId`。

响应也不应把整个 User 原样返回，否则密码字段可能跟着实体一起泄漏。课程用响应 DTO 把关联压成 `userId`：

```ts
export class ReportDto {
  @Expose()
  id!: number;

  @Expose()
  make!: string;

  @Expose()
  model!: string;

  @Expose()
  price!: number;

  @Expose()
  userId!: number;
}
```

DTO 不再假定 `report.user` 已加载，因此不会因为缺少 relation 而在序列化时访问 `undefined.id`。输出字段仍由白名单决定，实体以后新增敏感字段也不会自动出现在响应中。

## 4. 审批是授权问题，不是登录问题

新报告默认 `approved = false`，管理员审核后才允许进入估价样本。这样可以避免普通用户批量提交虚假价格，直接污染查询结果。

```ts
@Column({ default: false })
approved!: boolean;
```

身份认证回答“请求是谁发的”，授权回答“这个人能不能执行当前操作”。`AuthGuard` 只能证明用户已登录；审批接口还需要 `AdminGuard`：

```ts
@Injectable()
export class AdminGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest<Request>();
    return Boolean(request.currentUser?.admin);
  }
}
```

课程在这里遇到一个很典型的顺序问题。简化后的请求链是：

```text
middleware -> guard -> interceptor -> pipe/controller -> response interceptor
```

如果 `currentUser` 是在 interceptor 里查询并写入请求对象的，Guard 执行时它还不存在，管理员请求也会被拒绝。解决办法是把“根据 session 找用户”的逻辑前移到 middleware：

```ts
@Injectable()
export class CurrentUserMiddleware implements NestMiddleware {
  constructor(private readonly usersService: UsersService) {}

  async use(req: Request, _res: Response, next: NextFunction) {
    const userId = req.session?.userId;
    if (userId) {
      req.currentUser = await this.usersService.findOne(userId);
    }
    next();
  }
}
```

Express 的 `Request` 默认没有 `currentUser`，不要用 `@ts-ignore` 掩盖。通过声明合并补上类型：

```ts
declare global {
  namespace Express {
    interface Request {
      currentUser?: User;
    }
  }
}
```

中间件负责准备请求上下文，Guard 只做准入判断，Interceptor 更适合响应格式化、日志和调用前后增强。三者按职责使用，比“哪个装饰器顺手就放哪里”更不容易踩执行顺序的坑。管理员字段的默认值也必须是 `false`；课程暂时设成 `true` 只是为了演示，不能带到真实系统。

## 5. 用 QueryBuilder 做估价查询

估价接口从查询字符串接收品牌、型号、年份、里程和经纬度。查询字符串里的值最初都是字符串，即使 URL 中写的是 `year=2020`。DTO 要先转换，再验证：

```ts
export class GetEstimateDto {
  @IsString()
  make!: string;

  @IsString()
  model!: string;

  @Transform(({ value }) => Number(value))
  @IsInt()
  year!: number;

  @Transform(({ value }) => Number(value))
  @IsNumber()
  mileage!: number;

  @Transform(({ value }) => Number(value))
  @IsLongitude()
  lng!: number;

  @Transform(({ value }) => Number(value))
  @IsLatitude()
  lat!: number;
}
```

普通 `find()` 适合简单等值条件；估价需要范围过滤、排序和限制数量，用 QueryBuilder 更清楚。下面先找出里程最接近的三份已审批报告，再在应用层计算均价，避免“先聚合还是先 limit”的 SQL 歧义：

```ts
async createEstimate(dto: GetEstimateDto) {
  const { make, model, year, mileage, lng, lat } = dto;

  const reports = await this.repo
    .createQueryBuilder("report")
    .where("report.make = :make", { make })
    .andWhere("report.model = :model", { model })
    .andWhere("ABS(report.lng - :lng) <= 5", { lng })
    .andWhere("ABS(report.lat - :lat) <= 5", { lat })
    .andWhere("ABS(report.year - :year) <= 3", { year })
    .andWhere("report.approved = :approved", { approved: true })
    .orderBy("ABS(report.mileage - :mileage)", "ASC")
    .setParameter("mileage", mileage)
    .take(3)
    .getMany();

  if (reports.length === 0) return { price: null };

  const total = reports.reduce((sum, report) => sum + report.price, 0);
  return { price: total / reports.length };
}
```

参数要通过 `:make`、`:year` 这类占位符绑定，不能把用户输入直接拼进 SQL。第一次调用用 `where()`，后续条件用 `andWhere()`；再次调用 `where()` 会覆盖前面的过滤条件。课程里的正负 5 度、正负 3 年和三条样本只是教学规则，不是可靠的车辆估值模型。

## 6. 关闭 synchronize，改用 Migration

`synchronize: true` 会在应用启动时比较 Entity 和数据库结构，并自动改表。开发早期很省事，但生产环境里一次误删实体字段就可能让 TypeORM 删除整列及其数据。

开始维护真实数据后应把它固定为 `false`，结构变更交给 Migration：

```text
修改 Entity
  -> 生成并检查 migration
  -> 在测试库执行
  -> 备份生产库
  -> 在生产库执行
  -> 启动新版本应用
```

Migration 的 `up()` 描述如何前进，`down()` 描述如何回滚。生成文件不是最终答案，提交前仍要检查列类型、默认值、非空约束、索引和回滚逻辑。

课程版本通过根目录的 `ormconfig.js` 同时给 Nest 应用和 TypeORM CLI 提供配置，并按 `NODE_ENV` 切换 `.entity.ts` 与编译后的 `.entity.js`。这里真正值得记住的是：数据库配置应由应用和 CLI 共享，不能在 `AppModule` 与 CLI 配置中各复制一份。当前 TypeORM 常用 `DataSource` 文件解决同一问题，具体命令要跟随项目安装的版本。

测试环境删除数据库后需要自动运行 Migration；生产环境则更适合把迁移放在独立发布步骤中。小型单实例项目可以在启动时 `migrationsRun: true`，多实例部署若同时抢着迁移，风险会明显增大。

## 7. 生产配置与部署边界

生产环境通常换成 PostgreSQL，并由平台提供 `DATABASE_URL`。Cookie 密钥、数据库地址等秘密都由环境变量注入：

```ts
const productionOptions = {
  type: "postgres" as const,
  url: process.env.DATABASE_URL,
  synchronize: false,
  ssl: { rejectUnauthorized: false }, // 是否需要取决于数据库服务商
};
```

服务器也不能写死端口，托管平台会在运行时分配：

```ts
await app.listen(Number(process.env.PORT ?? 3000));
```

一条完整的部署链至少包含：

1. 安装依赖并编译 TypeScript。
2. 校验必需环境变量，缺失时直接启动失败。
3. 对目标数据库执行已审查的 Migration。
4. 用 `start:prod` 启动编译后的 JavaScript。
5. 检查健康接口、日志和数据库连接。

课程最后使用 Heroku、`Procfile`、Heroku Postgres 和 Git push 部署。这一段适合用来理解“平台注入端口、数据库 URL 和秘密”的机制，不宜直接把当年的套餐名与命令当成今天仍有效的部署说明。换成 Render、Railway、云服务器或容器平台，配置边界仍然相同。

## 常见坑

- `NODE_ENV` 没设置，应用会尝试加载 `.env.undefined`，错误往往拖到读取配置时才出现。
- 开发和测试共用数据库，测试会受脏数据影响；并行 Jest 连接 SQLite 还可能触发锁错误。
- 删除测试数据库后没有执行 Migration，应用能连上文件，却找不到任何表。
- 以为 `@OneToMany` 会自动加载数据；关系是否加载由查询决定。
- 把 `currentUser` 放在 Interceptor 中，却让 Guard 依赖它，执行顺序必然出错。
- 把新用户默认设为管理员，演示代码因此变成权限漏洞。
- 忘记查询字符串都是字符串，DTO 类型写成 `number` 也不会自动改变运行时值。
- 多次调用 `where()` 覆盖旧条件，或直接拼接 SQL 导致注入风险。
- 估价查询漏掉 `approved = true`，未审核的虚假报告会进入样本。
- 生产环境继续使用 `synchronize: true`，一次实体改动就可能破坏数据。
- CLI 和应用各维护一份数据库配置，时间久了必然出现环境漂移。

## 上线前检查清单

- [ ] 开发、测试、生产使用不同数据库和不同密钥。
- [ ] `.env.*` 已忽略，仓库中没有 Cookie key、数据库密码或连接串。
- [ ] 全局 ValidationPipe 已开启，查询参数完成转换后再验证。
- [ ] Report 创建接口要求登录，审批接口同时要求管理员权限。
- [ ] User 响应与 Report 响应都不会暴露密码等敏感字段。
- [ ] 估价只读取已审批数据，空样本返回值有明确约定。
- [ ] 所有环境的 `synchronize` 均为 `false`。
- [ ] Migration 已在空库、已有数据的测试库和回滚流程中验证。
- [ ] 生产端口读取 `PORT`，数据库读取 `DATABASE_URL`。
- [ ] 部署后已检查健康接口、日志、数据库连接和一次完整业务请求。
