# NestJS 完全开发指南（4）：认证、授权与自动化测试

认证系统常被写成一大团：查用户、比密码、写 Cookie、判断权限，全挤在 Controller 里。课程采用了更容易测试的拆法：`AuthService` 只验证身份，Controller 负责修改 Session，`CurrentUser` 负责把当前用户送进处理器，Guard 决定请求能不能继续。

```text
注册：检查邮箱 -> 哈希密码 -> 创建用户 -> Session 记住 userId
登录：查找用户 -> 校验密码 -> Session 记住 userId
后续请求：读取 Session -> 查当前用户 -> Guard 放行或拒绝
```

认证和授权也要分开。认证回答“你是谁”，登录成功只说明凭据匹配；授权回答“你能做什么”，即使已经登录，也不代表能修改别人的资料或审批报告。Session 是两者之间的身份凭证，不是权限表。后续做角色或资源所有权校验时，应在 Guard 或业务 Service 中基于当前用户判断，不能把“Cookie 存在”当成全部安全条件。

## 一、密码存的是哈希，不是“加密后的原文”

密码不能明文入库，也不应该使用可逆加密。注册时保存 `salt.hash`；登录时取出 salt，用用户本次提交的密码重新计算，再比较两次哈希。

```ts
import {
  randomBytes,
  scrypt as scryptCallback,
  timingSafeEqual,
} from 'node:crypto';
import { promisify } from 'node:util';

const scrypt = promisify(scryptCallback);

async function hashPassword(password: string) {
  const salt = randomBytes(16).toString('hex');
  const hash = (await scrypt(password, salt, 32)) as Buffer;
  return `${salt}.${hash.toString('hex')}`;
}

async function verifyPassword(password: string, stored: string) {
  const [salt, storedHex] = stored.split('.');
  if (!salt || !storedHex) return false;

  const actual = (await scrypt(password, salt, 32)) as Buffer;
  const expected = Buffer.from(storedHex, 'hex');

  return (
    actual.length === expected.length &&
    timingSafeEqual(actual, expected)
  );
}
```

salt 不需要保密。它的作用是让相同密码产生不同哈希，降低彩虹表和批量破解的收益。比较时使用 `timingSafeEqual`，避免普通字符串比较泄露过多时序信息。

密码哈希函数还应刻意设置计算成本。普通通用哈希追求快，正好方便攻击者每秒尝试大量密码；`scrypt`、Argon2、bcrypt 这类密码哈希算法会消耗更多时间和内存。参数不是越大越好，需要在服务器负载和攻击成本之间做基准测试。课程使用 Node 内置 `scrypt`，少一个第三方依赖，也足够说明完整流程。

注册成功后也不要记录明文密码到日志。排查问题时只记用户 ID、请求 ID 和失败阶段，最多记录邮箱的脱敏形式。异常监控、HTTP access log、测试快照都可能成为新的泄露位置，密码只在当前请求内短暂存在。

AuthService 只处理“这个凭据是否成立”，不直接碰 Session：

```ts
@Injectable()
export class AuthService {
  constructor(private readonly usersService: UsersService) {}

  async signup(email: string, password: string) {
    const existing = await this.usersService.findOneByEmail(email);
    if (existing) {
      throw new BadRequestException('邮箱已被使用');
    }

    const passwordHash = await hashPassword(password);
    return this.usersService.create(email, passwordHash);
  }

  async signin(email: string, password: string) {
    const user = await this.usersService.findOneByEmail(email);
    const matched = user
      ? await verifyPassword(password, user.password)
      : false;

    if (!user || !matched) {
      throw new UnauthorizedException('邮箱或密码错误');
    }

    return user;
  }
}
```

课程分别返回“用户不存在”和“密码错误”，教学时更直观；公开接口通常合并成同一句，避免帮助攻击者枚举已注册邮箱。数据库仍要给邮箱加唯一约束，因为“先查再写”挡不住两个并发注册请求。

把 Session 留在 Controller 还有一个好处：AuthService 可以在没有 HTTP 的场景复用。命令行管理工具、消息消费者或 GraphQL resolver 都能调用 `signup`、`signin`，而不需要伪造 Cookie 对象。测试 AuthService 时也只需要准备用户依赖，不必把整个 Web 请求环境搭起来。

## 二、Session 只记录身份线索

课程使用 `cookie-session`。它把 Session 数据放在客户端 Cookie 中，并用签名防篡改。这里要纠正字幕里一个容易误解的说法：默认 Cookie 是签名，不等于内容加密，用户仍可能看到内容。因此只放 `userId` 这类最小信息，不要放密码、令牌或隐私数据。

```ts
type AuthSession = {
  userId?: number | null;
};

@Serialize(UserDto)
@Post('signup')
async signup(
  @Body() body: CreateUserDto,
  @Session() session: AuthSession,
) {
  const user = await this.authService.signup(body.email, body.password);
  session.userId = user.id;
  return user;
}

@Serialize(UserDto)
@Post('signin')
async signin(
  @Body() body: SigninDto,
  @Session() session: AuthSession,
) {
  const user = await this.authService.signin(body.email, body.password);
  session.userId = user.id;
  return user;
}

@Post('signout')
signout(@Session() session: AuthSession) {
  session.userId = null;
}
```

Cookie 密钥必须来自环境变量。生产环境还要设置 `httpOnly`、`sameSite`，HTTPS 下打开 `secure`，并评估 CSRF 防护。若 Session 内容变多、需要服务端撤销或多端管理，通常会换成 `express-session` 加 Redis，而不是继续扩大客户端 Cookie。

一次登录后的请求实际会走四步：浏览器自动带上 Cookie；中间件验证签名并还原 Session；代码从 Session 读出 `userId`；需要用户详情时再查数据库。Cookie 只证明这份 Session 没被随意篡改，不保证账号仍有效。用户被删除、封禁或修改安全状态后，数据库查询仍应成为最终依据。

## 三、`CurrentUser` 为什么需要 Interceptor

自定义参数装饰器能读取请求，却不能自行从 DI 容器取得 `UsersService`。课程的处理方式是让可注入的 Interceptor 先查用户，把结果挂到 request，再由装饰器取出来。

```ts
interface RequestWithUser extends Request {
  session?: AuthSession;
  currentUser?: User | null;
}

@Injectable()
export class CurrentUserInterceptor implements NestInterceptor {
  constructor(private readonly usersService: UsersService) {}

  async intercept(context: ExecutionContext, next: CallHandler) {
    const request = context
      .switchToHttp()
      .getRequest<RequestWithUser>();

    const userId = request.session?.userId;
    request.currentUser = userId
      ? await this.usersService.findOne(userId)
      : null;

    return next.handle();
  }
}

export const CurrentUser = createParamDecorator(
  (_: unknown, context: ExecutionContext) =>
    context.switchToHttp().getRequest<RequestWithUser>().currentUser,
);
```

把它注册为全局 Interceptor 后，任何 Controller 都可以写：

```ts
@Serialize(UserDto)
@Get('whoami')
whoAmI(@CurrentUser() user: User | null) {
  return user;
}
```

```ts
{
  provide: APP_INTERCEPTOR,
  useClass: CurrentUserInterceptor,
}
```

全局注册写起来方便，但每个带 Session 的请求都可能多查一次数据库，即使当前路由根本不用用户。项目大了以后，可以只给需要的 Controller 使用，或把“解析当前用户”合并进认证 Guard，再缓存到 request。

`CurrentUser` 不是新的数据来源，它只是把重复的取值动作封装起来。业务代码仍应把 `User | null` 当成真实类型，而不是因为加了装饰器就假定一定有用户。公开路由允许 `null`；受保护路由由 Guard 先拦截，处理器里才可以使用非空的 `User`。这种类型约定能少掉一批运行时的 `cannot read property of null`。

## 四、Guard 管“能不能进”，不管“返回什么”

Guard 的 `canActivate` 返回真就放行；缺少登录身份时，这里主动抛出 `UnauthorizedException`，让客户端得到语义明确的 401：

```ts
@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext) {
    const request = context
      .switchToHttp()
      .getRequest<RequestWithUser>();

    if (!request.session?.userId) {
      throw new UnauthorizedException('请先登录');
    }

    return true;
  }
}
```

```ts
@UseGuards(AuthGuard)
@Serialize(UserDto)
@Get('profile')
getProfile(@CurrentUser() user: User) {
  return user;
}
```

这里只证明 Cookie 里有 ID，没有证明对应用户仍存在。对敏感接口，Guard 可以注入 `UsersService` 再查一次，并把用户挂到 request。要留意 Nest 的顺序：Guard 在路由 Interceptor 之前执行，所以 Guard 不能依赖后面的 `CurrentUserInterceptor` 已经完成查询。

## 五、单元测试：Mock 到哪里为止

测试 AuthService 时，目标是验证注册、登录的业务逻辑。数据库不在这个测试的范围内，因此把 `UsersService` 替换成 Mock；密码哈希正是被测逻辑的一部分，不要顺手也 Mock 掉。

```ts
type UsersPort = Pick<
  UsersService,
  'findOneByEmail' | 'create'
>;

describe('AuthService', () => {
  let service: AuthService;
  let users: jest.Mocked<UsersPort>;

  beforeEach(async () => {
    users = {
      findOneByEmail: jest.fn(),
      create: jest.fn(),
    };

    const module = await Test.createTestingModule({
      providers: [
        AuthService,
        { provide: UsersService, useValue: users },
      ],
    }).compile();

    service = module.get(AuthService);
  });

  it('注册时不会把明文密码交给持久化层', async () => {
    users.findOneByEmail.mockResolvedValue(null);
    users.create.mockImplementation(async (email, password) =>
      ({ id: 1, email, password }) as User,
    );

    const user = await service.signup('a@example.com', 'secret123');

    expect(user.password).not.toBe('secret123');
    expect(user.password.split('.')).toHaveLength(2);
  });

  it('邮箱已存在时拒绝注册', async () => {
    users.findOneByEmail.mockResolvedValue({ id: 1 } as User);

    await expect(
      service.signup('a@example.com', 'secret123'),
    ).rejects.toThrow(BadRequestException);
  });
});
```

课程早期使用 `try/catch + done` 测异步异常；现代 Jest 直接用 `await expect(promise).rejects` 更短，也不会因为忘记调用 `done` 等到超时。

Mock 的边界可以这样判断：

- 测 AuthService：Mock UsersService，保留真实哈希逻辑。
- 测 Controller：Mock AuthService，只断言参数转交、返回值和 Session 是否被修改。
- 测装饰器、Pipe、Guard、Cookie：别硬塞进 Controller 单元测试，交给 E2E。
- 被测流程需要“先注册再登录”时，可以写一个小型内存 Fake；只验证单个分支时，用 `mockResolvedValue` 更直接。
- Mock 只实现被测对象实际调用的方法，并保持异步返回、参数和错误行为与真实依赖一致。

单元测试最好断言可观察行为，不要把实现步骤全部焊死。注册测试关心传给持久化层的密码不再是明文、重复邮箱会失败；没有必要断言 `randomBytes` 被调用了几次。登录测试关心正确密码能返回用户、错误密码会拒绝；不必把哈希函数内部每一行都 Mock。否则一次不改变行为的重构，也会让整套测试跟着碎。

课程还展示了两种 Fake。第一种是每个方法返回固定值，适合“用户不存在”“重复邮箱”这种单分支测试；第二种在数组里真正保存用户，适合“先注册，再用同一密码登录”的连续场景。选择标准不是哪种更高级，而是哪种用更少代码准确表达当前场景。Fake 一旦开始复制数据库查询、唯一约束和事务，就已经越过了单元测试边界。

Controller 单元测试不经过 Nest 的路由管线。直接调用 `controller.signin(body, session)`，能测 `session.userId` 是否改变，却证明不了 `@Body()`、ValidationPipe 或 Cookie 中间件真的工作。这正是 E2E 要补上的部分。

可以先列一张测试责任表，再决定用哪种测试，避免每层重复验证同一件事：

| 行为 | 单元测试 | E2E |
| --- | --- | --- |
| 密码不以明文保存 | AuthService | 可补一条响应不泄露密码 |
| Session 写入 `userId` | Controller | 用 Cookie 跨请求验证 |
| DTO 拒绝非法邮箱 | 不测装饰器 | 发送非法 HTTP 请求断言 400 |
| Guard 拒绝游客 | 可单测 `canActivate` | 请求受保护路由断言 401 |
| Repository 真能写库 | 不用 Mock 猜 | 使用隔离测试库验证 |

这张表的重点是“最便宜且能证明该行为的层级”。不是每个方法都要有单元测试，也不是所有分支都要跑完整 E2E。

## 六、E2E：启动真实 Nest 应用再发 HTTP 请求

E2E 测试从 `AppModule` 创建应用，使用 Supertest 发请求。需要跨请求保留 Cookie 时必须用 `request.agent`：

```ts
describe('Auth e2e', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const module = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = module.createNestApplication();
    await app.init();
  });

  afterAll(() => app.close());

  it('注册、退出并重新登录', async () => {
    const agent = request.agent(app.getHttpServer());
    const email = 'e2e@example.com';

    await agent
      .post('/auth/signup')
      .send({ email, password: 'secret123' })
      .expect(201)
      .expect(({ body }) => {
        expect(body.id).toBeDefined();
        expect(body.email).toBe(email);
        expect(body.password).toBeUndefined();
      });

    await agent.post('/auth/signout').expect(201);
    await agent
      .post('/auth/signin')
      .send({ email, password: 'secret123' })
      .expect(201)
      .expect(({ body }) => {
        expect(body.email).toBe(email);
        expect(body.password).toBeUndefined();
      });

    await agent
      .get('/auth/whoami')
      .expect(200)
      .expect(({ body }) => {
        expect(body.email).toBe(email);
        expect(body.password).toBeUndefined();
      });
  });
});
```

课程遇到的第一个 E2E 故障很典型：开发时在 `main.ts` 里注册了 Cookie 中间件和全局 ValidationPipe，但测试直接从 `AppModule` 建应用，根本不会执行 `main.ts`，于是 `session` 是 `undefined`，校验也悄悄消失。

排查这种 500 时不要只看 `.expect(201)` 的失败信息。先向上找到服务端真正抛出的异常，再比较开发启动路径和测试启动路径。E2E 创建出的不是“天然完整”的应用，它只包含测试代码实际导入和配置的部分。全局前缀、过滤器、Pipe、CORS、Session 等只要留在 `main.ts`，都有可能在测试中缺席。

一种处理方式是把全局能力接回模块：

```ts
@Module({
  providers: [
    {
      provide: APP_PIPE,
      useValue: new ValidationPipe({
        whitelist: true,
        transform: true,
      }),
    },
  ],
})
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(
        cookieSession({
          keys: [process.env.COOKIE_KEY!],
          httpOnly: true,
          sameSite: 'lax',
        }),
      )
      .forRoutes('{*splat}');
  }
}
```

NestJS 11 使用 path-to-regexp v8，全路由通配要写成 `'{*splat}'`；旧版 Nest 项目里常见的 `'*'` 写法不要直接照搬。另一种同样实用的做法是写一个共享 `configureApp(app)`，由 `main.ts` 和 E2E 同时调用。重点不是选哪种形式，而是开发环境和测试环境必须走同一套应用配置。

## 七、测试数据库必须和开发库分开

如果 E2E 直接使用 `db.sqlite`，第一次注册能通过，第二次跑同一个邮箱就会得到 400；更糟的是，测试还会污染手工调试的数据。最少要做到两件事：

1. 测试使用独立数据库，例如 `test.sqlite` 或 SQLite `:memory:`。
2. 每个测试前清空表、重建 schema，或用事务回滚，保证用例互不依赖。

```ts
TypeOrmModule.forRootAsync({
  useFactory: () => {
    const testing = process.env.NODE_ENV === 'test';

    return {
      type: 'sqlite' as const,
      database: testing ? 'test.sqlite' : 'db.sqlite',
      entities: [User],
      synchronize: true,
      dropSchema: testing,
    };
  },
});
```

`dropSchema` 适合课程里的小型测试库，不要用于生产。测试并行后，多个 Jest worker 共用一个文件也会互相干扰，可以给每个 worker 单独的数据库，或者使用独立容器和事务回滚。

测试数据隔离还决定了用例能否独立阅读。一个“登录成功”用例应在自己的准备阶段创建用户，不能依赖“注册成功”用例恰好先运行。测试框架可能调整顺序，也可能只运行单个文件。每个用例自己准备数据、自己清理，失败才不会随着执行顺序飘来飘去。

## 八、常见坑与调试顺序

### 1. E2E 中 `session` 是 `undefined`

检查测试是否跳过了 `main.ts` 中的配置。确认 Cookie 中间件在 `app.init()` 前注册，并查看请求是否收到 `Set-Cookie`。

### 2. 登录成功，下一次请求仍像未登录

Supertest 的普通 `request(app)` 不会自动替不同请求保存 Cookie。改用 `request.agent(app)`，或手动把 `set-cookie` 回传。

### 3. Guard 总是返回 401

先看 Cookie 有没有到服务端，再看 Session 中字段名是否一致：`userId`、`user_id` 混用很常见。这里缺少登录身份会主动抛 `UnauthorizedException`，所以应返回 401；若看到 403，通常说明 Guard 仍在简单返回 `false`。最后确认 Guard 是检查 Session，还是错误地依赖了尚未执行的 Interceptor。

### 4. 注销后却查到了第一个用户

不要把 `null` 或 `undefined` 继续传给查询。`findOne` 在收到空 ID 时应直接返回 `null`，Controller 和 CurrentUser Interceptor 也要先判断 Session。

### 5. 单元测试通过，接口校验却坏了

直接调用 Controller 方法不会运行装饰器、Pipe 和 Guard。给关键路由补一条 E2E，真正发送非法请求体并断言 400。

### 6. Mock 越写越像第二套业务代码

先缩小 Mock 边界。静态返回值能表达场景时不要造内存数据库；只有“先写后读”的连续流程确实需要状态时，再使用内存 Fake。

### 7. E2E 只能成功运行一次

这通常不是随机邮箱的问题，而是测试隔离没做好。检查测试库是否独立、每个用例前是否清理，以及 Jest 并行 worker 是否在共享同一个 SQLite 文件。

这套结构的好处会在测试里直接体现出来：哈希逻辑能单测，Session 变化能在 Controller 测，Cookie、Pipe、Guard 和序列化则由 E2E 一次串起来。每层只证明自己该证明的事，失败时也更容易知道该从哪一层查。

上线前还应补上登录限流、密码策略、密钥轮换、Session 过期和安全日志；这些属于生产安全配置，不应靠课程里的最小示例默认具备。
