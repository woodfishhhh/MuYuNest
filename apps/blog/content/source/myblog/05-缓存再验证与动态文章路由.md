# 缓存、再验证与动态文章路由

博客首页和文章详情页的访问模式不同：首页适合缓存一段时间，文章详情需要根据 ID 查询，发布文章后又要主动让列表失效。缓存设计的关键不是“所有东西都缓存”，而是明确数据的新鲜度和失效入口。

## 1. 时间再验证与按需再验证

传统的 ISR 思路是为路由设置一个时间窗口：

```ts
export const revalidate = 30;
```

这表示缓存内容最多在一段时间后重新生成。它适合变化不频繁、允许短暂陈旧的页面。发布文章后，如果希望列表马上出现，可以在写入成功后执行按需再验证：

```ts
import { revalidatePath } from 'next/cache';

await fetchMutation(api.posts.create, input);
revalidatePath('/blog');
```

`revalidatePath` 是路由级失效，适合“某个页面整体需要重新生成”的场景。后面引入 Cache Components 后，还可以通过 tag 精确失效某类数据，不要把两种模型混在一起却没有明确规则。Next.js 版本演进较快，使用 Cache Components 时要以当前版本文档为准，避免盲目叠加旧的 route segment 配置。

## 2. 动态路由和异步 `params`

文章详情页可以放在：

```text
app/blog/[postId]/page.tsx
```

Next.js 16 中，动态参数按异步值处理：

```tsx
import { notFound } from 'next/navigation';
import { fetchQuery } from 'convex/nextjs';
import type { Id } from '@/convex/_generated/dataModel';

type Props = {
  params: Promise<{ postId: Id<'posts'> }>;
};

export default async function PostPage({ params }: Props) {
  const { postId } = await params;
  const post = await fetchQuery(api.posts.getById, { postId });

  if (!post) notFound();
  return <PostDetail post={post} />;
}
```

`Id<'posts'>` 只提供 TypeScript 类型约束，不会在运行时验证字符串。来自 URL 的 ID 仍然可能是恶意输入，Convex 函数需要处理无效 ID、找不到文章和无权限访问等情况。

数据库函数通常只接受一个 ID，并把存储图片解析为最终 URL：

```ts
export const getById = query({
  args: { postId: v.id('posts') },
  handler: async (ctx, { postId }) => {
    const post = await ctx.db.get(postId);
    if (!post) return null;

    return {
      ...post,
      imageUrl: post.imageStorageId
        ? await ctx.storage.getUrl(post.imageStorageId)
        : null,
    };
  },
});
```

## 3. 详情页的数据与展示边界

详情页常见的渲染结构是：

```tsx
<article>
  <h1>{post.title}</h1>
  <time dateTime={post.createdAt.toISOString()}>
    {formatDate(post.createdAt)}
  </time>
  {post.imageUrl && (
    <div className="relative aspect-video overflow-hidden">
      <Image src={post.imageUrl} alt={post.title} fill className="object-cover" />
    </div>
  )}
  <MarkdownContent>{post.body}</MarkdownContent>
</article>
```

发布时间、作者和正文是服务端可直接渲染的内容；评论输入框、点赞、在线状态等需要事件或实时数据的区域，再单独下沉为 Client Component。这样既保留首屏速度，也避免给整页增加 hydration 成本。

## 4. 选择缓存策略的判断表

| 数据 | 推荐策略 | 失效方式 |
| --- | --- | --- |
| 博客导航和稳定配置 | 长时间缓存 | 配置改变时按需失效 |
| 文章列表 | 短时间缓存或按 tag 缓存 | 创建/删除文章后失效 |
| 文章详情 | 按 ID 查询，可缓存 | 更新文章后失效对应路径或 tag |
| 当前用户、权限、实时评论 | 动态/实时查询 | 会话或数据库更新驱动 |

不要为了让构建通过而把所有页面强行变成静态。更可靠的做法是先标注每个数据源的生命周期，再决定它应该在哪一层缓存。

## 5. 本章检查清单

- 明确页面允许陈旧多久，以及谁负责触发失效。
- 动态 `params` 先 `await`，不要沿用旧版本的同步写法。
- URL 参数仍需运行时校验，TypeScript 类型不能替代鉴权。
- 文章不存在时返回 `notFound()`，而不是渲染一张空白详情页。
- 互动区域与服务端内容分离，避免整页客户端化。
