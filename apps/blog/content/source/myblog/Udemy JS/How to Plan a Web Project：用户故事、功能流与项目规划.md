## 一、项目规划的重要性（核心前提）

### 1.1 规划的必要性

- 复杂一点的项目（比如这门课的 Mapty 锻炼记录项目），写代码前先规划，能避免后面代码乱成一团、功能漏掉。
- 之前课上的项目大多直接开写，没怎么考虑功能逻辑和架构；实际开发里"先规划再开发"才是标准流程，能少返工。

### 1.2 规划的适用场景

- 适合中小型 Web 项目（这门课推荐的流程）；大型项目可以在这个基础上再加需求评审、技术选型评审这些环节。

## 二、Web 项目规划四步流程（核心方法）

### 2.1 第一步：定义用户故事（从用户视角明确功能）

#### 2.1.1 用户故事的概念

- 定义：从用户的角度描述应用功能，说清"谁用、做什么、为什么做"，几个用户故事合起来就能覆盖应用的核心功能。
- 标准格式：`作为[某类用户]，我想[执行某个动作]，以便我可以[获得某种好处]`。
- 作用：让开发者跳出技术视角，盯住用户真正的需求，少做没用的功能。

#### 2.1.2 Mapty 项目用户故事实例（结合需求落地）

| 序号 | 用户故事内容                                                                         | 对应核心需求                           |
| ---- | ------------------------------------------------------------------------------------ | -------------------------------------- |
| 1    | 作为用户，我想记录跑步锻炼的位置、距离、时间、步速和每分钟步数，以便保存所有跑步记录 | 跑步数据录入与存储                     |
| 2    | 作为用户，我想记录骑行锻炼的位置、距离、时间、速度和海拔增益，以便保存所有骑行记录   | 骑行数据录入与存储（与跑步差异化字段） |
| 3    | 作为用户，我想一目了然查看所有锻炼记录，以便跟踪锻炼进度                             | 锻炼记录列表展示                       |
| 4    | 作为用户，我想在地图上查看所有锻炼记录，以便了解锻炼集中区域                         | 地图可视化锻炼位置                     |
| 5    | 作为用户，我想在离开应用后再次打开时查看之前的锻炼记录，以便持续使用                 | 数据持久化存储                         |

#### 2.1.3 从用户故事推导功能（例题）

- 例题：从"记录跑步锻炼"这个用户故事，推出要实现哪些具体功能。
- 解析：
  1. 记录位置：要一个地图组件（能点击选锻炼的位置）；
  2. 录入数据：要一个表单（距离、时间、步速、每分钟步数的输入框）；
  3. 定位优化：要地理定位 API（自动拿到用户当前位置，以它为中心渲染地图）；
  4. 保存数据：要本地存储（临时存跑步记录，刷新页面不丢）。

### 2.2 第二步：绘制流程图（梳理功能逻辑与数据流向）

#### 2.2.1 流程图的核心要素

- 包括：要实现的功能、模块之间怎么交互、触发的事件、数据怎么流。
- 推荐的颜色约定：
  - 黄色框：用户或系统触发的"动作"（比如"点击地图""提交表单"）；
  - 绿色框："界面渲染"操作（比如"显示地图""渲染锻炼列表"）；
  - 红色框："异步操作"（比如"调用地理定位 API""读取本地存储"，要等结果返回）。

#### 2.2.2 Mapty 项目流程实例（分场景梳理）

1. 页面加载：
   - 触发：页面第一次加载 / 刷新；
   - 流程：调用地理定位 API（红色，异步）→ 拿到用户坐标 → 渲染中心地图（绿色）→ 读取本地存储里的锻炼数据（红色，异步）→ 渲染锻炼列表 + 地图标记（绿色）。
2. 添加锻炼：
   - 触发：用户点击地图；
   - 流程：显示锻炼表单（绿色）→ 用户选锻炼类型（跑步 / 骑行）并填数据 → 提交表单（黄色）→ 验证数据 → 渲染锻炼列表 + 地图标记（绿色）→ 把数据存进本地存储（红色，异步）。
3. 定位到某条锻炼：
   - 触发：用户点击锻炼列表里的某条记录；
   - 流程：拿到这条记录的位置坐标（黄色）→ 地图自动移到对应位置（绿色）。

#### 2.2.3 流程图绘制技巧（避坑指南）

- 不用追求一版就完美：先画个粗略的草图，开发过程中再补细节（比如一开始可以先不管"数据验证"，后面再完善）；
- 从"事件"入手：每个流程都以用户操作（点击、提交）或系统事件（页面加载）为起点，逻辑就不容易乱；
- 标出依赖关系：异步操作要写明"等结果回来再做下一步"（比如必须先拿到定位，才能渲染地图）。

### 2.3 第三步：规划项目架构（确定代码组织方式）

#### 2.3.1 架构的核心定义

- 说白了就是代码怎么组织、加上技术选型（要不要用类封装数据、要不要拆成多个文件、要不要用框架）。不用搞得太复杂，目标是好维护、好扩展。

#### 2.3.2 中小型项目架构选择（推荐方案）

- 基础架构（适合这门课的 Mapty 项目）：
  1. 按功能模块拆函数：
     - 地图模块：`initMap()`（初始化地图）、`addMarker()`（添加锻炼标记）；
     - 表单模块：`showForm()`（显示表单）、`validateForm()`（验证数据）；
     - 存储模块：`saveToLocalStorage()`（保存数据）、`getFromLocalStorage()`（读取数据）。
  2. 用类封装锻炼数据（可选，代码复用性更好）：
     - 定义 `Workout` 父类，放共同的属性（位置、距离、时间）和方法（`save()`）；
     - 定义 `Running` 和 `Cycling` 子类，加各自特有的属性（跑步的"步速"、骑行的"海拔增益"）。

#### 2.3.3 架构规划误区（例题：反例分析）

- 反例：所有代码都写在一个 `script` 标签里，不拆函数，直接用全局变量存锻炼数据（比如 `let workouts = []`）。
- 问题：
  1. 污染全局变量：引入别的脚本时，`workouts` 可能被覆盖；
  2. 难维护：代码过了 500 行，就很难快速找到"添加锻炼"或"保存数据"的逻辑；
  3. 难扩展：以后要加"编辑锻炼数据"功能，得改一大堆原来的代码。
- 改进：用 IIFE（立即执行函数）把代码包起来，避免全局变量；按模块拆函数，比如把"存储相关"的逻辑单独封装。

### 2.4 第四步：进入开发阶段（落地规划）

#### 2.4.1 开发前的准备

- 确认技术：要用哪些 API 或库（比如 Mapty 项目要"Leaflet 地图库""地理定位 API""localStorage"）；
- 准备资源：拿到第三方库的 CDN 链接（比如 Leaflet 的 CSS 和 JS 文件），定好数据格式（比如锻炼记录的 JSON 结构：`{type: "running", distance: 5, time: 30, coords: {lat: 30.123, lng: 120.456}}`）。

#### 2.4.2 开发与规划的联动

- 开发中发现规划有漏洞（比如表单没考虑"数据格式错误"），就回头改流程图和架构（比如加一个 `validateForm()` 函数，补上"数据验证失败→提示用户"的流程）；
- 先把主要功能做出来：先完成"添加锻炼 + 显示地图"，再去优化"数据持久化""点击列表定位"这些次要功能。
