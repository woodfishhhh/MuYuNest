## 二、核心知识：事件循环实践核心示例

### 2.1 示例代码构建

视频先写了下面这段代码，引出事件循环执行顺序的问题：

```javascript
// 1. 同步代码：第一次打印“测试”
console.log("测试1");

// 2. 宏任务：零秒计时器（回调函数打印计时器内容）
setTimeout(() => {
  console.log("零秒计时器回调");
}, 0);

// 3. 微任务：立即 resolved 的 Promise（回调函数打印 Promise 结果）
Promise.resolve("Promise 成功结果").then((res) => {
  console.log(res);
});

// 4. 同步代码：第二次打印“测试”
console.log("测试2");
```

## 三、逻辑：事件循环执行顺序分析

### 3.1 第一步：明确任务类型分类

事件循环里，JavaScript 的任务分两类，执行顺序主要由它们的优先级决定：
| 任务类型 | 定义 | 本示例中的对应任务 |
|----------|------|--------------------|
| 同步任务 | 主线程直接执行，无需进入任务队列的代码 | 两次 `console.log("测试")` |
| 微任务（Microtask） | 优先级高于宏任务，同步任务执行完后立即执行，需进入“微任务队列” | Promise.then() 回调 |
| 宏任务（Macrotask） | 优先级低于微任务，微任务队列清空后才执行，需进入“宏任务队列” | setTimeout 回调（即使延迟 0ms） |

### 3.2 第二步：执行顺序推导（含例题验证）

#### 例题 1：基于上述代码，推导输出顺序

1. 第一步：执行同步任务
   主线程先把所有同步代码跑完，所以先输出：

   ```
   测试1
   测试2
   ```

2. 第二步：清空微任务队列
   同步任务跑完后，主线程先看微任务队列。这个例子里，`Promise.resolve()` 马上就 resolved 了，它的 `then` 回调已经进了微任务队列，所以执行微任务，输出：

   ```
   Promise 成功结果
   ```

3. 第三步：执行宏任务队列
   微任务队列清空以后，主线程才去看宏任务队列。`setTimeout(..., 0)` 的回调虽然延迟设的是 0ms，但它还是宏任务，到这时才执行，输出：
   ```
   零秒计时器回调
   ```
4. 最终的输出顺序：
   测试1 → 测试2 → Promise 成功结果 → 零秒计时器回调

## 四、拓展实验：微任务耗时对宏任务的影响

### 4.1 实验代码构建

为了看看"微任务优先级比宏任务高"实际会造成什么影响，视频又加了一个很耗时的微任务：

```javascript
console.log("测试1");

// 宏任务：零秒计时器
setTimeout(() => {
  console.log("零秒计时器回调");
}, 0);

// 微任务：含耗时循环的 Promise（模拟微任务执行耗时）
Promise.resolve("Promise 成功结果").then((res) => {
  console.log(res);
  // 模拟耗时操作：循环 1 亿次（阻塞主线程）
  for (let i = 0; i < 100000000; i++) {}
});

console.log("测试2");
```

### 4.2 实验现象与结论

#### 例题 2：分析上述代码的执行现象

1. 现象：运行后，"零秒计时器回调"明显晚了很多才输出，要等微任务里的 1 亿次循环跑完才出现
2. 结论：
   - JavaScript 的计时器（比如 `setTimeout`）保证不了"精确地延迟执行"，回调什么时候执行要看宏任务队列的调度
   - 微任务跑得久，就会挡住后面宏任务的执行，宏任务被推迟触发。这也说明了"微任务队列优先级高于宏任务队列"

## 五、视频总结与后续预告

### 5.1 知识点总结

1. 事件循环的执行流程：同步任务 → 清空微任务队列 → 执行宏任务队列（循环）
2. 任务优先级：同步任务 > 微任务（比如 Promise.then）> 宏任务（比如 setTimeout）
3. 注意：`setTimeout(..., 0)` 只表示"尽快执行"，不代表"0 秒后马上执行"，还要看微任务的执行情况
